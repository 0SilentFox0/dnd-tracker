# Рульові системи: база, модулі, пресети

Довідник для коду після E2 Ч17. Історія (межі wfrp 5a–5h, розділи Ч1–Ч16, ratchet E1) — [docs/archive/architecture/rule-systems-history-2026-11.md](../archive/architecture/rule-systems-history-2026-11.md); специфікації: [E1](../superpowers/specs/2026-11-10-architecture-modularity-design.md), [E2](../archive/superpowers/specs/2026-11-11-e2-d20-homm-modules-design.md).

Кампанія грає за **композицією** `rules.system = { key, modules? }`; `key` обов'язковий (без нього `parseRules` кидає `RulesSystemError`, API відповідає 422). Три шари: **core** (бій, лист, шаблони, не називає ні систем, ні модулів), **`systems/<id>/`** і **пакет шаблону** (`data/templates/<key>/` + хуки `scripts/templates/systems/<id>/`).

## Три види теки `systems/<id>/`

| Вид (`SystemMeta.kind`) | Що це | Приклади |
|---|---|---|
| `base` (типово) | повний набір хуків гри: правила, лист, бій, магія, UI, сервер; ключ(і) кампанії = `keys` | `d20` (`dnd5e`), `wfrp` |
| `addon` (модуль) | необов'язкова надбудова над базою з `requires`; додає секції правил, хуки, колонки, UI-слоти | `morale`, `retaliation`, `heroscaling`, `skilltrees`, `artifactsets`, `unitstacks` |
| `preset` | лише ім'я: база + набір модулів (`preset: { base, modules }`) | `homm` = `d20` + шість модулів |

Явний `system.modules` заміщує набір пресета; `modules: []` = «голий» base; відсутній `modules` = набір пресета; зміна `key` скидає `modules`. Вимкнення модуля нічого не видаляє (колонки, секції правил, рядки лишаються, їх лише ігнорують).

## Маніфест (`systems/<id>/meta.ts`)

Дані без логіки, `import type` (`SystemMeta`, `lib/utils/rules/systems/meta.ts`): `module`, `kind`, `keys`, `preset`, `requires`, `conflicts`, `claims`, `after`, `toggle` (`free | setup`; `setup` = зміна в кампанії з персонажами вимагає `confirm`), `distance`, `tokens` (підрядки для ratchet), `i18n` (слоти `battle | campaign | member | dm | pages`; див. нижче), `dmSections`, `contentKinds`. Із нього виводяться `systemScope`, бюджети `scope-size`, каталог модулів (`moduleCatalog()`, `moduleToggles`, `withModule`, `moduleChange`). **`meta.i18n`:** список namespace-ів на слот, який вантажиться разом з композицією через `systemScope(system, slot)` (`lib/i18n/system-scope.ts`: база + модулі за порядком): `battle` — екран бою (модульний UI бою: `battle: ['battleMorale']`), `campaign` — сторінки кампанії, `member` — гравець/учасник, `dm` — DM-сторінки, `pages.<scope>` — окремі сторінки (`character | dmCharacters | dmCharacter | dmRules | draft`). Модуль без власних текстів поза `gameTerms` — `i18n: {}`. `budgetKb` (gzip КБ на слот `battle|member|dm|pages.<scope>`) читає `lib/i18n/__tests__/scope-size.test.ts` лише в **бази** (типово ліміт 105 КБ на «кампанія+бій»); у addon воно ігнорується, а його namespace входить у тест «`<key>` battle + modules». Для кожного addon обов'язкові `gameTerms.module.<id>.{name,summary}`, для кожного ключа `gameTerms.ruleSystem.<key>`.

## Порядок композиції

`composition({ key, modules? })` → `{ base, modules }` (`catalog.ts`); `validateComposition` ловить `requires`, `conflicts`, подвійний `claims`, невідомий id, модуль не тієї бази, цикл; `systemIssues` = `validateComposition` + `validateSections` (одна перевірка для сервера, створення й `template validate`). `compositionOrder` — топологічно за `requires` + `after`, рівні за id. Згортка (`compose.ts`: `composeSystem`/`composeUi`/`composeServer`, `defineAddon`, `composeCached`): масиви й списки хуків конкатенуються (база, потім модулі), прості об'єкти зливаються вглиб, словники й групи задані в `FieldKinds`, скаляри й функції замінюються лише через `claims` (будівник отримує `prev`). Секції правил: `sectionsOf(composition)`, `extendSection`, колізія шляху між власниками — помилка; `merge?(current, patch)` у `RulesSection` дає спецзлиття (d20 `conditions`, core `encounters`, wfrp `tables`). `parseRules` розбирає по пунктах (невалідний → default), `mergeRules` зберігає секції неактивних модулів. Типи секцій `advancement`/`tables` додає wfrp через module augmentation `RulesetExtensions` (`section-shapes.ts`), core не імпортує `systems/wfrp`.

Дефолти правил: `SECTION_DEFAULTS` (`lib/utils/rules/defaults.ts`, без `system`) для нейтральних дефолтів пунктів; **`DEFAULT_RULES` — лише тестова фікстура** (homm), нетестовий код її не імпортує (ESLint `no-restricted-imports`; виняток `scripts/{sim,seed,constructor,import}/**`). Продакшн-код бере правила кампанії/бою, `rules` обов'язковий параметр; `PREVIEW_RULES` (`lib/utils/battle/fx/preview-rules.ts`) — d20-пісочниця анімації превʼю заклинання (ключ `PREVIEW_SYSTEM_KEY` береться з `SystemMeta.previewSandbox` (лише d20), без літерала й без залежності від порядку реєстру; страхується тестом `preview-rules.test.ts`: `kind === 'base'` і `combat.dice === 20`). Це мок-пісочниця (`PREVIEW_UNITS`, фіксовані кубики): її використовують `spell-preview.ts` і плейграунд, правила кампанії в превʼю не прокидаються (рішення власника, Ч19 F-17). Для баз без d20-касту кадри влучань ілюстративні.

Core бачить `systems/*` лише через корені (`SYSTEM_ROOTS`, `scripts/shared/system-ratchet.ts`) із блоками `// <systems:generated>`, які пише `pnpm systems:index` (перевірка `lib/__tests__/systems-index.test.ts`):

## Реєстр: пошук ≠ встановлення (Ч21)

- **Lookup** (`lib/utils/rules/systems/lookup.ts`, `lib/server/systems/lookup.ts`): `ruleSystemOf`, `systemServerOf`, `RULE_SYSTEM_REGISTRY`, `SYSTEM_SERVER` читають таблицю встановлених записів, самі систем не імпортують, тож не створюють циклів. Виклик до встановлення кидає `SystemNotInstalledError`.
- **Корінь** (`registry.ts` поруч) імпортує всі `systems/<id>` і викликає `installModules(entries)` (rules) / `installServerModules(entries)` (server). Серверний корінь імпортує й rules-корінь, тож встановлення сервера ставить обидва.
- **Де стоять корені.** Правило: будь-який модуль, що першим входить у граф маршруту й викликає `*Of`, має корінь у своєму статичному графі (~13 серверних сервіс-файлів, `lib/server/battles/run-mutation.ts` та ін.). Тест `lib/__tests__/system-install-entries.test.ts` перевіряє точки входу; нова точка входу без кореня = червоний тест. Тестам прогрів (`beforeAll(import registry)`) не потрібен: якщо тест викликає `*Of` без маршруту/сервісу в графі, він має статичний `import '@/lib/server/systems/registry'` (або rules-реєстр).
- **Ратчети:** `registry-cycles.test.ts` — `KNOWN_CYCLES = []` (раніше `rules:d20`, `server:d20`); `utils-no-server-imports` — `lib/utils` не імпортує `lib/server` (0). Файли, що переїхали: `from-character.ts` → `lib/server/battles/participant/`, `persist-*`/`save-battle` → `lib/server/battles/store/`, `parse.ts` компендіуму → `lib/utils/compendium-import/`, `bundle-error.ts` → `lib/server/templates/`, `content-routes.ts` → `lib/server/content/`.
- **`sideEffects`.** Корінь працює лише побічним ефектом (`installModules(...)` на верхньому рівні), а бандлер викидає голі імпорти модулів без запису у `"sideEffects"`. Кожен новий голий імпорт кореня (`import '@/…/registry'`) мусить підпадати під запис у `package.json` (зараз `**/systems/registry.ts`); після змін перевіряти `grep -o "installModules)(" .next/server/chunks/*.js` у свіжій збірці.
- **Часткове встановлення.** Клієнт ставить лише модулі однієї композиції (`loadSystems`), тож `installModules`/`installUiModules` зливають записи, а `ruleSystemOf`/`systemUiOf` резолвлять лише вибрану композицію; `RULE_SYSTEM_REGISTRY`/`SYSTEM_UI` містять тільки встановлені ключі (невстановлений ключ = `undefined`, не виняток). Тести цього — з ізоляцією `vi.resetModules()` (глобальний `vitest-setup` ставить rules-корінь). Серверний і UI-корені `vitest-setup` не ставить (вони тягнуть увесь серверний/компонентний граф у кеш модулів до `vi.mock` тесту): тест, що викликає `systemServerOf`/`systemUiOf`, сам імпортує `@/lib/server/systems/registry` / `@/components/systems/registry`; тест, що мокає барель `@/lib/utils/rules/systems` або модуль з графа rules-кореня, робить `vi.resetModules()` і динамічні імпорти предмета тесту.
- **Сервер і браузер — різні екземпляри модулів.** `system-install-entries` рахує корінь окремо для серверного замикання (до `'use client'`) і для об'єднання клієнтських замикань сторінки; серверний корінь не рятує клієнтський компонент, його рятує `SystemGate`/`install.ts` або клієнтський корінь. Скрипти (`scripts/**`) мають імпортувати корінь самі.
- **Клієнт (`components/systems/`).** `lookup.ts` (`systemUiOf`, `SYSTEM_UI`, без записів) ≠ `registry.ts` (eager-корінь UI: лише тести й сторінки без гейта) ≠ `install.ts`: `loadSystems(selection)` через згенеровану мапу `LOADERS` робить `import()` rules, UI й ability-модуля кожної системи композиції (з `requires`), ідемпотентний, один повтор, збій забувається. `SystemGate` на сервері й першій гідратації віддає скелет (`LoadingState`), далі `useSyncExternalStore` до `isSystemReady`; застарілий чанк після деплою — один `location.reload()` (прапор у `sessionStorage`), потім помилка. Вхідний чанк бою не містить жодного `systems/*` крім `meta.ts` (тест `client-entry-imports`).
- **Ability-реєстри (Ч21).** Рядки реєстру ефектів, рядки прапорців і змінні формул ставляться так само: `lib/utils/abilities/registry/install.ts` (`AbilityModule { effectRows, moduleEffectRows, flagRows, variables }`, `installAbilityModules`, `onAbilityInstall`), шар у модулі — `systems/<id>/rules/ability-install.ts` (`<ID>_ABILITY_MODULE`; d20, morale, retaliation, wfrp). Rules-корінь `lib/utils/rules/systems/registry.ts` викликає `installAbilityModules(ABILITY_MODULES)` разом з `installModules` (серверний корінь імпортує його, тож сервер ставить усе); на клієнті ability-модуль грузить `loadSystems` у складі композиції. Похідні таблиці (`EFFECT_REGISTRY`, `FLAG_REGISTRY`, `FLAG_KEYS/FLAG_OPTIONS/FLAG_FIELDS/FLAG_DEFAULTS`, `ABILITY_VARIABLES`/`FORMULA_VARIABLE_NAMES`, `SYSTEM_EFFECT_ROWS/DEFAULTS/OWNERSHIP`, `MODULE_EFFECT_*`, `SYSTEM_ABILITY_VARIABLES`, `ALL_KINDS`/`EFFECT_DEFAULTS` редактора) перезаповнюються на місці після кожного встановлення (посилання на них лишаються дійсними); читати їх у `const` на верхньому рівні модуля можна лише як посилання, а не як знімок. Ефект модуля, якого немає в клієнтській композиції, не має власника й рядка в реєстрі: `applyEffect` для нього no-op (виняток: kind без власника й без рядка в реєстрі — помилка, а не мовчання), `describeEffect`/`describeFlag` дають `summary.unknownEffect`, `FlagEditor` — порожній набір полів. Контракт-тест `ability-install` (`schema and rows stay in step`): кожен kind/flag зі схеми має рядок після rules-кореня. Zod-схеми ефектів і прапорців (`ability-effects`, `ability-flags`, `ability-module-effects`) лишаються статичними коренями `schema/system-*.ts`: вони входять у zod-юніони при завантаженні й не потрапляють у чанк бою (бій не тягне zod). Рядки/змінні взяті в `system-install-entries` парою `lib/utils/abilities/registry/install.ts` ↔ rules-корінь: скрипти й маршрути, що досягають реєстру ефектів, мусять мати корінь (`import '@/lib/utils/rules/systems/registry'` у скриптах).
- **Перевірка збірки (2026-11-14, `next build`, Turbopack).** Серверні чанки маршрутів з `ruleSystemOf` (`ai/proposals`, `ai/threads`, `battles/[battleId]/{attack,spell,next-turn}`, `campaigns`, `characters`) містять виклики `installModules(`, `installServerModules(` і `installAbilityModules(`; відсутні вони лише в маршрутах без систем (`locale`, `theme`, `scenario/*`, `world/*` тощо). Команда: для кожного `.next/server/app/.../route.js` взяти `R.c("server/chunks/...")` і `grep "installModules)("` по цих чанках.
- **Лишилося клієнтським винятком.** `CLIENT_LAZY` (`app/campaigns/page.tsx`) — без кампанії, `*Of` не викликає; `STATIC_SAFE` — статичні сторінки без композиції.
- **Гейт кампанії (Ч21).** `CampaignSystemGate` (`components/systems/`) бере композицію з `useCampaignSystemSelection` (сід із layout, потім завантажені `rules`) і обгортає `SystemGate`; без композиції (`null`) пропускає дітей. Його ставлять серверні `layout.tsx` клієнтських піддерев `app/campaigns/[id]/{dm,show,world,acquaintances}` та `battles` (бій теж: його хуки викликають `*Of` вище за `SystemGate` сторінки) через спільний `app/campaigns/[id]/system-layout.tsx`/`battles/layout.tsx`; сід дає `systemSelectionOfCampaign` (невідомий ключ → без гейта, невідомі модулі відфільтровано) (він же імпортує серверний корінь для RSC-сторінок піддерева): сторінки без правок, SSR цих піддерев віддає скелет. Дашборд, профіль, інфо, чернетки гейтяться на рівні сторінки (потрібен перший HTML). `system-install-entries` зараховує корені й гейти з `layout.tsx` над сторінкою (без їхніх lookup-ів) і сам перевіряє `layout.tsx` як точки входу (`LAYOUT_SAFE`: кореневий і `[id]/layout.tsx` читають лише захищено — `classesEnabled`, `ruleSystemByKey`); тест не доводить, що lookup стоїть саме під гейтом, це покриває `battles/__tests__/layout.test.tsx` (happy-dom, без кореня). Зміна композиції ДМ: `useUpdateCampaignRules` перед `setQueryData` чекає `preloadSystem` (`lib/utils/rules/systems/preload.ts`, його реєструє `install.ts`), тож гейт не повертається до скелета й діти не перемонтовуються; `useCampaignSystemSelection` лише читає кеш (`rules` не запитує). Прапорець `system-gate-reloaded` скидається після успішного завантаження. `ruleSystemByKey` (`ActionResultCard`, `fx/dice/from-action`) резолвить голий ключ-пресет: для кампанії з явними `modules` ≠ пресет картка/dice-FX системної частини можуть не з'явитися (відомо, композиції в контексті картки нема). `system-layout` доступ не перевіряє (не-член лише завантажить чанки; дані віддають API). Виняток `CLIENT_LAZY`: `app/campaigns/page.tsx` (без кампанії; `*Of` не викликає, lookup лише статично через барель хуків).

## Слоти

**`SystemSlot = { key, data }`** (`lib/utils/rules/systems/slot.ts`), `defineSlot(key, parse)` → `{ read, write }`; чужий ключ → `read()` = `undefined`. `SlotCodec.extend(module, parse)`: дані модуля в `data.ext[module]`, `write(data, prev?)` переносить `prev.ext`. Слоти в core-типах: `abilities.system`, `attack.system`, `sheet.systemSlot`, `actionDetails.system`/`AttackRollResult.system`, `scene.system` (`battle_scenes.system_state`), `characteristics` (непрозорий `SystemData`).

Кодеки бази: d20 — `D20_STATE` (`systems/d20/rules/state.ts`, поряд `d20State`/`withD20State`/`d20StateData`), wfrp — `PARTICIPANT_STATE` (`systems/wfrp/rules/slots.ts`, `wfrpState`/`withWfrpState` у `state.ts`); модуль розширює кодек своєї бази: `D20_STATE.extend(...)` / `PARTICIPANT_STATE.extend(...)`.

**Слот стану учасника бою** — `battleData.system = { key: <база>, data: { …поля бази…, ext: { <модуль>: … } } }` у колонці `battle_participants.state` (і `battle_snapshots.state`), не в знімку; `snapshotHash` стабільний. База пише свої поля в `data`, модуль — лише свій ключ `ext` (напр. `ext.retaliation.used`). d20: `systems/d20/rules/state.ts` (`d20State`/`withD20State`/`d20StateData`; `deathSaves`, `inspiration`, `inspirationSpent`, `attackedWithLight`), wfrp: `systems/wfrp/rules/state.ts` (`fortune`, `channelledSl`, `sin`, `conditionTests`, `psychologyTested`). Нейтральний прапорець `battleData.dying` (`isDying(p)` = `dying === true`) каже core «лежить на 0 HP» без знання лічильників. Плоских полів і dual-read більше немає (прибрано в Ч17). **Видимість:** слот і інші поля стану (`battleData.system`, `battleData.dying`, `combatStats.moraleCap`, `scene.system`, стати ворогів) видимі гравцеві в мережі, приховування лише в UI ([participant-privacy-scope.md](participant-privacy-scope.md)); система не кладе секретів у слоти стану.

## Таблиця хуків і слотів

Позначки: **обов'язковий** (база мусить дати), **необов'язковий** (немає хука = нейтральна поведінка core), **список** (конкатенується за порядком композиції).

`RuleSystemDefinition` (`lib/utils/rules/systems/types.ts`; типи слотів у сусідніх `types-{combat,turn,actions,conditions,magic,sheet,participant}.ts`, `types.ts` реекспортує їх, тож імпорт лишається з `types`). `combat.saves`/`combat.proficiency` необов'язкові: читач — `savesOf`/`proficiencyOf` (`lib/utils/battle/saves/access.ts`), відсутній слот = `noSaves`/`noProficiency`:

**D15 (види контенту й композиція).** Вид, чий власник — модуль поза композицією кампанії, прихований: список `[]`, інші дії й імпорт 404, рядки не видаляються. Sync гейта не проходить.

**Читання характеристик статблока в core — лише через хуки:** модифікатори рятунків — `combat.saves.modifiers(p)` (баланс: `hitModel.saves(p)`), бонус майстерності — `combat.proficiency.bonus(p)`, бонус атаки закляття — `magic.spellAttackBonus`; система без цього віддає нулі. Необовʼязковий `combat.holdsOn?(p)` (Ч18c; d20 — `systems/d20/rules/death-saves/holds.ts`, поруч з `onRevived`): полеглий учасник, що ще в бою (d20: вмирає й не стабільний); core не читає `stable` слота, а `checkVictoryConditions` бере хук, щоб не віддавати поразку, поки герой робить кидки смерті.

**E4 / трек S (S.4):** для дев’яти d20 характеристик єдине правило читання: числове `characteristics[key]`, інакше legacy-колонка, інакше дефолт кодека (`readD20Columns`, `withStoredColumns`, `withColumnView`). S-B продовжує dual-write у колонки та JSON, тож відкат S-B → S-A безпечний; зупинка запису в колонки має бути окремим деплоєм перед S.6. M1: level-up, PATCH персонажа й оновлення чернетки перечитують `characteristics` під блокуванням перед merge; `units.update` працює під campaign-content lock і читає рядок у цій транзакції. DB/seed-скрипти, що зливають статблок, також блокують рядок і перечитують JSON. S.6 має два зафіксовані ризики: після DROP зміняться хеші шаблонів, якщо `characteristics` не містить усіх дев’яти ключів; до DROP результати `withColumnView` і `withStoredColumns` треба типізувати як `T & D20Columns`, бо споживачі читають плоскі поля з Prisma-рядків. D20 `--report --expect-zero` перевіряє лише d20-вибірку й рівність JSON колонкам; цього недостатньо для DROP після зупинки dual-write. До S.6 потрібен окремий all-system аудит наявності дев’яти JSON-ключів і порівняння хешів до/після DROP, зокрема для WFRP та інших не-d20 рядків. Див. [план контрактного кроку](../superpowers/plans/e4-s6-drop-columns/README.md).

**Винятки й домовленості контракту.**
- d6pool (і будь-яка база без `magic.resource`) кастує вільно: слотів/ресурсу немає, `picksSlot` відсутній (Ч7-M2).
- Бойова операція, якої немає в базі кампанії, дає 422 `action_rejected` (з `missing`); 404 `systemActionUnknown` лише коли такої дії немає в жодній системі чи модулі композиції (Ч7-M7).
- Змінені коди відмов (Ч11-M3): `condition-test`/`system-condition` без wfrp — `action_rejected` замість `invalid_target` (ключ `CONDITION_UNSUPPORTED` той самий, статус 422); `PUT race-profile` гравцем — `DM_ONLY` замість `FORBIDDEN`; `PUT race-profile` без `creation` — тіло парситься першим, невалідне = 400 замість 409; `race-profiles` у не-wfrp кампанії — 404 замість 200. Права (404/403 учасника кампанії) перевіряються до парсингу тіла операції.
- Гарди DM-сторінок у `layout.tsx` не перевиконуються при клієнтській навігації; прийнято, бо CRUD-маршрути самі дають 404 (Ч11-M6). Меню з модульними розділами з'являється після гідратації правил, не в першому HTML (повний варіант потребує пропса `Header` з кореневого layout).
- Тести core можуть брати фікстури систем (`WFRP_RULES`, `withD20State`, …): тести поза ESLint-зонами. Імпорт UI системи в тест core (як `PrimaryAbilityPicker`) — ні, такий тест лежить у `systems/<id>/__tests__/ui/`.

## Правила зони

- **Зона.** Поза коренями й `system-imports-exempt.json` нічого не імпортує `@/systems/*` (ESLint `systems/zone`).
- **Шари всередині системи** наслідують правила core: `rules/**` = `lib/utils`, `ui/**` = `components`, `hooks/**` = `lib/hooks`, `api/**` = `lib/api`, `server/**` без обмежень шару. Система не імпортує іншу систему (лише теки з `requires`), `@/app/*`, `@/scripts/*`; `meta.ts` — лише `import type`.
- **Контракт** (`lib/__tests__/system-contract.test.ts`): ключі meta = логіка = UI = сервер = `PACK_HOOKS`; кожен namespace meta має файл у `messages/{uk,en}`; `assertSystemContract` проходять і реальні системи, і фікстура `d6pool` (`lib/__tests__/fixtures/d6pool`, `d6pool-plus` — модуль, `d6pool-alt` — той самий `claims`). Матриця композицій — `system-composition-matrix.test.ts`; бій без d20 — `lib/__tests__/d6pool-battle.test.ts` (граф імпортів зупиняється на коренях і не досягає жодного `systems/*`).
- **Гард колонок статблока** `lib/__tests__/statblock-guard.test.ts`: правила core не читають `abilities.<d20-колонка>` (дозволені будівники/мапери `battle/participant`, `battle/store`, `battle/transform`, `abilities/build`); максимум лише падає.
- **Статблок d20 у `characteristics` (E4 S).** 9 колонок (`strength…charisma`, `armorClass`, `initiative`, `speed` у `characters`/`units`/`unit_bases`) живуть у `characteristics` d20-рядка; колонки в S-B пишуться разом із `characteristics` (dual-write; припинення запису колонок — окремий крок перед DROP, S.6). Кодек — `columnView` системи (`systems/d20/rules/characteristics/codec.ts`): `read`: `characteristics[key]` якщо число, інакше колонка рядка, інакше дефолт кодека, `write` зливає у попереднє значення. Обгортки `lib/utils/rules/systems/column-view.ts`: `withColumnView(row, system)` (читання з композицією; рядок без ключа `characteristics` не чіпає), `withStoredColumns(row)` (без рулсету, те саме правило: збережене число перекриває колонку, інакше колонка), `flattenStoredColumns` (експорт/пакети лишаються плоскими, `characteristics` зникає, якщо крім статблока там нічого), `splitColumnView` (запис), `d20RowData` (скрипти). Шар завантаження накладає вигляд один раз (`gateCharacter`, `toUnit`, summon-pool, балансові завантажувачі), будівники учасників накладають самі. DTO/API лишаються плоскими; у відповідях d20 ключі статблока прибрано з `characteristics` (`columnViewDto`, `flattenStoredColumns` у get/list/`toUnit`); чужі ключі й `characteristics` інших систем лишаються. `characteristics.persisted` d20 лишається `false` — прапорець означає «система володіє власною формою characteristics» (схема, `CHARACTERISTICS_REQUIRED`, лист), а не просто сховище. Гарди: `statblock-write-guard` (запис без `characteristics`), `statblock-guard` (select колонки без `characteristics`, читання колонки з завантаженого рядка без накладання; списки винятків лише зменшуються).
- Блокування: зміна `system.key` у кампанії з `characters`/`units` → 409 `SYSTEM_LOCKED`; зміна `modules` — 422 `SYSTEM_MODULES_INVALID`, 409 `SYSTEM_MODULES_IN_BATTLE` (лише активний бій), 409 `SYSTEM_MODULE_CONFIRM` (`toggle: "setup"`).
- `system` не механіка: вкладки правил = секції композиції.

**Skilltrees (L4c).** `systems/skilltrees` володіє UI прокачки (`ui/progression`), хуками (`hooks`), правилами редактора/перегляду/переносу дерева (`rules/progression`, `rules/form`, `rules/tree-transfer`) і `SystemServer.participant.skillEntries` (вивчені вузли + персональне вміння для бою). Модель дерева (`lib/utils/skills/progression`: types/normalize/resolve/tree-json/validate/progress) лишається в core — її читають бій, лист героя і шаблони; `SystemUi.sheet.overlays` дає оверлей level-up без прямого імпорту. Відкладено: `skill-trees.*` content-операції (`operation-service`), `lib/server/skills/*`, `placement` (друк навичок), `source-sync` scopes.

**UI-слоти Ч23.** `SystemUi.dmPages: Record<section, ComponentType<DmPageProps>>` (`view`: list/new/edit, `data`) — сторінки видів контенту модулів (`classes`, `backgrounds` — d20; `skills`, `skill-trees`, `main-skills` — skilltrees; `artifact-sets` — artifactsets; `careers` — wfrp); `app/**` рендерить `SystemDmPage`, 404 — `dmSectionLayout`/`notFound`. `SystemUi.fx.dice: SystemDiceSource[]` (`(event) => SystemDice | null`, конкатенація модулів; `morale` дає кубик перевірки моралі); `SystemUi.fx.badges: Partial<Record<FxBadgeKey, TextRef>>` — текст бейджа замість нейтрального core-підпису (`morale` → `raincloud` «−N мораль»; дубль ключа між модулями = `CompositionError`), core-хуки `useBattleFxQueue`/`useFxImpacts`/`useBattleMapScene` беруть слот параметром.

Тест `lib/i18n/__tests__/label-keys-<ns>.test.ts` не обов'язковий: ніщо його не вимагає, `tsc` вже ловить статичні ключі; `expectLabelKeys` потрібен лише для ключів, що збираються динамічно.
5. Прапорці модуля, що живуть у правилах (`deathsaves`, `inspiration`), зберігаються в `rules` і заповнюються пресетом `dnd5e` (`rules-preset.ts`); увімкнення таких модулів на голій `d20` потребує ручного перемикача прапорця у формі правил (за замовчуванням `false`).
6. `pnpm systems:index`; звірити `system-contract`, `systems-index`, `system-composition-matrix`, `module-toggle-d16`, `content-kinds-contract`, `stat-columns-contract`, `system-literals`.

## Рецепти модуля

Експеримент-контроль (flanking на d20, fatigue на wfrp): [research/2026-11-14-module-experiment.md](../superpowers/research/2026-11-14-module-experiment.md).

**Скаляр чи список.** Згортка (`compose.ts`): масиви конкатенуються; прості об'єкти зливаються вглиб; усе інше (функція, число, рядок, група з `SYSTEM_FIELD_KINDS.groups` = `magic`, `conditions`) замінюється лише якщо шлях є в `meta.claims`, інакше `CompositionError "replaces … without a claim"`.

| Хук | Вид | Як модулю втрутитись |
|---|---|---|
| `combat.resolveAttack`, `abortedRoll`, `initiative`, `tieBreak`, `hitModel.*`, `damage`, `onZeroHp`, `progression.maxHp` та інші функції | скаляр | `claims: ['combat.resolveAttack']` + обгортка `prev` |
| `combat.turn.*`, `combat.actions.onMove`, `afterAttack`, `onDamaged`, `damageParts`, `participant.*`, `stats.columns`, `sheet.blocks` | список | просто додати елемент |
| `magic`, `conditions` | група | лише claim усієї групи |

**Обгортка скаляра** (так роблять `heroscaling`, `unitstacks`, flanking). Заявлений шлях — крапкова адреса поля; `prev` — уже зібрана база (і попередні модулі):

```ts
// meta.ts: claims: ['combat.resolveAttack']
export const X_MODULE = defineAddon<RuleSystemDefinition>((prev) => ({
    combat: { resolveAttack: (ctx) => prev.combat.resolveAttack(adapt(ctx)) },
}));
```

**Плоский бонус до атаки.** Через `ResolveAttackCtx.modifiers: Record<participantId, StaticEffect[]>` — додати `StaticEffect` (`{ kind: 'modifyStat', stat: 'attackBonus', flat, attackKind? }`) для нападника в `adapt(ctx)`; d20 `resolveAttack` читає його як `extra`/`targetExtra`. Обмеження: позачергові удари (`ctx.offTurn`: відсіч, нагода, readied, legendary) ідуть через `resolveOffTurn`, який `modifiers` ігнорує, тож бонус на них не діє; модуль мусить явно перевіряти `ctx.offTurn` і не обіцяти бонус там.

**Модуль зі станом** (приклад fatigue на wfrp; для d20 — `D20_STATE`, див. `systems/retaliation/rules/state.ts`):

```ts
export const FATIGUE_STATE = PARTICIPANT_STATE.extend<{ level: number }>(
    'fatigue', (raw) => isRecord(raw) && Number.isFinite(raw.level) ? { level: raw.level as number } : undefined);
const withFatigue = (p, level) => ({ ...p, battleData: { ...p.battleData,
    system: FATIGUE_STATE.write({ level }, p.battleData.system) } });
```

`write(data, prev)` обов'язково отримує поточний слот (`p.battleData.system`): з нього переносяться поля бази й чужі `ext`; зворотне теж — запис бази зберігає `ext` (`defineSlot.write`). Якщо слота (або слота іншого `key`) немає, створюється `{ key, data: { ext: { <модуль>: … } } }` без полів бази — база мусить читати такий слот толерантно. Читання чужого ключа слота = `undefined`.

**Який хук для лічильника.** `turn.resetState(p, 'turn' | 'reaction')` — обнулити per-turn значення, коли хід починається (або повернулась реакція; приклад retaliation); `onTurnEnd` — змінити стан суб'єкта після ходу (`ctx.id` = чий хід; фільтрувати за ним); `onRoundStart` — раз на раунд для всіх; `onTurnStart` — коли хід настав (можна `skipTurn`/`pending`); `onJoin` — вхід у бій. Хук повертає `{ participants, messages: LogLine[] }` (порожній масив допустимий).

**Корені й імена експортів.** `pnpm systems:index` (`scripts/shared/systems-index.ts`) додає рядок кореня лише коли файл шару експортує точне ім'я `export const|function <ID>_…`: `<ID>_META` (`meta.ts`), `<ID>_MODULE` (`index.ts`), `<ID>_MODULE_UI` (`ui/index.ts`), `<ID>_ABILITY_MODULE` (`rules/ability-install.ts`), `_SERVER`, `_HOOKS`; `<ID>` = id у верхньому регістрі, не-латинські/цифри → `_`. Інше ім'я чи `export { X }` — рядка тихо немає й жодного повідомлення; після запуску звіряти `git diff` коренів.

**Тест модуля в композиції.**

```ts
import '@/lib/utils/rules/systems/registry';          // ставить корінь rules
const rules = RulesetSchema.parse({ ...WFRP_RULES, system: { key: 'wfrp', modules: ['fatigue'] } });
expect(validateComposition(rules.system)).toEqual([]);
const hooks = ruleSystemOf(rules).combat.turn?.onTurnEnd ?? [];   // `?? []`: бази без хука дають undefined
runTurnHooks(hooks, { participants, id, round: 1, rng, rules });
```

Для d20: `{ ...DEFAULT_RULES, system: { key: 'dnd5e', modules: ['flanking'] } }` (фікстура лише для тестів).
