# i18n core Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Мультимовність `uk`/`en`: інфраструктура, пілот (`auth` + `landing` + перемикач мови) і ESLint-храповик; решта доменів переноситься частинами 1–6.

**Architecture:** `next-intl` без префікса в URL; мова з cookie `NEXT_LOCALE` → `Accept-Language` → `uk`; `User.locale` синхронізується з cookie при вході й зміні мови. Тексти в `messages/<locale>/<ns>.json` за `MessageSource`; не-React код віддає ключі, переклад на межі (`getTranslator`, `translateIssue`).

**Tech Stack:** next-intl 4, use-intl, Next 16 App Router, Zod 4, Prisma 6, Vitest 4, ESLint 9 flat config.

**Spec:** `docs/superpowers/specs/2026-10-28-i18n-core-design.md`

**Розмір плану.** Тут детально розписана лише частина 0 (інфраструктура + пілот). Частини 1–6 — зміст і межі; перед кожною окрема сесія пише власний детальний план `docs/superpowers/plans/2026-10-28-i18n-part-N.md` (за зразком world-map: «plan part N»). На ~150–200k токенів — стоп, оновити handoff.

## Review Focus

1. Невалідне значення cookie (`NEXT_LOCALE=fr`, порожнє, сміття) → `uk`, без падіння.
2. `Accept-Language: en-GB,en;q=0.9,uk;q=0.8` і `*`, `de` → `en` / `uk` за пріоритетом q; невідомі мови → `uk`.
3. Ключ є в `uk`, але відсутній в `en` → показується `uk`-текст, не ключ і не виняток.
4. Українські плюрали ICU (`one/few/many/other`: 1, 2, 5, 21, 11) у `en` не ламають паралельні ключі; тест паритету ловить розбіжність плейсхолдерів.
5. `PUT /api/locale` з невалідним `locale` → 400; неавторизований користувач → cookie ставиться, БД не чіпається; `User.locale = null` → cookie не перезаписується.

## Рішення: статичний лендинг (варіант B, затверджено)

`docs/architecture/landing-auth.md`: лендинг статичний (`○ /`, CDN), а `cookies()`/`headers()` у `app/layout.tsx` зробили б динамічними всі сторінки. Тому:
- **Root layout лишається статичним** і не читає запит. `<html lang="uk">` статичний; клієнтський `HtmlLang` оновлює `document.documentElement.lang`. Початковий HTML має `lang="uk"` (і на `/`) — відомий компроміс, SEO страхують `hreflang` і `canonical`.
- **Лендинг на двох URL:** `/` (`en`, x-default) і `/uk` (`uk`), обидва статичні, з явним `NextIntlClientProvider locale=…` (не залежать від request-конфіга). `proxy.ts` робить rewrite `/` → `/uk` для cookie `uk` або `Accept-Language: uk` (без cookie); rewrite відбувається до CDN-кешу.
- **Застосунок** (campaigns, settings, help, `(auth)`) — динамічні сегменти; кожен має `layout.tsx` із серверним `<LocaleScope namespaces>` (мова з cookie через `getRequestLocale`).
- **Root-chrome** (лінивий `Header`, `ConfirmProvider`, `error.tsx`, `not-found.tsx`) отримує мову з клієнтського `ClientLocaleProvider`: статичний HTML — `uk`, після монтування читає cookie. Оскільки `Header` — `dynamic()`-чанк, а діалоги з'являються після взаємодії, SSR-розбіжності немає. Тому cookie ставиться з `httpOnly: false`. Повідомлення обох мов для `common`+`validation` вбудовуються в чанк.
