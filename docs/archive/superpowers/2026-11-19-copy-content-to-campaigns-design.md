# Копіювання контенту бібліотек в інші кампанії — дизайн

Дата: 2026-11-19. Статус: чернетка на огляд.

## Мета

Клієнт може взяти вже створений контент зі своєї кампанії й скопіювати його в одну, кілька або в усі свої кампанії, не створюючи його вдруге.

**Критерій успіху:** DM відкриває будь-яку бібліотеку, вибирає елементи, у діалозі вибирає кампанії (або галочку «Усі кампанії»), бачить попередній перегляд і після підтвердження отримує копії в цілях. Копія не залежить від оригіналу.

## Рішення власника

- **Обсяг:** 13 видів `ContentKind` (`lib/constants/content-kinds.ts`) + карти (звуки знято: бібліотека звуків акаунтна, доступна в усіх кампаніях) (`BattleMap`).
- **Залежності** копіюються автоматично й транзитивно, id переписуються. Сутність, яка вже є в цілі за назвою, перевикористовується, не дублюється.
- **Файли** (звуки, фони карт) копіюються як нові об'єкти в сховищі цілі, а не ділять один файл між кампаніями.
- **Три етапи**, кожен з окремим мерджем: (1) ядро + 13 `ContentKind` + UI; (2) звуки — знято (акаунтні); (3) карти; далі файлові треки.

## Припущення (не від власника, можна змінити)

- Цілі: лише кампанії, де користувач має роль DM. «Усі кампанії» = усі такі, крім джерела.
- Копія незалежна: пізніші правки оригіналу її не змінюють.
- Вибраний елемент, що вже є в цілі за назвою, пропускається й потрапляє у звіт. Режиму «перезаписати» немає.

## Що перевикористовується (за CLAUDE.md) і чому потрібне нове

| Існує | Роль |
|---|---|
| `lib/server/templates/{export-campaign,bundle,remap-ids,import-bundle}.ts` | Кампанія → бандл → переписування id → запис у кампанію (шлях клонування шаблонів). **Основний кандидат** на ядро копіювання. На старті плану перевірити, чи підтримує вибіркове підмножинне копіювання; якщо ні, додати фільтр за id, а не писати паралельний шлях |
| `lib/server/content/import/{export,import-content}.ts` | Експорт у `ImportRecord` з посиланнями назвами та `importContent` (валідація всього до запису, `dryRun`, Zod ресурсу). Запасний шлях, якщо бандл-шлях не годиться; обмеження: поля без колонки в `IMPORT_SPECS` йдуть у `extra` |
| `scripts/templates/lib/import-order.ts` | Порядок видів за залежностями. Лежить у `scripts/`, тож `lib/` його не імпортує: переносимо чисту функцію в `lib/utils/content/` і залишаємо реекспорт у скрипті |
| `requireDM`, `requireCampaignAccess`, `parseBody`, `errorResponse` (`lib/utils/api`) | Доступ і помилки |

| `lib/server/soundboard/sound-store.ts`, `lib/supabase/soundboard-storage.ts` | Шлях об'єкта, ліміт `MAX_SOUNDS_PER_CAMPAIGN`, перевірка завантаженого звуку |

Нове: **розрахунок набору копіювання** (транзитивні залежності вибраного й відсів дублів за назвою в цілі) та діалог вибору кампаній.

## Архітектура

Шари за CLAUDE.md: роут → `lib/api/content-copy.ts` → хук `lib/hooks/content-copy/` → компонент. Компоненти не імпортують `lib/api`.

### API

`POST /api/campaigns/[id]/content-copy` (id = кампанія-джерело).

```
body: {
  items: [{ kind: ContentKind | 'sounds' | 'maps', ids: string[] }],
  targets: { campaignIds: string[] } | { all: true },
  dryRun?: boolean
}
response: {
  targets: [{
    campaignId, name,
    status: 'ok' | 'partial' | 'failed',
    created:  [{ kind, id, name }],
    reused:   [{ kind, id, name }],   // уже було в цілі, використано як залежність
    skipped:  [{ kind, name, reason }], // вибране вже є / вид не підтримано цілью / ліміт
    error?:   string
  }]
}
```

Роут тонкий: Zod, сесія, `requireDM` на джерелі, делегування в сервіс. Помилки у форматі `{ error, issues? }` з текстами в `lib/constants/api-errors.ts`.

### Сервіс `lib/server/content/copy/`

- `resolve-targets.ts`: список цілей. Для `all` це кампанії користувача з роллю DM, без джерела. Для явного списку кожну id перевіряє на роль DM. Чужа або недоступна кампанія дає 403, а не мовчазний пропуск.
- `plan.ts`: від вибраних елементів транзитивно збирає залежності, відсіює дублі за назвою в цілі, відкидає види, які ціль не підтримує (`isKindActive`). Порядок запису за `importOrder`. Цикли (`spells ↔ units`, `artifacts ↔ artifact-sets`) розв'язуються другим проходом, як у шаблонах.
- `apply.ts`: пише кожну ціль в окремій транзакції. Збій однієї цілі не відкочує інші; звіт по кожній. Після запису один раз інвалідовує кеш довідника цілі.
- `dryRun` проходить `plan` і валідацію, нічого не пише. Попередній перегляд у UI = цей самий виклик.

### Сутності, які не є «рядком довідника»

- **Звуки (етап 2):** копіюємо рядок і об'єкт у сховищі цілі за `soundObjectPath` цілі. Перевірка ліміту `MAX_SOUNDS_PER_CAMPAIGN` для цілі; понад ліміт: `skipped` з причиною. Збій копіювання об'єкта не лишає рядка без файлу (спочатку файл, потім рядок; при помилці рядка файл прибирається).
- **Карти (етап 3):** `BattleMap` із `header` та `chunks`, без історії версій (`BattleMapVersion`), `mapVersion` у копії = 1. Фонове зображення копіюється як окремий об'єкт у сховищі цілі.

### Egress та продуктивність

Копіювання об'єктів у межах сховища виконується серверною операцією `copy`, а не скачуванням і заливанням. Дельти замість повторних вибірок: сервіс не читає зайвого з джерела, лише вибрані рядки та їхні залежності.

## UI

- На сторінках бібліотек DM: вибір кількох елементів і дія «Копіювати в кампанії…» (біля «Імпорт/Експорт»; для одного елемента також у меню картки).
- Діалог з трьох кроків: (1) кампанії: список, де користувач DM, з пошуком, чекбокси й верхня галочка «Усі кампанії»; (2) попередній перегляд із `dryRun`: «буде скопійовано: 1 юніт, 2 заклинання; уже є в цілі й буде використано: раса Ельф»; (3) підсумок по кожній кампанії (створено / використано / пропущено з причиною, збій окремої кампанії видно окремо).
- Якщо в користувача лише одна кампанія (джерело), дію не показуємо.
- Тексти: `messages/{uk,en}/*.json`. Запис у `lib/onboarding/whats-new.ts` і ключі `whatsNew.<id>` в обох мовах, підказка за правилами онбордингу.

## Помилки та граничні випадки

- Ціль не підтримує вид за композицією правил: елемент `skipped` з причиною, решта копіюється.
- Назва залежності є в цілі, але це інший за змістом елемент: ми все одно використовуємо наявний (рішення власника «за назвою»), у звіті він у `reused`.
- Одна ціль впала посеред запису: транзакція цілі відкочується, інші цілі не зачеплені, статус `failed` з повідомленням.
- Копія в кампанію, де є активний бій: контент довідника не змінює стан бою; обмежень немає.
- Дві одночасні копіювання в одну ціль: захист існуючим content-write lock (`lib/server/content/write.ts`, перевірити на старті плану).

## Тести

- Юніт: `plan.ts` (транзитивні залежності, цикли, дублі за назвою, непідтримуваний вид), `resolve-targets.ts` (ролі, `all`).
- Інтеграційні (`pnpm test:integration`, локальна БД): юніт із заклинанням і расою в другу кампанію; повторне копіювання не створює дублів; чужа кампанія → 403; збій однієї цілі не торкається іншої.
- Етап 2: ліміт звуків, збій копіювання об'єкта. Етап 3: карта з чанками й фоном.
- UI: тест діалогу (галочка «Усі кампанії», попередній перегляд, підсумок).

## Поза обсягом

Копіювання decks, acquaintances, сценаріїв, світової карти; режим «перезаписати»; синхронізація копій з оригіналом; копіювання між акаунтами.

## Відкриті пункти для плану (перевірити в коді, не вирішувати зараз)

1. Чи годиться бандл-шлях `lib/server/templates/*` як ядро, чи потрібен `importContent`-шлях (див. таблицю).
2. Чи існує серверне `copy` об'єкта в обгортках Supabase Storage, чи додати.
3. Яких видів торкається `isKindActive` для всіх 13, і як це показати в UI до підтвердження.
