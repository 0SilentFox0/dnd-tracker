## 0. Знахідки планувальника (доповнюють розвідку)

1. **Ключ `dnd5e` лишається валідним без міграції.** Слот стану d20 має ключ модуля `'d20'` (`D20_STATE = defineSlot('d20', …)`, `systems/d20/rules/state.ts`), не ключ кампанії; `RULES_PRESETS` теж за id модуля (`d20`, `homm`). Тож: база `d20` отримує новий ключ **`d20`** (голий), а тека `systems/dnd5e` (`kind: 'preset'`, `keys: ['dnd5e']`, `preset: { base: 'd20', modules: [...] }`) забирає старий ключ. Збережені `rules.system.key = 'dnd5e'` (кампанії, `battle_scenes.rules`, `manifest.system` шаблонів SRD, профілі sweep) читаються як пресет — **переписувати ключі в даних не треба, alias не потрібен.** Бекфіл потрібен лише для **явних** `modules` (п. 2).
2. **Явні `modules` на проді майже напевно є.** `initialRules` пише `system: { key, modules }` явно для кожної нової кампанії (`lib/utils/rules/initial-rules.ts:41`), майстер Ч24 і `withModule` теж пишуть повний набір. Ч13 бачив 0 таких рядків, але кампанії після 2026-11-13 вже їх мають. Тому бекфіл явних `modules` закладено в план як очікуваний (звіт лише підтверджує).
3. **Нові модулі — в обидва пресети (`dnd5e` і `homm`).** Причина, крім поведінки: `mechanicKeysOf`/`rulesHashes` синку шаблонів беруть лише секції активної композиції (`lib/server/templates/sync/hash.ts`). Якщо `homm` не матиме `deathsaves`, секція `deathSaves` випаде з хешів синку HOMM-кампаній → розбіжність з базовою лінією. З модулями в обох пресетах набір активних секцій незмінний; поведінку все одно гейтять прапорці (рішення 1).
4. **Правило бекфілу одне:** для рядка з базою `d20` (`key ∈ {dnd5e, homm}`) і масивом `modules` (включно з `[]`) → `modules := sortedUnique(modules ∪ NEW)`, де `NEW` = id модулів, винесених у 25.1–25.2. Це точна еквівалентність поведінки (те саме, що мав рядок до розбиття).
5. **Вікно між деплоєм і бекфілом можна прибрати** двома деплоями: Deploy A1 реєструє id нових модулів як порожні оболонки (поведінка в базі, як зараз) → бекфіл → Deploy A2 переносить логіку в модулі. Старий код скидає невідомий id до набору пресета (`schema.ts:120-125`), а з A1 id вже відомі, тож і відкат A2→A1 безпечний.
6. **Наслідки нового ключа `d20`:** `RULE_SYSTEM_KEYS` (генерований порядок) може почати з `d20` → `FALLBACK_SYSTEM_KEY` (`catalog.ts:11`, читає `useBattleSetup`) стане голою базою; `SystemSection` покаже `d20` у списку; `metaOf('dnd5e')` поверне мета пресета (без `distance`/`i18n`/`dmSections` — як уже з `homm`, тож читачі мусять іти через `composition().base`); `systemServerUnion` ключується `base.keys[0]` = `d20` (споживачі беруть лише `Object.values`); `PREVIEW_SYSTEM_KEY` = `d20` (пісочниця, без смерті — допустимо). Потрібні `gameTerms.ruleSystem.d20`.
7. **Ефекти критів.** Єдиний `crit`-хук — у d20 (`crit: (rules) => rules.criticals`); фолбек `critRulesOf` (`lib/utils/battle/attack/crit-rules.ts`) = `SECTION_DEFAULTS.criticals` з `effects: true`. Пресет d20 уже ставить `effects: false`, тож «голий d20 без effects» = нейтральний фолбек для баз без хука (wfrp, d6pool). Змінюється лише фолбек; d20-хук і прапорець лишаються.
8. **Статблок: хеш контенту можна не змінювати.** `contentRowHash` (`lib/utils/content/row-hash.ts`) — єдина точка для синку (`sync/hash.ts`) і матеріалізації шарів (`content-layer.ts:864`). Канонічна проєкція (перед хешуванням підняти ключі статблока з `characteristics` у плоскі поля рядка) дає **той самий** `sourceHash`/базові лінії до й після переносу → нуль дифів sync. Таблиць три: `characters`, `units`, **`unit_bases`** (шар контенту, `UnitBase`, `schema.prisma:1401`).
9. **Snapshot бою не змінюється**, якщо будівник учасника (`from-character`, `fromUnit`) віддає ті самі `abilities.*` → `snapshotHash` стабільний; активні бої колонок не читають (стан у `battle_participants.snapshot/state`).

## Трек S — статблок у `characteristics` (iv-b)

**Обсяг (типово, питання 3):** 9 колонок — `strength…charisma`, `armorClass`, `initiative`, `speed` — у таблицях `characters`, `units`, `unit_bases`. Решта d20-колонок (`savingThrows`, `skills`, `proficiencies`, `spellSlots`, `spellcastingAbility`, `class*`, `level`, `proficiencyBonus`, `saveProficiencies`, `statblock`, `spellcasting`, `multiattack`, `legendary*`, `cr`, `xp`) лишаються колонками у власності d20 через `stats.columns` — вони не протікають у core.

**Форма:** `characteristics` d20-рядка = плоский об'єкт з тими самими іменами (`{ strength, …, speed }`). Перенос **лише сховища**: DTO/API (`types/characters.ts`, OpenAPI, AI-інструменти, пакети `units.json`) лишаються плоскими (питання 4) — мапінг на межі сервера.

**Механіка (як wfrp):** d20 переходить на `characteristics.persisted: true`; 9 колонок виходять з `D20_STAT_COLUMNS` (`owns`), core заповнює їх дефолтами через `statColumnFillOf` (наявний шлях wfrp).

### S.1 — Кодек і канонічний хеш (M)

**Файли:** `lib/utils/rules/systems/{types,meta}.ts` (нові поля), `systems/d20/rules/characteristics/{columns,codec}.ts`, `systems/d20/meta.ts`, `lib/utils/content/row-hash.ts`, тести.

**Сигнатури.**
```ts
// RuleSystemDefinition.characteristics
columnView?: {
    columns: readonly string[];                                   // 9 імен
    read(row: { characteristics: unknown } & Record<string, unknown>): Record<string, number>; // characteristics ?? legacy-колонки (dual-read до S.5)
    write(cols: Partial<Record<string, number>>, prev: unknown): SystemData;                 // зливає в prev.characteristics
};
// SystemMeta (дані, бо row-hash чистий і без композиції)
characteristicsColumns?: readonly string[];
```
- `contentRowHash('Unit' | 'Character', picked)`: перед поточною логікою — для `c ∈ ∪ meta.characteristicsColumns`: якщо `picked.characteristics?.[c] !== undefined` → `row[c] = characteristics[c]` і видалити з копії `characteristics`; далі наявна перевірка «порожні characteristics → видалити». Результат = хеш легасі-рядка (колонки зі значеннями, `characteristics: {}`).
- Контракт-тест: `D20_META.characteristicsColumns` = `columnView.columns`; жодна інша система не має ключа characteristics з цими іменами (wfrp — інші ключі).

**Тест-кейси:** (1) легасі-рядок юніта (колонки, `{}`) і перенесений (дефолтні колонки + `characteristics` з 9 ключами) → **однаковий** `contentRowHash`; (2) рядок пакета `units.json` (плоский) — хеш як був; (3) wfrp-юніт — хеш як був (`emptyCharacteristicsHashes` не зачеплено); (4) `columnView.read` легасі = перенесений; (5) хеш для всіх 331 юнітів `srd-5.2` + HOMM-пакета однаковий після «віртуального переносу» в тесті.

### S.2 — Сервер: читання/запис через кодек, dual-write (L; Deploy S-A)

**Файли (≈16 за розвідкою):** `lib/server/characters/{core,operations}/**`, `lib/server/battles/participant/from-character.ts`, `fromUnit`-будівник, `lib/server/content/resources/units.ts`, компендіум-адаптери, draft-маршрути, `lib/db/content-layer.ts` (форма `asLocalShape`), `scripts/templates/systems/d20` (`toPackRow/fromPackRow`).

**Рішення.**
- Core-сервіси не називають 9 колонок: читання — `withColumnView(row, system)` (накладає `columnView.read` на DTO), запис — `splitColumnView(data, system)` → `{ characteristics, columns }`. **Dual-write у S-A:** пишемо і `characteristics`, і колонки (колонки = страховка відкату й для старих читачів).
- `select` Prisma там, де беруться 9 колонок, додає `characteristics`.
- Будівник учасника бере значення через кодек → `snapshot.abilities` той самий.

**Задачі (Sonnet, 3):** S2-1 персонажі (core + operations + drafts + from-character); S2-2 юніти (resources, fromUnit, компендіум, content-layer/`unit_bases`, адаптери пакета); S2-3 скрипти й інструменти: `scripts/{seed,sim,srd,constructor,import}/**` (~21) через спільний `d20RowData()` або сервіси, `lib/ai/tools/party.ts`, raw SQL (`grep '\$queryRaw' | grep -i armor`), + ratchet-тест «скрипт пише стат-колонку без `characteristics`» = червоний.

**Тест-кейси:** golden `fromCharacter`/`fromUnit` для легасі і перенесеного рядка → однаковий `snapshot` і `snapshotHash`; D12 (`d12-columns.test.ts`) зелений; створення/патч персонажа пише обидва місця; wfrp-шлях не змінено; імпорт пакета D14 0/0/0; `stat-columns-contract`, `system-contract` (d20 `persisted: true` → покриття колонок через fill).

**Стоп «так»:** merge + Deploy S-A (звичайний; dual-read робить його безпечним для активних боїв — `--expect-idle` не обов'язковий, але звіт до/після запустити).

### S.3 — Бекфіл (M; дані)

`scripts/db/backfill-d20-characteristics.ts` (+ `lib/…-{plan,snapshot,db}.ts`, зразок Ч13):
- Відбір: `characters`/`units` кампаній з базою `d20` (`composition(rules.system).base === 'd20'`); `unit_bases` — рядки шарів, чий шаблон має d20-базу (через `manifest.system` шару); `characteristics` порожній або без усіх 9 ключів.
- Запис: `characteristics := { ...characteristics, ...pick(row, 9 колонок) }`; колонки не чіпати.
- **Гард хешу:** для кожного рядка `contentRowHash` до == після, інакше abort усієї транзакції (`--expect-same-hashes` типово увімкнено). Плюс `sourceHash` збережених рядків не переписується.
- Батчі по ~500 у транзакціях, оптимістичний замок (`updatedAt`/вміст), файл-знімок (`id`, старий `characteristics`), `--revert` повертає старі значення (колонки живі завдяки dual-write).
- Звіт `--report`: рядків, де колонки ≠ `characteristics` (гейт `--expect-zero` для S.5).

**Тест-кейси (без БД):** план на фікстурах (d20 / wfrp / вже перенесений / частковий), ідемпотентність, гард хешу ловить навмисну розбіжність.

### S.4 — Перемикання на `characteristics` (S; Deploy S-B)

Лише після бекфілу й `--report --expect-zero` на проді. `columnView.read` читає тільки `characteristics` (дефолти, якщо ключа нема); запис колонок припиняється (лишаються дефолтами з fill). `statblock-guard` розширити: читання 9 колонок у `lib/**`, `systems/**`, `scripts/**` поза кодеком = 0. Golden S.2 повторити.

**Стоп «так»:** Deploy S-B з `active-battles-report --expect-idle` (на випадок операцій посеред бою, що читають рядок персонажа: відпочинок, приєднання).

### S.5 — Rehearsal на prodcopy (входить у гейт кінця E4)

Повна репетиція runbook RS на `prodcopy_<suffix>`: бекфіл → гард хешів → `template sync --dry-run` по всіх кампаніях = 0 дифів → sweep 4 профілі = 0 дифів → `--revert` → знову 0 дифів.

### S.6 — Contract (не в E4 за замовчуванням)

`DROP COLUMN` 9 колонок × 3 таблиці — окрема міграція в окремому деплої, коли ≥1 деплой без читачів (grep код + `scripts/`), посилання на коміт S.4; перегенерувати `UnitBase` (`scripts/db/gen-base-models.ts`), прибрати колонки з `t.columns` бандла (канонічний хеш їх і так додає). Рекомендація: **не дропати в E4** (колонки мають дефолти, виграш малий, ризик — відкат схеми Vercel не повертає). Окремий стоп і «так».

**Opus-ревю треку S** — після S.4 (одне).

## 6. Runbook прод-кроків

**Загальне для кожного кроку:** бекап (`scripts/db/backup-database.sh`, `DIRECT_URL` 5432) → `active-battles-report --expect-idle` → dry-run → «так» власника → `--apply` → повторний звіт = очікуване → зберегти файл-знімок (`--snapshot-dir`) поза репо. Скрипти: `pnpm exec tsx --env-file=.env.production-db.local --tsconfig tsconfig.scripts.json scripts/db/<script>.ts … --allow-remote`.

**RA — модулі (після Deploy A1, до Deploy A2):**
1. `rule-modules-report.ts --json` → кількість рядків з явним `modules` у `campaigns`/`battle_scenes` (активні окремо).
2. Якщо 0 → пропуск до Deploy A2. Інакше: `backfill-rule-modules.ts` (dry-run) → перевірити план (лише доповнення `NEW`, жодних видалень) → «так» → `--apply`.
3. `rule-modules-report.ts` → усі явні набори містять `NEW`.
4. Deploy A2 (`--expect-idle` до/після); smoke: бій dnd5e — герой падає на 0, кидок смерті; HOMM-бій — без змін.
5. **Rollback:** код A2 → A1 (Vercel) безпечний (id відомі); дані — `--revert <snapshot>` лише якщо відкочуємось нижче A1.

**RS — статблок (після Deploy S-A):**
1. Репетиція на prodcopy (S.5) — обов'язково перед продом.
2. `backfill-d20-characteristics.ts` (dry-run): рядків по таблицях, гард хешів = 0 розбіжностей.
3. «так» → `--apply` (батчі, знімок) → `--report --expect-zero`.
4. `template sync --dry-run` на 2–3 кампаніях (SRD, HOMM) = 0 дифів.
5. Deploy S-B (`--expect-idle` до/після); smoke: лист героя, створення юніта, старт бою (snapshot ≠ змінився).
6. **Rollback:** S-B → S-A безпечний (dual-read, колонки живі); дані — `--revert` повертає старі `characteristics`. Після S.6 (DROP) відкат лише з бекапу — тому S.6 окремо й пізно.
