# Редактор мап — етап E: редактор тайлів

**Дата:** 2026-11-15 · **Гілка:** `feat/map-editor-c` · **База:** `main` `feb6088c4` уже є предком гілки · **Статус:** дизайн уточнено; реалізація триває, expand-only міграцію створено локально, не застосовано · **Епік:** [дизайн](2026-11-13-map-editor-design.md), етап E; [план епіку](../plans/2026-11-13-map-editor.md), етап E · **План етапу:** [stage E](../plans/2026-11-15-map-editor-stage-e.md)

## 1. Мета та межі

Дати ДМ редактор для малювання текстур по клітинках бібліотечної карти, щоб створити та зберегти мапу 100×100 і відкрити її в бою. Рендер текстур робиться Canvas 2D чанками поверх наявного фото-фону за потреби та під DOM-шарами токенів, стін, FX й інтерактивної сітки.

Входить: Spike 3 і пілот шести текстур; реєстр текстур і контроль ліцензій; приватне сховище тайлів; формат шарів/чанків і RLE; autotile та детермінований вибір варіанта; Canvas із видимими чанками й кешем; desktop UI редактора, інструменти малювання, undo/redo; збереження лише змінених чанків; перевірки та документація.

Не входить: зміни боєвої логіки стін/дверей, редагування тайлів під час активного бою, автогенерація зображень у застосунку, масова генерація всіх 138 промптів, туман, дах, нова таблиця для чанків, production-зміни чи застосування міграцій.

## 2. Підтверджені рішення власника

- Розширити наявну `battle_map_chunks` для тайлів.
- Перевикористати кампанійний прапорець `mapLibraryEnabled`.
- Брати CC0-текстури та власні згенеровані текстури; не додавати контент із неперевіреною ліцензією.
- Використати підготовлені промпти та передбачити пілот до масової генерації.
- Не починати реалізацію, доки власник не погодить дизайн і план.

**Виконавчі рішення для погодження:** малювання відбувається в редакторі бібліотеки `MapEditorScreen`, а не у формі inline-бою; вибір готової бібліотечної карти в setup лишається наявним шляхом. Tile `blocks` бере участь у похідному наборі blocked-клітинок для руху, як задумано в епіку; `blocksSight` лише зберігається для наступних етапів туману й не активує FOV у E. Кампанійні assets читаються гравцями через ту саму публічну URL-модель, що й фон бібліотечної карти; авторизація кампанії контролює metadata/read API та upload/delete, не сам URL.

## 3. Досліджений поточний стан і повторне використання

- База етапу D уже є в історії цієї гілки: `feb6088c4` — предок `HEAD`; перебазування не потрібне. `docs/STATUS.md` позначає live-run і battle-sweep як відкладені перевірки епіка.
- `BattleMapChunk` (`prisma/schema.prisma`) має `mapId`, `cx`, `cy`, `data String`, первинний ключ `(mapId,cx,cy)`. `data` — base64 від 256 байтів: два біти для кожного зі 512 ребер чанка 16×16 (`lib/utils/battle/map-storage/edge-chunks.ts`). Старі рядки не мають `tile_layers`; відсутність значення означає, що в рядку є лише legacy-ребра.
- `library-service.ts` замінює весь набір ребер при зміні карти через `deleteMany`/`createMany`; версіює повний payload. Тайли мають писати лише змінені записи чанків і не ламати історичне читання/rollback карти.
- Бібліотека карт і редактор уже використовують `battle_maps`, `battle_map_versions`, API `/maps`, ETag/версію, читання карти учасниками кампанії, DM-права запису та `requireMapLibrary` для сторінок. API навмисно не вимагає прапорець; його не слід неузгоджено додавати до загальних маршрутів карт.
- `mapLibraryEnabled` уже є в кампанії, налаштуваннях, клієнтському хуку й обмеженні карт до 200×200. Нової кампанійної колонки/прапорця не потрібно.
- Фон бібліотечної карти зберігається через `battle-maps` (`lib/supabase/battle-map-storage.ts`). Загальний `imageBucketStorage` підтримує обмеження бакета й підписані upload URL. `pnpm assets:attach` натомість призначений для іконок контенту й викликає імпорт Prisma, тому не підходить для tile catalog без окремого шляху.
- Існують `MapEditorScreen`, `useMapEditorDraft`, `useBattleMapEditor`, `useStrokePaint`, `useGridWindow` та Canvas/SVG шари карти. Повторно використати керування картою, CTM геометрію і вікно видимих чанків; не створювати паралельний контролер панорамування/масштабу.
- DOM-контракт FX лишається: `[data-fx-grid]`, `cellPoint` через CTM і всі наявні `data-fx-*` якорі. Canvas є візуальним шаром без клітинкових DOM-якорів.

## 4. Підходи до зберігання чанків

### A. Додати nullable `tile_layers JSONB` у наявну таблицю — обраний підхід

Зберегти PK `(mapId,cx,cy)` та `data String` без змін. Додати nullable `tile_layers JSONB`, де ключі — `ground`, `wallfill`, `objects`, `edge-art`, а значення — рядки `r1:` RLE. `NULL` однозначно означає старий edge-only рядок. Тайловий чанк співіснує з `data`: якщо ребер немає, у `data` записується валідний payload порожніх ребер, тому старий декодер і надалі може прочитати рядок без помилки. Зміна одного шару оновлює тільки відповідне поле JSONB у рядку координати; транзакційна версія карти запобігає перезапису конкурентних змін.

Міграція expand-only: лише `ADD COLUMN ... JSONB`, без backfill, заміни PK/FK, переписування рядків або зміни RLS. `NULL` зберігає точну сумісність історичних записів. Перед увімкненням запису тайлів має бути розгорнутий код, який читає й зберігає обидва поля: старі writers можуть замінити рядки й втратити `tile_layers`, тому tile writes вмикаються лише після завершення rollout сумісних writers/readers. Після появи tile data не можна відкочуватися до коду, що не зберігає `tile_layers`.

Переваги: безпечне additive-розширення таблиці й незмінний ключ; одне DB-читання координати містить усі його шари. Ціна: оновлення шару читає-модифікує-записує JSONB карти координати, отже потрібна транзакція з `expectedVersion`, а не незалежні рядки шарів.

### B. Окремий рядок на шар із новим складеним ключем

Відхилено: це вимагало б видалити/замінити чинний PK. Така операція не є expand-only за `.claude/rules/db-deploy.md`, навіть якщо перед нею додати колонку та backfill.

## 5. Дані та сумісність

- Старий рядок із `tile_layers = NULL` читається як реберний chunk; base64 `data` на 256 байтів не є тайловим RLE і ніколи не інтерпретується як масив tile ID. Новий рядок зберігає цей самий edge payload у `data`, а тайлові RLE-значення — тільки в обʼєкті `tile_layers`.
- Значення `tile_layers.<layer>` мають version-tagged формат `r1:<base64>`; payload — послідовність пар `(runLength, tileId)` у little-endian `Uint16`, рівно 256 клітинок після декодування. Codec задає межі run length і перевіряє некоректний розмір та version tag до підключення API.
- Порожні чанки не зберігаються; координати чанка не від'ємні, межі крайніх чанків обрізаються розміром карти. Невідомі версії, переповнення run, некоректна довжина й ID поза реєстром відхиляються з доменною помилкою.
- Кожен шар має логічний ключ `(mapId, layer, cx, cy)`, фізично — поле шару в рядку `(mapId,cx,cy)`. Обʼєкт з footprint, що перетинає чанки, зберігається як anchor ID в одному шарі `objects`; рендер перевіряє anchor чанки з відступом максимального footprint.
- Expand-міграція лише додає nullable `tile_layers JSONB`; вона не змінює старі рядки, PK, FK чи RLS. Старий writer може знищити JSONB при заміні рядка, тому ввімкнення tile writes залежить від повного rollout сумісного коду; downgrade після появи tile data заборонений, доки дані не експортовано/не перенесено окремим contract plan.
- Історія версій зберігає всі шари у тому самому versioned snapshot; rollback повертає чанк за шаром, а не затирає інші шари.

## 6. Реєстр, ліцензії й upload

- Каталог коду в `lib/constants/tilesets/` описує стабільний набір, тип шару, asset URL, footprint, autotile та flags `blocks`/`blocksSight`. `source` розрізняє `cc0`, `generated`, `campaign`; записуємо назву ліцензії/джерело й attribution, якщо CC0-пак цього вимагає.
- CC0-ресурси й власні глобальні текстури лежать у версіонованому `battle-tiles` bucket. Кампанійні файли — під префіксом кампанії, upload/delete доступні лише DM тієї кампанії, із сумарним обліком не більш як 50 MiB на кампанію. Як і наявний `battle-maps` bucket, asset URL публічно читається; він не є межею безпеки чи приватним сховищем, а права контролюють API метаданих/запису. Signed read URLs — окреме рішення, якщо знадобиться конфіденційність файлів. Не зберігати копії глобальних текстур у кожній кампанії.
- Валідація до upload: PNG/WebP; ground/wallfill 256×256; objects — 256 px на клітинку footprint (до 512×512 для 2×2), прозора альфа; edge-art 256×64 з альфою; кожен файл ≤200 KiB; сумарний кампанійний бюджет ≤50 MiB. Сервер перевіряє декодовані розміри/MIME, а не лише розширення.
- Пілот до каталогу: шість точних файлів із README промптів — `tiles_stone-floor_1`, `tiles_grass_1`, `tiles_wood-planks_1`, `tiles_wall-stone`, `tiles_barrel`, `tiles_door-wood-closed`. Перевірити шов через offset, читабельність 64 px, прозорість без пурпурової кайми, масштаб і цільовий розмір. Якщо 2 або більше з 6 мають шов чи кайму — скоригувати промпт або протестувати CC0 Kenney як базу до масової генерації.
- Spike 3 фіксує фактичний розмір/формат активів, завантаження шести файлів у локальне/тестове storage, Canvas повторення текстур, пам'ять чанків 200×200, частоту перемальовування й читабельність шести зразків. Жодного production storage або DB під час спайку.
- README говорить, що команди `assets:attach --kind tiles` ще немає. План додає окремий tile asset CLI/шлях завантаження, не викликаючи `importContent`; чинний generic icon attachment не розширювати так, щоб він записував тайли в контентні таблиці.

## 7. Рендер, autotile та редактор

- Чанк 16×16; Canvas 2D із device-pixel-ratio-aware backing store, кешем растрового чанка та invalidation лише змінених чанків. Малюються лише чанки у `GridWindow` плюс відступ для footprint; приховані/порожні шари не створюють canvas-поверхонь. OffscreenCanvas — оптимізація за підтримки, є fallback на звичайний Canvas.
- Ground: детермінована варіація за координатою та seed карти. Спершу autotile edge mask із 16 станами; формат каталогу дозволяє майбутній blob-47 без зміни чанка. Spike 3 має перевірити межі змішування сусідніх матеріалів (маска + noise); якщо якість/вартість неприйнятна, v1 залишає чіткі межі й фіксує це як відкладене рішення.
- Wallfill малюється вздовж наявних стін із квадратними кінцями, стики утворюються накладанням сегментів; він не змінює collision. Edge-art лише декорує ребро, а прохідність дверей/ґрат і надалі визначає наявна логіка етапу B.
- Порядок: фото-фон → ground → wallfill/edge-art → objects → наявні SVG grid/terrain/zones → DOM стіни/двері, учасники та FX згідно з їхнім поточним порядком шарів. Порядок перевірити під D-змінами; не переносити FX як Canvas bitmap.
- Редактор v1 — desktop у наявному `MapEditorScreen` бібліотеки карт: вибір набору/палітри, ground/wallfill/objects/edge-art, пензель 1–3, прямокутник, лінія, заливка, гумка, піпетка, перемикач шару, undo/redo. У setup форми бою можна вибрати вже готову бібліотечну карту, не редагувати inline tiles. На touch — пояснення, що редагування потребує desktop; мобільний перегляд карти лишається.
- Одна транзакція undo — один pointer stroke або один завершений геометричний/заливний інструмент; історія зберігає попередні/наступні дельти клітинок/чанків, обрізається лімітом пам'яті. Undo/redo й збереження відображають лише зміни після останньої підтвердженої версії.
- UI й API запису доступні DM лише коли прапорець `mapLibraryEnabled` увімкнений. Читання для рендеру доступне користувачам із доступом до кампанії, як карта; asset URL мають публічну модель `battle-maps`. Старі карти без tiles продовжують рендерити як раніше; фото-карта й тайли можуть співіснувати.

## 8. Збереження та правила

- Setup/бібліотечний редактор зберігає чанк-патчі за `(layer,cx,cy)` усередині JSONB `tile_layers` рядка `(mapId,cx,cy)` у межах версії карти; кожен запит має `expectedVersion`, транзакційно перевіряє версію та оновлює тільки передані ключі. Конфлікт використовує наявний 409 `BATTLE_MAP_CONFLICT`/перезавантаження карти.
- Політика чанків: ті самі campaign ownership і DM write права, що й `battle_maps`; RLS зберігається та розширюється тільки якщо перевірка схеми доведе, що новий доступ потребує політики. Публічні тайли не повинні відкривати campaign-private assets.
- Бій тайли тільки читає; геометрія бою лишається сумісною. Бойові дельти не пересилають full tile payload; карти завантажуються версійовано й кешуються окремо від `battle_scenes.map`.
- Блокування й прозорість — метадані типу тайла, з яких похідні клітинкові набори кешуються за версією тайлів. `blocks` у E додається до blocked-клітинок карти й обмежує рух наявним шляхом; `blocksSight` зберігається в реєстрі, але не змінює видимість до Fog G.
- Розмір активів впливає на Storage egress: cache-control для глобальних asset URL, не дублювати незмінні активи, завантажувати тільки видимі texture assets/чанки та не кодувати binary assets у JSON/API payload.

## 9. Збережені контракти та перевірки

- Не змінювати DOM-контракт `data-fx-*`, особливо `[data-fx-grid]`; `cellPoint` продовжує застосовувати CTM і працює крізь Canvas-шар.
- Зберегти межі шарів проєкту: чисті формат/автотайл у `lib/utils/battle/tiles`, серверне сховище в `lib/server/battle-maps`/`lib/supabase`, API тонкий, стан UI — у hooks, UI — `components`.
- Unit-тести формату покривають старі edge payload, round-trip кожного шару, край карти, некоректний/невідомий payload, максимальні ID та RLE worst case. Інтеграційні тести — права кампанії, прапорець, ETag/version conflict, частковий patch, rollback і RLS міграційний guard.
- Canvas-тести перевіряють тільки видимі чанки, відсутність малювання поза viewport, стабільність autotile/variant, invalidation одного чанка, відсутність Canvas DOM-якорів для FX.
- Live-run у браузері й battle-sweep залишаються відкладеними перевірками `docs/STATUS.md` за інструкцією власника; не запускати в межах підготовки.
