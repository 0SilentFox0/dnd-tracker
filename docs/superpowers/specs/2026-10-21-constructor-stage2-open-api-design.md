# Конструктор кампаній — етап 2: відкрите API (дизайн)

## Context

Етап 2 дорожньої карти з `2026-10-20-campaign-constructor-design.md`. Мета — контент кампанії (раси, юніти, заклинання, школи магії, основні скіли, скіли, дерева скілів, артефакти, сети, музика) і правила кампанії можна створювати й змінювати не лише з UI, а й через відкрите API. Головний споживач — AI-агент: зовнішній MCP-клієнт (Claude Desktop, Cursor), а також скрипти, що працюють через REST. Зміни діють лише в кампанії, якій належить токен.

Критерій успіху:
- агент через MCP може «створити расу з двома здібностями, юніта цієї раси і заклинання для нього», і результат видно в UI;
- ті самі операції описані в OpenAPI;
- REST, MCP і UI проходять через одні й ті самі Zod-схеми й перевірки.

Що вже є (AI-асистент, злитий у `main` і в `feat/constructor`, 1b56568c):
- таблиця `api_tokens` (`scopes String[]`, зберігається SHA-256 хеш, `revokedAt`, `lastUsedAt`);
- `lib/ai/api-tokens.ts`: `verifyApiToken` перевіряє, що власник досі ДМ;
- роути `app/api/campaigns/[id]/api-tokens`;
- `/api/mcp` на `mcp-handler`, stateless і без CSRF-перевірки;
- реєстр інструментів `AI_TOOLS` з адаптерами для чату й MCP;
- сторінка `/dm/ai`.

Етап 2 **розширює** цю інфраструктуру і не створює нову.

Розвідка CRUD-роутів (2026-10-21):
- перевірка доступу до запису за id різна в різних доменах;
- відповіді `DELETE` мають п'ять різних форм; через це клієнт `deleteAllSkills` чекає поле `deleted`, а роут повертає `deletedCount`;
- частина помилок віддається напряму через `NextResponse.json`, без `errorResponse`;
- артефакти, сети, треки й дерева не скидають кеш-тегів;
- `loadOwned` використовують не всі роути;
- схеми скілів лежать поруч із роутами;
- `z.toJSONSchema` (Zod 4.3) серіалізує всі наявні схеми, але схема здібностей займає 55 КБ: ефект `randomOf` вбудовує вкладені ефекти повністю.

## Рішення з брейншторму

- Етап будується на `api_tokens` і `/api/mcp` AI-асистента.
- Агент пише контент **напряму**, без пропозицій. Захист — валідація схемами і права токена.
- Права обираються під час створення токена: `ai`, `content:read`, `content:write`.
- Обсяг: увесь контент бібліотек і правила кампанії. Музика — лише YouTube-треки і зміна порядку. Бої, персонажі й сценарій не входять.
- Архітектура — **реєстр ресурсів**: один опис на кожен вид контенту, з нього будуються REST, OpenAPI і MCP.
- Запис за id для рас, основних скілів і артефактів, як і зараз, читає лише ДМ.
- Токени з `content:*` можна створювати й на шаблонах.

## Дизайн

### 2a. Фабрика: реєстр, сервіс, роути

`lib/server/content/` (`server-only`):

- **`define-resource.ts`** описує тип `ContentResource<Row, Create, Update>`:
  - `kind`, `label` (укр.), `description` (для OpenAPI та MCP);
  - `schemas: { create, update }` — з `lib/schemas`; схеми скілів переносяться з роутів у `lib/schemas/skills.ts`;
  - `db(tx)` — делегат Prisma;
  - `access: { list: "member" | "dm", item: "member" | "dm" }` — зберігає поточну поведінку кожного домену;
  - `invalidates: ReferenceKind[]`;
  - `toResponse(row)`.

  Необов'язкові хуки:
  - `list(ctx, query)` — для кешованих читачів (`readRaces`, `readSpells`, `readSkills`, `readArtifacts`, `readArtifactSets`, `getCachedUnits`, `getCachedMainSkills`) і параметрів `spells?ids=`, `skills?mainSkillId=`. Серверні сторінки ДМ і далі заздалегідь завантажують дані цими ж функціями;
  - `beforeCreate` / `beforeUpdate(ctx, input, existing?)` — перевірка посилань (`invalidCampaignRefs`, раса юніта), іконки артефактів, legacy-колонки заклинань; повертають дані для запису;
  - `update(ctx, id, data)` — заміняє стандартне оновлення; для каскадного перейменування раси (`updateRaceCascade`);
  - `afterWrite(ctx, row)` — синхронізація членів сету;
  - `remove(ctx, id)` — для сету: відв'язати артефакти й видалити в одній транзакції.
- **`service.ts`** — `contentService(resource)` надає `list`, `get`, `create`, `update`, `remove`, `removeAll`, кожен приймає `ctx = { campaignId, userId, isDM, via }`.
  - Пошук завжди за `{ id, campaignId }`; запис іншої кампанії = 404.
  - Після запису — `invalidateReference(resource.invalidates, campaignId)`.
- **`errors.ts`** — `ContentError(message, status, issues?)`; роут перетворює її на `errorResponse`. Сюди переходять усі «сирі» відповіді: конфлікт назви раси, недійсна раса юніта, 422 іконок, `toArtifactSetErrorResponse`, `{errors}` дерев. Тексти — у `lib/constants/api-errors.ts`.
- **`resources/*.ts`** — `races`, `units`, `spells`, `spell-groups`, `main-skills`, `skills`, `artifacts`, `artifact-sets`, `tracks`.
  - Для `tracks` через API доступне лише створення YouTube-треку; завантаження файлу лишається в UI.
  - `index.ts` збирає `CONTENT_RESOURCES` (`satisfies Record<ContentKind, ContentResource>`).
- **Нестандартні операції** — окремі сервіси в тій самій теці; у реєстрі `CONTENT_OPERATIONS` у кожної є опис для OpenAPI і MCP:
  - дерево скілів (`saveSkillTree` з міграцією прогресу й оптимістичним повтором);
  - правила (`GET`/`PATCH rules`);
  - дублювання скіла;
  - порядок треків;
  - імпорт юнітів;
  - видалення заклинань за рівнем;
  - прибирання заклинання з групи;
  - експорт бандла.

`lib/utils/api/content-routes.ts`:
- `collectionRoutes(resource)` → `{ GET, POST, DELETE }`, де `DELETE` без id = видалити все;
- `itemRoutes(resource)` → `{ GET, PATCH, DELETE }`;
- обидві розбирають параметри, викликають `resolveActor` (2b), `parseBody` і сервіс, а помилки віддають через `ContentError` / `handleApiError`;
- `route.ts` — один рядок: `export const { GET, PATCH, DELETE } = itemRoutes(units)`.

Підроути `spells/delete-all` і `units/delete-all` стають псевдонімами `DELETE` колекції. Решта підроутів — тонкі обгортки над сервісами нестандартних операцій.

Уніфікація відповідей (клієнти `lib/api/*` оновлюються в тому ж коміті):
- `POST` → 201 із записом;
- `PATCH` → запис;
- `DELETE` одного запису → `{ ok: true }`;
- видалення всіх → `{ ok: true, deleted: n }` (закриває баг з `deletedCount`).

Зміни поведінки (свідомі, з тестами):
- запис іншої кампанії тепер 404 замість 403;
- `PATCH` юніта записує `morale`, яке схема вже приймає;
- `GET` дерев скілів переходить на стандартну перевірку доступу учасника.

### 2b. Токени й автентифікація

- **Scopes** (`API_TOKEN_SCOPES` у `lib/constants/ai.ts`): `ai`, `content:read`, `content:write`. `content:write` включає `content:read`. Наявні токени мають `["ai"]` і нових прав не отримують. Міграція не потрібна.
- **Створення токена.**
  - `createApiTokenSchema` отримує `scopes` (мінімум одне право).
  - На `/dm/ai` у діалозі створення — три галочки; у списку — чипи прав.
  - Змінити права наявного токена не можна: відкликати й створити новий.
- **`verifyApiToken`** повертає `{ campaignId, userId, scopes }`.
- **`resolveActor(req, campaignId, need: { access: "member" | "dm", scope?: "content:read" | "content:write", sessionOnly?: true })`** у `lib/utils/api/actor.ts` — єдина точка автентифікації для роутів фабрики, нестандартних операцій контенту, `rules` і `export`.
  - **Є `Authorization: Bearer …`.**
    - Токен перевіряє `verifyApiToken`.
    - Недійсний або відкликаний токен → 401; відкату до cookie **немає**.
    - `campaignId` токена має збігатися з `campaignId` у шляху, а потрібний scope має бути в токені. Інакше 403.
    - Через токен діє як ДМ: `isDM = true`.
  - **Заголовка немає** — як зараз: `requireCampaignAccess` / `requireDM`.
  - **`sessionOnly`** (масове видалення) — токен отримує 403. «Видалити всі» доступне лише з UI.
  - Повертає `ctx = { campaignId, userId, isDM, via: "session" | "token" }`.
- **Інші роути** (бої, персонажі, сценарій, показ, AI-чат) Bearer не читають, лише cookie: запит лише з токеном отримає 401.
- **CSRF** (`lib/supabase/middleware.ts`): запит із заголовком `Authorization: Bearer` пропускається незалежно від `Origin`.
  - Це безпечно, бо `resolveActor` за наявності заголовка cookie не читає.
  - Чужа сторінка не може надіслати `Authorization` з браузера без CORS-дозволу, а CORS-заголовків ми не віддаємо.
- **Шаблони.** На `/dm/ai` шаблону показується лише секція токенів: без AI-ключів, інструкцій і чату; пункт меню — «API».
- **Ліміти запитів** — поза етапом (етап підписки).

### 2c. OpenAPI

- **`lib/server/content/openapi.ts`** — `buildOpenApi()` будує документ OpenAPI 3.1 з `CONTENT_RESOURCES` і `CONTENT_OPERATIONS`.
- **Тіла запитів:** `z.toJSONSchema(schema, { io: "input", unrepresentable: "any" })`.
  - Спільні підсхеми мають `.meta({ id })`: здібність, тригер, ефект, умова, `SpellFx`, `WeaponStats`, `Ruleset`. Вони потрапляють у `components/schemas` через `$ref`, у тому числі рекурсивний `randomOf`, тож схема здібностей не дублюється в кожному шляху.
  - Ключові поля отримують `.describe()` українською: здібності, `fx`, бонуси артефактів, `knownSpells`, `attacks`, елементи дерева.
- **Відповіді.**
  - Помилки описані точно: `{ error, issues? }`, коди 400/401/403/404/409/422.
  - Успіх — об'єкт з обов'язковими `id` і `name` та `additionalProperties`. Повні схеми відповідей — поза етапом.
- **Безпека.**
  - У документі є `securitySchemes.bearerAuth`.
  - Кожна операція має потрібний scope в описі й у `x-scopes`.
  - Операції лише для сесії (масове видалення) в документ не входять.
- **`GET /api/openapi.json`**:
  - публічний: документ однаковий для всіх і не містить секретів;
  - віддається з `Cache-Control: public, max-age=3600`;
  - будується ліниво, один раз на інстанс.
- **UI:** на `/dm/ai` у секції токенів — посилання на `openapi.json` і приклад `curl` з `Authorization`. Swagger/Scalar UI не додаємо.

### 2d. MCP-інструменти контенту

- **`AiToolDef` отримує `scopes: ApiTokenScope[]`.** Наявні інструменти мають `["ai"]`.
  - `registerMcpTools` реєструє лише ті інструменти, чиї scopes є в токені.
  - Чат усередині застосунку працює з `["ai"]` і нових інструментів не бачить; вбудований AI з правом запису — етап 6.
- **`lib/ai/tools/content.ts`** — загальні інструменти з параметром `kind` (а не 50 інструментів «вид × операція»):

  | Інструмент | Scope | Що робить |
  |---|---|---|
  | `content_kinds` | read | види контенту з описом і переліком операцій |
  | `content_schema(kind, op, effectKind?)` | read | JSON Schema вводу з генератора 2c. Для `kind: "abilities"` — схема здібності; з `effectKind` — схема одного виду ефекту, щоб результат вмістився в ліміт |
  | `content_list(kind, query?, limit?, offset?)` | read | `id`, `name` і ключові поля, до 50 записів, з `total` |
  | `content_get(kind, id)` | read | повний запис |
  | `content_create(kind, data)` | write | валідується схемою ресурсу в сервісі |
  | `content_update(kind, id, patch)` | write | |
  | `content_delete(kind, id)` | write | один запис |
  | `get_rules` / `update_rules(patch)` | read / write | |
  | `get_skill_tree(race)` / `save_skill_tree(race, tree)` | read / write | |

  - Помилки Zod повертаються агентові текстом зі шляхами полів (`AiToolError`), щоб він міг виправити запит.
  - Масового видалення й експорту бандла в MCP немає: бандл HOMM5 не вміщається в ліміт результату (24 000 символів). Бекап — через REST `GET /export` з `content:read`.
- Наявні `search_reference` / `read_reference` (scope `ai`) лишаються без змін.

  - `battle-sweep` на `constructor`.
- **2b.** Тести `resolveActor`:
  - немає scope → 403;
  - токен іншої кампанії → 403;
  - відкликаний токен → 401;
  - недійсний Bearer за наявності cookie → 401;
  - `sessionOnly` з токеном → 403;
  - Bearer на роут бою → 401.

  CSRF: Bearer з чужим `Origin` проходить, cookie-запит з чужим `Origin` → 403.
- **2c.**
  - Документ будується без помилок.
  - Кожен ресурс і кожна операція мають шляхи.
  - Шляхи документа відповідають наявним `route.ts`: тест обходить `app/api/campaigns/[id]`.
  - Схема здібностей іде через `$ref`, а не вбудовується.
- **2d.**
  - Інтеграційний тест MCP за зразком `app/api/__tests__/api-tokens-mcp.test.ts`: набір інструментів залежить від scopes; `create → get → update → delete`; помилка Zod доходить до агента текстом.
  - Кожен результат `content_schema` і `content_list` (на 150 юнітах) вміщається в `AI_LIMITS.toolResultChars`.
  - Живий прогін на `constructor`: створити токен → `curl` до `/api/mcp` → створити расу і юніта → вони видні в UI → видалити.
- **Наприкінці:** `pnpm test:run`, `pnpm lint` (0 errors), `pnpm build`.

## Обмеження й правила

- **Ізоляція.** Будь-який шлях запису (REST, MCP) отримує `campaignId` тільки з `ctx` і шукає записи за `{ id, campaignId }`. Посилання в тілі (раса, група, сет, скіли, заклинання) перевіряються на належність кампанії: `invalidCampaignRefs`.
- **Одне джерело правди.** Схеми з `lib/schemas` використовують і UI-форми, і REST, і MCP, і OpenAPI. Окремих «API-схем» немає.
- **Без міграцій.** `scopes` уже є. Якщо реалізація все ж потребуватиме змін схеми, вони мають лише розширювати її (expand-only).
- **Кеш.** Кожен запис через сервіс скидає теги свого виду, у тому числі ті, що досі пропускалися.
- **Злиття.** У `main` і на prod нічого не потрапляє до завершення всього епіку (етапи 1–6).

## Ризики

- **Регрес UI через уніфікацію відповідей.** Пом'якшення: клієнти `lib/api` і хуки оновлюються в тому ж коміті, що й роут; наявні тести роутів; браузерна перевірка кожної бібліотеки.
- **Особливі випадки не вміщаються в хуки.** Пом'якшення: хук `update`/`remove` повністю заміняє стандартну операцію; нестандартні операції — окремі сервіси, а не прапорці фабрики.
- **Агент шле некоректні здібності.** Пом'якшення: та сама `AbilitiesSchema`, що й у редакторі, плюс `readAbilities`-перевірки; помилка повертається агентові зі шляхами полів.
- **Витік токена з правом запису.** Пом'якшення: токен прив'язаний до однієї кампанії; масове видалення лише з сесії; відкликання на `/dm/ai`; `lastUsedAt` видно в списку.
