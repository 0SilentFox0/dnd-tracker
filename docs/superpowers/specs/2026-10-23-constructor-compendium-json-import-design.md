## 1. Мета й погоджені межі

Користувач створює порожню кастомну кампанію, вибирає свій JSON, бачить preview і одним підтвердженням наповнює всі доступні частини кампанії. Не треба по черзі імпортувати кожну бібліотеку або налаштовувати колонки. Після завершення видно, з чим уже можна грати та що конкретно треба доробити.

Це **додатковий JSON-потік поруч із CSV/TSV і простим табличним JSON**, а не заміна CSV. Імпортер універсальний: жодних перевірок назв Obojima, спеціальних конвертерів її навичок, інгредієнтів чи механік. Локальна книжка — лише read-only зразок форми. Імпорт заповнює наявні ресурси; новий рушій правил, stage6 AI та відтворення всіх механік 5etools не входять у роботу.

Уточнення користувача в цьому обговоренні: наповнювати всі аспекти **по можливості**, для решти повідомляти наступні дії. Відсутня механіка не означає пропустити весь запис: зберігаємо читабельний опис там, де це можливо, чітко відрізняючи його від автоматизації.

Користувач дозволив перейти до наступної задачі після аудиту backgrounds. Це дозвіл на Task18, не доказ проходження pending single-connection PUT/PATCH live-перевірки backgrounds і не оголошення того блоку закритим. Backgrounds використовуються за чинним контрактом ресурсу; старе застереження залишається в його ledger.

## 4. Підхід і повторне використання

Рекомендація автора: окремий агрегований адаптер, спільні доменні валідатори/guards і транзакційний writer. Альтернативи: зберегти JSON вкладенням (не наповнює кампанію); пропустити через CSV імпорт (втрачає категорії, source-aware refs і атомарність); повністю емулювати 5etools (не відповідає межам задачі). Рекомендація ще не погоджена користувачем.

Чинний `FileStep` уже приймає CSV/TSV/JSON. `parseJsonTable` у `lib/utils/content/import/table.ts` трактує object як один рядок; це залишається для простого JSON. Додати dispatch перед табличним parsing: aggregate з відомими root-масивами → compendium; масив звичайних рядків/object без aggregate markers → чинний табличний потік; bundle зі своїм форматом → пояснення про існуючий bundle importer. Не перетворювати compendium на одну таблицю. Розширення файлу не є доказом формату.

Інтеграція: `components/content-import/ContentTransferButtons.tsx`, `ContentImportWizard.tsx`, `steps/FileStep.tsx`, `lib/hooks/content-import/`; окремий campaign-level entry «Імпортувати JSON» доступний і в порожній кампанії, без відкриття конкретної бібліотеки. Категорії, які викликали wizard, не обмежують весь файл. Типове обрання — всі підтримувані категорії, опції можна зняти в preview.

Використати `lib/schemas/{spells,units,artifacts,races,classes,feats,backgrounds,scenario}.ts`, Choice/Picks і наявні rules schemas. `scripts/srd/convert/*` — приклад domain mapping, але їхні Open5e типи, pinned overrides та книжкові regex не є універсальним runtime adapter. Немає AI-мапування або прихованого звернення до AI.

Важлива технічна межа: ресурси `ContentResource` зараз пишуть через глобальний prisma, а CSV writer послідовний і вирішує refs переважно за назвою. Не викликати ці create/update ззовні `$transaction`, вважаючи операцію атомарною. Task19 має виділити спільні write/guard функції з параметром tx, які використовують і ресурси, і importer. Зберегти campaign refs, background ASI409, feat guards, name uniqueness, класові валідатори, cache invalidation після commit.

## 5. Покриття першої версії та mapping

Позначення результату: **native** — структуровані поля, **partial** — структуровані поля + опис/ручні механіки, **skipped** — жодного domain row, із причиною. Немає статусу «повністю підтримано» для текстового fallback. Unsupported field не можна мовчки загубити через Zod strip.

| Вхід | Ціль і структуроване перенесення | Текст / обмеження |
|---|---|---|
| spell | Spell/spellsResource: name, level, school→spell-group, class lists, концентрація, casting time→cost/casting; лише однозначні range/targeting і save/attack варіанти | entries + higher-level + components/duration; damageInflict не задає damage dice, conditionInflict не задає тригер. Не виводити повну механіку з тегів. Складні цілі, upcast, ritual та effect rules → partial/manual. Якщо немає однозначного targeting, зберігати тільки описовий запис з явним статусом ручного застосування, див. нижче |
| monster | Unit/unitsResource:6 характеристик, числові AC/HP average/walk speed, CR/XP, size/type, movement/senses/languages там, де є точна відповідність | actions/traits/reactions/legendary/spellcasting не стають автоматично довільними Ability. Простий attack переноситься лише за повністю розпізнаним шаблоном, інше — source notes. Умовні імунітети не перетворювати на безумовні; hp.special/умовний AC без числової бази → row error з дією «вказати HP/AC» |
| baseitem/item | Artifact/artifactsResource: name, description, явні rarity/slot, weapon/armor через чинні схеми; item.unique=false для звичайної бази, attunement лише якщо явно задано | custom type/property → опис і warning, не нова бойова механіка. Вартість/вага, light, спеціальні proficiency та speed rules зберігаються в notes. attachedSpells — refs, а не доказ cost/DC/uses; заряди не вигадувати. Складні reqAttune/charges/recharge — partial. | background | Background/backgroundsResource: skillProficiencies, toolProficiencies, choices, originFeatId, equipmentText | Детальний контракт §6; біографію героя не змінювати |

Невідомий caster тип — blocker до вибору користувача, не none |
| subclass/subclassFeature | GameClass.subclasses[]; stable nested id; refs з'єднують features/level; parent class зі source-aware lookup | Не перезаписувати інші subclasses. Невідповідність edition/рівня отримання subclass показати до застосування, не пересувати features. Нема parent — §8 |

Для custom skill — опис і next action «вести вручну», без вигаданої автоматизації |

**Описові механіки й безпека застосування.** Для spell та інших записів, які лише partial і не мають визначеної бойової дії, не підставляти schema defaults як «правильну» атаку/ціль. Запропоноване мінімальне розширення — metadata `automation: native | partial | manual`, плюс `manualPaths`. Для manual spells серверний cast повертає зрозумілу помилку «Налаштуйте механіку або застосуйте вручну», UI пропонує відкрити опис/редактор; resource PATCH із явним підтвердженням коректних полів знімає manual gate. Для partial records gate діє тільки на неперенесену дію, точно перенесені атаки можна використовувати. Не створювати фальшиві Ability, що витрачають дію й нічого не виконують. Це частина імпорту й редактора, не новий ефектний рушій. У Task19/20 потрібні відповідні guard/UI тести.

Чинний AbilitySchema вимагає trigger і хоча б один effect; тому описові class features не можна кодувати fake Ability. Розширити featureSchema/domain reader опційним `description` (max8000), зберігати поряд з level/abilities/choices, показувати в редакторі та листі класу/підкласу; legacy records без description незмінні. Опис ChoiceOption вже підтримується. Описові дії монстра живуть у source notes з доступом з бібліотеки та бойового statblock, не в масиві автоматичних Ability.

Уточнення після builder check: gate spell має бути **доменним**, не лише CompendiumEntry metadata. Додати `Spell.executionMode: native | manual` з default native для всього legacy контенту, провести через create/PATCH/export/bundle/source-sync, reader, battle snapshot та всі cast/grant/item/monster cast paths. Manual row використовує явно задокументовані інертні storage placeholders `cost=action,targeting={kind:self},resolution={kind:auto},dice=0,spellEffects=[]`; це не перенесені механіки й вони не показуються як визначені правила. Gate перевіряється перед витратами ресурсів/дії; manual spell відкриває лише опис. Зняття gate — лише explicit DM edit з повним schema-valid набором механіки та executionMode=native, не звичайний rename або reimport. Оновлення definition не переписує старі snapshots. Немає null targeting або другої spell table. Прибір meta provenance ніколи сам по собі не знімає цей gate.

Для непідтриманих feat prerequisites додати `prerequisite.manualText: string[]` до чинного prerequisite JSON/schema, показувати при виборі й у листі. Чинні структуровані умови перевіряються як раніше; manualText автоматично не перевіряється і не приховується за `{}`. Політика v1 — ручний контроль ДМ з видимим попередженням, вибір не блокується лише через manualText; report має next action «ДМ: перевірте ці вимоги». Неперенесені class requirements аналогічно зберігаються як видимі source notes. Немає удаваної гарантії перевірених вимог і додаткової системи approval receipts у персонажа.

**Не підтримуються як активні механіки:** foundry* масиви/поля, macro/script/Foundry effects/advancement, magicvariant.inherits, custom fonts, довільні фільтри, homebrew DSL, кастомні типи ресурсів/скіли без domain відповідника. Вони мають warnings/next actions; не виконуються й не завантажуються. `*Fluff` та inline fluff не імпортуються автоматично: ілюстрації й великі flavor payload пропускаються; користувач бачить це в preview. Текст основних entries зберігається. Інші невідомі root keys — inventory зі статусом skipped, без сирих значень у report.

## 6. Backgrounds: єдиний чинний контракт

Використати `types/backgrounds.ts`, `lib/schemas/backgrounds.ts`, `lib/server/content/resources/backgrounds.ts`. Немає другого background subsystem.

- Сталі відомі стандартні skills → skillProficiencies. Скінченний skill choose/any → Choice(kind=skill), якщо схеми дозволяють exact count. Custom skill ref → читабельний опис і `MANUAL_CUSTOM_SKILL`; не видаляти інші стандартні навички цього запису.
- Явні сталі назви інструментів → toolProficiencies. `anyArtisansTool`, комбіновані tool/language alternatives та мови → опис/next action: чинний Choice не підтримує tool/language kind. Не записувати назву групи як уже вибраний інструмент.
- ASI переносити лише з явного `ability`. Правило3 points/maxPerAbility2/cap20 — тільки для точно відповідної source структури; фіксовані бонуси й інші варіанти потребують точного представлення чинним контрактом або ручного попередження. Classic без ability лишається без ASI. Жодних вигаданих+3.
- `feats` із єдиним конкретним ref → originFeatId лише після розв'язання feat і перевірки type=origin. Choice з кількох origin feats не можна стиснути в одне originFeatId: залишити як manual requirement до явного вибору в preview. Unresolved/non-origin → блокувати цей background до виправлення refs або явного виключення запису, не встановлювати null без пояснення.
- startingEquipment, alternative money й інвентарні refs → equipmentText з позначенням альтернатив. Гроші й речі видає ДМ вручну. Character.background лишається біографією; імпорт не вибирає background для старих героїв і не змінює picks.
- feats→backgrounds; вкладені spell refs через спільний remap. Оновлення використаного background проходить чинний ASI409 guard; зміна origin type/deletion не обходить featInUse.

## 7. Entries, refs та edition

Детермінований visitor entries: text/entries/section/list/table/inset/quote → plain text або дозволені RichNode. b/i → formatting; font/style/color не виконувати. dice/damage/hit/dc/recharge залишаються читабельними позначеннями, не повною бойовою програмою. Невідомий tag зберігає безпечний display text із warning. Невідомий entry type не зникає мовчки: warning path, а його розпізнаний текст зберігається. Ніякого raw HTML, JS/eval, template execution, довільних attrs або завантаження URL. Посилання лише http(s) з escaping та rel; images/fonts/tokenHref/foundryImg не fetch і не render remote.

Refs поділити на **жорсткі** (originFeatId, parent race/class, mechanical spell grant) і **описові** (inline tag, таблиця/розділ). Нерозв'язаний жорсткий ref блокує залежний запис; описовий зберігає display text і next action. Файл може містити refs на інші sources, не лише на власний. Dependency graph вирішується до записів, незалежно від порядку масивів. Цикли механічних refs — error, цикли суто текстових links — warning, без рекурсивного inline expansion.

Identity ref містить kind/name/source, для class/subclassFeature також className/classSource/subclassShortName/subclassSource/level. UID/tag parsing за форматом конкретного типу; source за замовчуванням не можна заміняти першим `_meta.sources`. Якщо schema-defined default source не підтриманий adapter registry, source має бути явним або заданим через однозначний preview binding. Named source aliases не об'єднувати автоматично.

Контракт v1: `_meta` необов'язковий; якщо є — object, sources якщо є — array source objects з унікальними непорожніми json IDs. Для оголошених sources зберігати всі присутні attribution поля; неповні full/version не вигадувати, warning. Entity.source без declaration приймається як external source ID із warning `SOURCE_METADATA_MISSING`, без створення вигаданої атрибуції. Missing entity.source — row blocker до явного binding; implicit source defaults у v1 не підтримуються взагалі, включно з builtin PHB/DMG. Unknown source ID сам по собі не є помилкою. Edition unknown приймається з preview warning; без `_meta` жодного automatic classic/one inference.

`_meta.dependencies/includes/internalCopies` — декларації, не дозвіл скачати контент. `_copy` і magicvariant.inherits у v1 **не обчислюються**, навіть якщо parent є: записи з material copy semantics пропускаються як `UNSUPPORTED_COPY`, залежні записи блокуються. Порожні fluff copies просто входять у skipped fluff. Наступна підтримка copy DSL — окреме рішення, не прихована «merge object» евристика.

Upstream edition enum: classic/one. Effective edition = record.edition, інакше `_meta.edition`, інакше unknown. Версія джерела й schema version — окремі значення. Classic не конвертується в one, unknown не оголошується SRD5.2. Кампанія може містити змішаний контент; preview показує конфлікти й вимагає явного підтвердження mixed edition, особливо parent class/subclass. Назва книжки чи актуальна сторінка видавця не змінюють edition файлу.

## 8. Порожня кампанія та залежності

Файл не гарантує повного набору базових правил. Спочатку всі обрані записи файлу, потім записи цього compendium, вже імпортовані в цю кампанію. Жодного довільного name-match до unrelated local content.

Для відсутніх базових refs preview пропонує мінімальний dependency closure із **вже наявного доступного офіційного SRD-шаблону**, з його джерелом та edition. Ніяких зовнішніх book downloads. Користувач погоджує цей набір у тому самому підтвердженні імпорту; при одному однозначному сумісному джерелі додавання рекомендоване за замовчуванням. Якщо існує лише SRD5.2, а файл classic, це mixed edition з окремим явним checkbox, не мовчазна сумісність. Несумісний parent subclass level не виправляти автоматично; показати конкретний конфлікт.

SRD не переписує custom entries, не додає всі свої категорії без потреби і не створює single source-sync прив'язку кампанії до шаблону. Дозволені explicit per-ref bindings до конкретного local record або source з preview; зберігати їх для повторного імпорту, перевіряти type/campaign/edition. Якщо шаблон недоступний, повідомити «додайте базовий клас/заклинання або виключіть залежний запис», показати решту незалежного контенту готовою до імпорту.

Rules bootstrap: запропонувати в preview наявний 5e-профіль правил для classes/items та інших перенесених категорій; застосувати лише змінені видимі прапорці через чинний rules validator. Compendium не містить довільного наказу змінювати правила платформи. Не змінювати visibility/invites/DM/allowPlayerEdit/AI credentials. Не створювати героїв із monster.isNpc, історію кидків або бої з текстових глав.

Campaign name/description не брати автоматично з назви першого source або книжки. Для порожньої кампанії можна запропонувати title/короткий summary з явно обраного manifest у тому самому preview; чинне ім'я/опис зберігаються, якщо користувач не обрав заміну. Attribution додається до credits. Сторінки матеріалів створювати `kind=note,status=draft,characterId=null`, з непорожнім DM notes та порожнім story; через `contentWrite` будувати searchText, зберігати versions за чинним контрактом. Глави і supporting materials рахуються в selected-record limits; завеликі глави блокуються до виключення/поділу користувачем, без тихої втрати тексту. Campaign settings, яких 5etools не задає, залишаються поточними з поясненням, а не вгадуються з prose.

## 9. Стабільна ідентичність і повторний імпорт

Чинні `sourceId/sourceHash` належать template source-sync: **не використовувати їх для 5etools identity**. Bundle виключає ці поля й проставляє власний source lineage. Назви в бібліотеках мають власні uniqueness guards, але не зберігають source/edition.

Запропоноване розширення в Task19: campaign-scoped `CompendiumSource`, `CompendiumEntry` та `CompendiumImportRun` (назви — проєкт дизайну). Source зберігає json ID й атрибуцію; entry — canonical key, local kind/id/nested locator, effective edition, adapter version, input hash, lastApplied native baseline, source notes, manual paths, explicit ref bindings. Run — idempotency key, стан і структурований report без повного payload. Unique entry constraint `(campaignId, canonicalKey)`, run `(campaignId, idempotencyKey)`; FK campaign cascade, RLS та DM access як у чинній інфраструктурі. Tx lock кампанії серіалізує два imports/changes для перевірки baseline.

Locking — спільний контракт `withCampaignContentWrite(campaignId, callback(tx))`: lock Campaign row до читання existing/baseline/guard і записів. Його мусять використовувати звичайні create/update/delete усіх імпортованих kinds, CSV writes, compendium confirm, source-sync apply, scenario content writes і rules writes; transaction-local внутрішні функції не відкривають nested transaction. Інакше імпортер не вважається concurrency-safe. Preview може читати без lock, confirm усе перечитує під lock. Не блокувати HTTP/network роботу всередині lock. Клієнтський explicit PATCH, який прийшов після commit імпорту, лишається звичайною пізнішою ручною зміною і буде conflict на наступному reimport.

Canonical key — JSON tuple, не неоднозначне з'єднання через `|`: `[formatVersion,kind,source,edition,name,parentTuple?]`. NFC, trim і case folding для lookup; exact original name/source зберігаються. Колізії після нормалізації у файлі → error з двома paths. ParentTuple включає повну class/race identity; feature додає level. Source version не входить у key, перейменування/source/edition зміна → нова identity; не вгадувати rename. Source abbreviation не є identity.

У same-name/different-source collision лишаються різні identities. Для domain name guards deterministic display suffix `Name [source; edition]` тільки коли потрібен; оригінальна назва окремо в provenance. Якщо suffix перевищує schema max length — стабільно скоротити лише display name з hash suffix, preview показує обидві форми; original не обрізати.

Reimport: same input+adapter+bindings і baseline без локальних змін→unchanged, IDs збережені. Змінені джерельні поля оновлюються, якщо local value=lastApplied; локально змінені поля дають conflict. Default — keep local, explicit overwrite обирається в preview. Злиття subclasses/lineage options — по stable nested id, не overwrite всього масиву; видалені у файлі записи **не видаляються**, позначаються missing-in-file у report. Повтор click/retry з тим самим idempotency key повертає попередній committed report без повторних writes. Змінений plan під тим самим key→409.

Clone/bundle/source-sync: нові provenance records мають окрему versioned optional bundle секцію; campaign/local ids remap, external canonical keys/attribution незмінні. Старий bundle без секції чинний. Після clone imported identity лишається локальною, source-sync lineage окремий. При видаленні domain row provenance не може dangling-match при reimport: той самий write service очищує binding або позначає missing target. ScenarioPage source binding живе у CompendiumEntry, бо модель не має sourceId. Видалення кампанії очищує все; content export не додає весь original JSON.

Source-sync policy v1: provenance їде разом із відповідним native row при create/update і remap local/nested locators у тій самій транзакції; не створюється другий canonical binding. Update використовує явне source provenance або, якщо source його не має, лишає local provenance baseline незмінним і позначає `changedOutsideCompendium` для наступного conflict/reimport. Native executionMode є звичайним domain field, ніколи не виводиться з наявності provenance. Source-sync delete очищує local binding після чинних in-use guards. Від'єднання template source-sync саме по собі не видаляє compendium provenance. Merge-конфлікт canonicalKey→інший localId блокує sync/import до явного resolution, а не дублює записи.

## 10. Збереження та ліміти

За замовчуванням зберігати лише перенесені domain дані, source attribution, allowlisted нормалізовані entries/source notes і hash/baseline. Не зберігати цілий original file або unsupported Foundry payload. Необроблені unknown values — skipped; report містить path/reason. Проєктуємо source notes panel для бібліотек, щоб опис Unit або manual requirement не існував лише у transient report. Подробиці rulebook/fluff та images не дублювати в кожний запис. Main entries з легально імпортованого user file можуть зберігатися як його приватний контент; локальний дослідницький файл не імпортується взагалі.

Запропоновані стартові ліміти (продуктові defaults автора, не вимоги upstream): UTF-8 JSON object;3MiB файл; до10000 root records, до2000 обраних domain/nested records за один atomic import;100 sources; глибина32;500000 JSON nodes; string до128KiB; record до256KiB; rendered notes до64KiB; description і кожне доменне поле — також у своїх чинних schema limits. Перевищення не обрізається мовчки: row error або file error, пропозиція виключити category/розділ. Прості CSV/табличний JSON залишають власні limits.

Для великих bookData: parser рахує весь файл у Web Worker; перед server request відбирає обрані categories/chapters без fluff/Foundry/media. Serialized request до3000000 байт (чинний import chunkBytes; не піднімати понад hosting body cap). Якщо обране перевищує — до відправки запропонувати менший набір, не розбивати один atomic import на невидимі незалежні commits. Сервер повторює всі guards для отриманого projection; заявлені клієнтом totals full-file — інформаційні. Ліміти scanner застосовуються до JSON.parse, а nodes/depth/duplicate-object-keys — tokenizer до parse. Заборонені prototype keys `__proto__/constructor/prototype` у всіх об'єктах; null-prototype maps для indexes. Невалідний UTF-8, NaN/Infinity, неоднозначні duplicate keys, root null/array, неправильні category types → reject до writes.

Browser parsing timeout5s із cancel/worker terminate; server planning15s; tx timeout30s/maxWait5s; concurrency1 import на campaign. Якщо ліміти не вкладаються — 413/422 з дією, не частковий успіх. HTTP/platform timeout реалізатор звіряє з реальною конфігурацією route; обрані таймаути мають бути нижчі за неї. Немає URL-import, ZIP, JSON5 або executable modules.

## 11. Preview → confirm → report

1. «Імпорт» пропонує чинний табличний потік і JSON-компендіум; auto-detect виправляє невдалий вибір. Файл читається локально, нічого не пишеться в кампанію.
2. Server preview перевіряє DM права, sources/edition, mapping, refs, dependency closure, rules diff, conflicts і manual requirements. Показує counts для кожного типу, create/update/unchanged/partial/skipped/error, а також конкретні missing refs. Усі підтримувані categories обрані типово; пов'язані об'єкти позначені як залежності. Book/adventure текст — окремий видимий вибір «Додати матеріали ДМ», з кількістю сторінок; images/fluff не обрані й не імпортуються.
3. Preview має стани «можна імпортувати» та «готовність до гри». Перше не означає, що перенесено всі правила. Для blocker records користувач може вирішити ref або одним кліком виключити всі blocked разом із залежними; решта плану перебудовується. Жодних записів до натискання «Імпортувати».
4. Preview повертає підписаний сервером digest normalized input+selection+bindings+adapterVersion+baseline hash+settings diff, термін15хв, прив'язаний до actor/campaign. Секрет HMAC лише серверний; за відсутності конфігурації endpoint fail closed. Confirm надсилає ті самі дані й token; server перевіряє права та повторно будує план. Зміна baseline/ролі/файлу →409/403 і новий preview, а не застосування старого плану. Preview не зберігає payload у БД.
5. Confirm виконує один atomic write для обраного valid closure: нові ids зарезервовані в пам'яті, refs ремапляться, schema/guard перевірки ще раз, потім source groups→spells→feats→backgrounds→races/classes із вкладеними features→artifacts/units→scenario notes і settings. Фактичний порядок topological, а не жорсткий порядок root keys; будь-які механічні цикли блокуються раніше. Dependency bootstrap у тій самій транзакції. Error будь-де→rollback domain/provenance/settings/run. Invalidation після commit.
6. Підсумок: counts, посилання на заповнені бібліотеки/сценарій і «Що далі». Кожна дія має priority, code, entity locator, missing field/ref, пояснення й destination: «Налаштуйте цілі цього заклинання», «Додайте базовий клас», «Ведіть custom skill вручну», «Видайте спорядження/гроші героям», «Створіть персонажів», «Прочитайте неперенесені правила». Немає хибного «готово до гри» при unresolved core dependencies/manual actions. Report доступний повторно після refresh DM користувачу, без необхідності знову обирати файл.

Report JSON: `runId`, `adapterVersion`, `sources`, `editionSummary`, `countsByCategory`, `rows[{canonicalKey,kind,targetId?,status,coverage,issues[]}]`, `nextActions[]`; issue=`{code,severity,path,messageKey,refKey?,destination?}`. Report export містить атрибуцію й identifiers, не книжковий текст, картинки або вихідні рядки. UI може показувати names власнику; operational logs лише runId/category/counts/code/duration. Для довгого report pagination; загальна кількість issue paths обмежена10000 з per-code counts, не втратою сумарної кількості.

## 12. Права, приватність та attribution

Операція доступна автентифікованому DM цільової кампанії через чинні actor/access checks, включно з Origin/CSRF та rate limiting. Гравець, member без DM, чужа кампанія й звичайний content token не отримують aggregated import endpoint. Preview і confirm однаково перевіряють права; source шаблони — за чинною видимістю. Жодної можливості задати campaignId/owner/DB id через payload.

Користувач підтверджує право використати свій файл в цій кампанії. Source metadata не є ліцензією. Зберігати authors, convertedBy, full/abbreviation/json, version/dateReleased, url та page/additionalSources/otherSources/referenceSources, якщо вони присутні; показувати поруч із контентом і в credits без перезапису попередніх credits. Unsafe URL — текст без активного посилання. При clone/export attribution зберігається, автоматичної публікації або official visibility немає.

Жодних payload у analytics/errors/server logs/localStorage/AI mapping. У браузері — тільки пам'ять вкладки, очищення при закритті майстра. Невідомі URL не завантажуються сервером; формат не дає доступу до filesystem. Комерційні файли не потрапляють у seed, fixtures, репозиторій або публічний storage. У цій задачі приклад з Downloads ніколи не передається import endpoint, навіть майбутньому локальному live server.

## 13. Acceptance criteria Tasks19–21 після погодження

- Порожня custom campaign+синтетичний aggregate з усіма native categories, features і матеріалами → один preview/confirm наповнює всі відповідні бібліотеки й DM notes; не потрібні CSV mapping або імпорт кожного типу окремо. CSV/TSV/simple JSON і bundle не регресують.
- Generic unknown homebrew sources/types/skills без назв реальних книжок → стандартні поля імпортовані; unsupported values мають coverage/report/next actions, жодної книжкової таблиці overrides або AI.
- Classic background без ability/feat → без ASI/origin. Synthetic one background із3/2/20, origin feat і nested spell pick → чинні Choice/Picks і backgroundsResource; немає автоматичної видачі gear/gold, зміни biography або старих picks. Custom skill/tool choice залишаються описом. Used ASI change→409/rollback.
- Same-name different-source/edition та nested parent identities → різні stable IDs; identical reimport→unchanged; rename→new identity; native local edits→visible conflict, default keep local; lost/deleted targets, simultaneous confirm, stale preview, duplicate send→контрольовані результати без дублів.
- Hard ref missing/non-origin/wrong campaign/unselected dependency → blocker до writes; preview дозволяє вирішити або виключити closure. Text refs не блокують решту. Parent class missing у file → сумісний available SRD dependency closure або чітка next action; classic→one ніколи не проходить без explicit mixed-edition choice.
- Class/subclass і race/subrace refs не перетирають локальні nested entries; IDs survive reimport/clone. Optionalfeature без owner не перетворюється на Feat. Template lineage і compendium provenance не змішуються.
- Adventure/book manifest з data→приватні DM notes за schema/versioning; не відкритий player story. Нема live battles, automatic NPC heroes, image/font fetch. Непідтримані entries/Fluff/Foundry/copy/inherits видимі в report.
- Manual spell не отримує invented targeting і не може виконати fake auto cast; UI відкриває опис/редактор. Після підтвердженого налаштування механіки наявний cast path працює звичайно. Partial monster зберігає числові stats і читабельні дії; відсутні AC/HP не заповнюються неправдивими defaults.
- Межі size/depth/nodes/record/string, invalid UTF-8, duplicate keys, prototype payload, XSS tags, cyclic refs, timeout, report pagination, unauthorized preview/confirm перевірені тільки синтетичними fixtures. Будь-яка commit-помилка дає повний rollback; reimport не видаляє відсутні records.
- Attribution і coverage доступні після refresh, export/clone/remap збережені, unknown field не зникає мовчки. Operational logs не містять text/media/file body. Report кожному manual/skipped/error дає наступну дію, ready-to-play не завищує підтримку.

Потрібне погодження цього дизайну перед Task19, зокрема: багатокатегорійний імпорт+DM матеріали; compendium provenance окремо від template sync; manual gate для неперенесених spells; explicit optional SRD dependency bootstrap;3MiB/2000 selected records як стартові ліміти. Це перевірка дизайну, не review або дозвіл реалізації. Юзерські уточнення про універсальний формат, empty campaign і next actions включено до §1,5,8,11,13.

## 15. Уточнення реалізації Task19

Backend: `lib/server/compendium-import/` — bounded scanner, generic adapters, source-aware plan, signed preview/confirm, transaction repository, provenance, dependency closure та bundle/sync transfer. Це ще не upload UI чи HTTP endpoints Task20. Backgrounds використовують чинний ресурс і guards; інвентар/гроші та невідома механіка лишаються ручними діями зі звіту.

Source JSON id обмежено128 UTF-8 bytes, canonical key —2000 UTF-8 bytes для безпечного індексування. Ліміти2000 обраних записів/100 sources стосуються одного JSON-імпорту; накопичений campaign bundle не обмежено цими per-file числами. Відхилений copy/inherits можна явно виключити за canonical key; запис без identity — за root path (`excludedPaths`), без прихованого виконання наслідування.

Nested provenance зберігає тільки власну частину дерева, не сусідні підраси/підкласи. Domain patch для явно зв’язаного батька не замінює його provenance. IDs виборів включають стабільну identity власника й feature, не індекс root array. Рівень підкласу виводиться лише за однозначним першим рівнем його features; неоднозначність блокує імпорт із конкретною дією. Відомі різні editions у saved/explicit local bindings потребують такого самого `allowMixedEdition`, як bootstrap.

Обмеження transfer: чинний source-sync не має scope для ScenarioPage. Bundle/clone переносить DM notes; source-sync переносить provenance обраних native rows і повідомляє, що DM-матеріали треба оновити через JSON reimport або вручну. Це не прихована синхронізація сценарію.

Відкладено Minor з фінального review: окремий список раніше імпортованих записів, відсутніх у новому файлі (автовидалення немає); повнотекстовий `searchText` клонованих DM notes наразі містить заголовок. Невідомі поля feature збережено в description. Усі fixtures синтетичні; комерційний приклад не читали повторно й не імпортували під час Task19.
