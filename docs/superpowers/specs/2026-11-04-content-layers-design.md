# Content layers — результат spike (Part 3)

Гілка `spike/content-layers` (не мерджиться). Прототип: `lib/db/content-layer.ts`, схема `SpellBase` / `SpellGroupBase` / `campaign_content_hides` / `campaigns.baseSourceId, baseVersion`, тест `lib/db/__tests__/content-layer.integration.test.ts` (12 сценаріїв, локальна БД `layers`). План: `docs/superpowers/plans/2026-11-03-content-layers.md`.

## Рекомендація: **go, з обмеженнями** (Prisma client extension)

Прозорий шар у `lib/db.ts` працює для `Spell` + `SpellGroup`: union, hide, override-при-записі, `count`, `orderBy/skip/take`, `select`, `include` між двома шарованими моделями, версійні вікна (`validFrom/validTo`), відкат матеріалізації разом з транзакцією, passthrough без запитів для кампанії без бази (HOMM5). Запасний варіант (Postgres view) не потрібен, але див. «Ризики» — три з них вимагають змін у читачах, не лише в шарі.

## Що доведено тестами

| Сценарій | Результат |
|---|---|
| Кампанія без бази | 0 запитів до `*_base`/`hides`, 1 закешований lookup кампанії на 30 с |
| union local+base, валідність за `baseVersion` | ок (v1 бачить рядок із `validTo=2`, v2 — ні, і навпаки для `validFrom=2`) |
| `where` + `orderBy` + `skip/take` + `count` по union | ок |
| `select` без полів `orderBy` | ок (шар добирає й обрізає) |
| `include: { spellGroup }`, група базова | ок, через шар `SpellGroup` |
| `update` базового id | матеріалізація копії (`sourceId = id`, `sourceHash = hash`) у тій самій транзакції, база не змінена |
| rollback транзакції | матеріалізована копія відкочується |
| `updateMany` | матеріалізує збіги, потім оновлює |
| `delete` базового / `deleteMany` | запис у `campaign_content_hides`, шаблон незмінний |

## Знахідки, що змінюють план Part 4

1. **Tx-клієнт теж «розширений», внутрішні запити шару рекурсують.** Шар читає/пише ті самі моделі (матеріалізація, пошук локальних id) → без захисту бачить сам себе. Рішення в прототипі: `AsyncLocalStorage`-bypass для внутрішніх запитів до локальних таблиць.
2. **Запити шару мусять іти в транзакції контентного запису.** Query-хук не має доступу до поточного tx; при `connection_limit=1` (тести) читання базових таблиць поза tx дає deadlock, у проді подвоює тиск на пул (ліміт 5). Прототип бере `currentContentWrite().db`. Для звичайних `prisma.$transaction` (бої) такого контексту немає — Part 4 має розширити `createScopedDatabase.$transaction`, щоб він завжди клав tx в ALS (читання базових таблиць поза tx безпечні — вони незмінні, але з'єднання вони все одно беруть).
3. **FK між контентними моделями мусять зникнути** (як і заплановано в 4.1). У spike довелося зняти `spells_groupId_fkey`, інакше локальна копія з `groupId` на базову групу не вставляється. `spells.summonUnitId → units` та інші — аналогічно.
4. **Читання за одним `id` без `campaignId`** (`prisma.spell.findUnique({ where: { id } })`): 17 місць по 13 моделях (для Spell — 5, зокрема `battles/action-service.ts`, `spell-mutation.ts`, `legendary-mutation.ts`). Шар не знає кампанії → повертає базовий рядок **без `campaignId`** (`loadOwned` на такому дасть 403/помилку). Ці місця треба змінити на `findFirst({ where: { id, campaignId } })` до/в рамках Part 4 (бій знає `campaignId`). Це також усуває читання чужих рядків за id.
5. **Порядок у `orderBy` по union — у JS, не в БД.** Рядкові порівняння можуть розходитись із колацією Postgres (регістр, кирилиця). Для списків із `orderBy: name` слід або сортувати однаково скрізь (`localeCompare` з фіксованою локаллю), або порівняти з тим, що сьогодні віддає БД.
6. **Непідтримувані форми запиту падають явно** (не мовчки втрачають базу): фільтр за відношенням (`spellGroup: {…}`), `campaignId` усередині `AND/OR`, `include` не-шарованих відношень (`skills`) при наявності базових рядків. Для 13 моделей треба або покрити, або переписати читачів — це ~8 `include` між контентними моделями і 2 фільтри в `update-race.ts` (як у плані).
7. **Типи.** `$extends` змінює тип клієнта й він перестає присвоюватись `Prisma.TransactionClient` (десятки помилок tsc). У прототипі — `as unknown as PrismaClient` у `lib/db.ts` (типи не гірші за поточні, бо шар не додає API). Виконувати каст в одному місці.
8. **Масштаб читачів:** 349 викликів `findX/count/update/delete` по 13 моделях у `lib`/`app`/`scripts` (131 — у `scripts/`, там шар лише збільшує вимоги до `campaignId` у `where`). Для Spell: 30 викликів у 23 файлах.
9. **Кеш кампанія→база** (30 с TTL) прийнятний лише з явною інвалідацією при зміні `baseVersion` (`invalidateCampaignLayer`); у Part 4 інвалідація має бути в одному місці (apply/upgrade).

## Не перевірялось у spike

- Решта 11 моделей і `knownSpells` персонажів на базові id.
- Локалізація SRD-оверлею поверх базових рядків (кеш `${sourceId}:${version}:${locale}`).
- Вартість: union-читання робить 3 запити (локальні, hides, база) замість 1; для гарячих шляхів (`getCachedSpells`, бій) потрібен кеш union за `(campaignId, contentVersion)`. Заміри не робились.
- Фактичний вплив на повний тестовий набір — див. нижче.

## Результат повного прогону тестів з увімкненим розширенням

1828/1829 файлів, 12 687 тестів зелені (без `dm/units/page-client.test.tsx`; 3 старі падіння не відтворились). Єдине падіння — `lib/__tests__/db-pool.test.ts`: мок `@prisma/client` без експорту `Prisma`, який тепер імпортує `content-layer.ts` (`Prisma.defineExtension`). Лікується `importOriginal` у моку. Тобто fake-db тести шар не ламають, бо майже всі мокають `@/lib/db`; реальну поведінку перевіряють лише інтеграційні тести.
