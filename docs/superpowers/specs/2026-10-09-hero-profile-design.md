# Профіль героя: велике фото, жетони, ріст за архетипом і расою

Дата: 2026-10-09. Три незалежні частини, порядок виконання: 1 → 2 → 3.

## Мета

- Кожен гравець чітко бачить, як виглядає його герой, — велике фото в профілі.
- ДМ видає гравцям червоні й зелені жетони з підписом; гравець бачить їх кількість і підписи.
- Ріст HP і шкоди залежить від того, як герой грає: архетип (Воїн, Лучник, Маг…) і раса (ельф стріляє краще, слабший впритул). Ручні множники героя прибираємо.

## Частина 1. Велике фото героя

### Проблема зберігання

`Character.avatar` зараз — base64 data URL (до 3 МБ, `components/ui/image-upload.tsx`). Він копіюється в знімок учасника бою (`lib/utils/battle/participant/from-character.ts:112`), тож велике фото роздуває `battle_participants.snapshot`, дельти Pusher (> 9 500 байт → `refetch`) і egress Supabase.

### Рішення

- **Storage.** Новий публічний бакет `avatars` (за зразком `lib/supabase/artifact-icon-storage.ts`, admin-клієнт, `ensureBucket`). Файл — `<campaignId>/<characterId>/<uuid>.webp`, `cacheControl` рік (файли незмінні, нове фото = новий шлях).
- **Завантаження.** Як для іконок артефактів: форма надсилає data URL у `avatar` при створенні/PATCH героя, сервер (`resolveAvatarForPersistence`) кладе файл у бакет і зберігає публічний URL; URL нашого Storage зберігається як є. Доступ — як у PATCH героя. Старі файли не видаляються (дрібниця для free tier).
- **Клієнт.** `ImageUpload` з `maxSide={1200}` стискає фото в браузері до ≤ 1200 px webp ~0.85 (canvas) перед тим, як покласти data URL у форму. Поле URL (`IconUrlField`) лишається.
- **Сумісність.** Наявні base64-аватари далі показуються (`EntityIcon` їх підтримує). Скрипта міграції немає — прод порожній.

### UI

- **`ProfileHero`**: великий портрет. Телефон — на всю ширину, пропорція 3:4, ім'я/рівень/клас під ним; ≥ 1024 px — колонка ~320 px ліворуч від імені й статів. `next/image` з `sizes`, `object-cover`, золота HUD-рамка. Без фото — плейсхолдер з першою літерою та (для того, хто може редагувати) підказкою «Додати фото». Натиск на фото відкриває його на весь екран (`ResponsiveDialog`).
- **`DmCharacterCard`**: портрет угорі картки (3:4, обрізаний `object-cover`) замість кружка 56 px.
- Бій, налаштування бою, списки учасників — без змін (малі іконки).

### Тести

- Route: 401/403/404, неправильний тип/розмір → 400, успіх записує URL (Storage замокано).
- Компонент `ProfileHero`: рендер з фото / без фото.

## Частина 2. Жетони

### Дані

Нова таблиця (міграція з `ENABLE ROW LEVEL SECURITY`):

```prisma
model CharacterToken {
  id          String   @id @default(cuid())
  characterId String
  character   Character @relation(fields: [characterId], references: [id], onDelete: Cascade)
  color       String   // "red" | "green"
  label       String   // 1..120 символів
  createdBy   String
  createdAt   DateTime @default(now())

  @@index([characterId])
  @@map("character_tokens")
}
```

Один запис — один жетон. Кількість = число записів кольору. Жетони не впливають на механіку.

### API

`app/api/campaigns/[id]/characters/[characterId]/tokens/`:

- Читання — разом з листом героя: `GET …/sheet` (уже пускає лише ДМа й власника) віддає `story.tokens`, новіші першими. Окремого `GET` немає.
- `POST` — лише `requireDM`. Тіло `{ color: "red" | "green", label: string }` (Zod, trim, 1–120).
- `DELETE …/tokens/[tokenId]` — лише `requireDM`; `loadOwned` перевіряє належність кампанії/герою.
- Помилки — тексти з `lib/constants/api-errors.ts`.

Клієнт: `createCharacterToken`/`deleteCharacterToken` у `lib/api/characters.ts`, хук `useCharacterTokens` у `lib/hooks/characters` оновлює кеш листа героя. Тип — `types/characters.ts`.

### UI

У `StoryTab` (поруч з біографією) блок «Жетони» (`HudSection`):

- два лічильники — червоний і зелений кружок з числом;
- список жетонів: кольорова мітка, підпис, дата;
- ДМ: кнопка «+ Жетон» → `ResponsiveDialog hud` з вибором кольору (два чіпи) і полем підпису; кнопка видалення біля жетона з `useConfirm()`;
- гравець — лише перегляд; порожній стан — «Жетонів ще немає».

Блок показується лише тим, хто має доступ на читання (ДМ, власник).

### Тести

- Route: доступи (ДМ / власник / чужий гравець), валідація, видалення чужого жетона → 404.
- Компонент: лічильники рахують кольори; кнопки ДМ приховані для гравця.

## Частина 3. Ріст героя: архетип і раса

### Архетип

Нове поле `Character.archetype String?` (expand-only міграція; `null` = «Універсал», поточна поведінка). Довідник `lib/constants/hero-archetypes.ts`:

| Ключ | Назва | HP/рівень | Ближній | Дальній | Магія |
|---|---|---|---|---|---|
| `universal` (null) | Універсал | 10 | 100 % | 100 % | 100 % |
| `warrior` | Воїн | 12 | 120 % | 80 % | 60 % |
| `paladin` | Паладин | 14 | 110 % | 50 % | 90 % |
| `ranger` | Лучник | 9 | 70 % | 125 % | 70 % |
| `rogue` | Розбійник | 9 | 110 % | 100 % | 60 % |
| `mage` | Маг | 8 | 50 % | 60 % | 125 % |

Цифри — стартові; фіксуються після прогону балансу (див. «Перевірка»).

ДМ обирає архетип у формі героя (`CharacterBasicInfo`, `SelectField`); власник при `allowPlayerEdit` змінити його не може (стрипається в `patch-character.ts`, як `level`). У профілі архетип показується поруч з класом.

### HP

`hero-scaling.ts`: `HP = max(1, floor(3 × hpPerLevel + рівень × (hpPerLevel(архетип) + мод.ВИТ × 1.5)))` — базовий запас `3 × hpPerLevel`, щоб герой 1-го рівня не був слабшим за юніта T1 (медіана 31 HP). Орієнтир (ВИТ +1): Універсал 41 / 64 / 99 / 145 / 202 / 260 на рівнях 1 / 3 / 6 / 10 / 15 / 20 ≈ 1.1–1.6 × HP юніта відповідного тіру. Сила більше не впливає на HP (вона дає шкоду ближнього бою); тепер ВИТ гномів/некромантів має сенс. `heroBaseHp` приймає `{ level, constitution, archetype }`. Ручний `hpMultiplier` героя не читається.

### Шкода

- Ручні `Character.meleeMultiplier` / `rangedMultiplier` / `hpMultiplier` не читаються рушієм і прибираються з форми (`scalingCoefficients` у `character-form.ts`). Колонки лишаються в БД (expand-only).
- `from-character.ts` заповнює `abilities.meleeMultiplier` / `rangedMultiplier` з архетипу (+ нове `abilities.magicMultiplier`). Завдяки цьому `applyHeroDmDamageMultiplier` (`compute.ts`), `breakdown.ts`, `average.ts` і оцінка сили партії в чесному балансі працюють без змін логіки.
- Рядок розбору шкоди: `× 1.2 (архетип: Воїн) = …` замість «коеф. DM».
- Магія: у `spell/power.ts` (`computeSpellPower`, там же діє расовий `damageBonus` magic) шкода героя множиться на `magicMultiplier`, лікування — ні; оцінка spell DPR героя в `balance` теж множиться на нього.
- Кубики рівня і `+рівень` — без змін.
- Ворожий множник чесного балансу (`battleData.damageMultiplier`/`hpMultiplier`) — без змін.
- Бої, що вже йдуть, зберігають старі значення у знімках.

### Раса

Бонуси раси — дані, не код: `damageBonus` з фільтром `melee` / `ranged` / `magic` (відсоток, може бути від'ємним) додається в `trait` пасивок `data/library/race-passives.ts` і в їхні описи:

| Раса | Бонус |
|---|---|
| Люди | ближній +10 % |
| Демони | ближній +15 %, дальній −10 % |
| Ельфи | дальній +20 %, ближній −15 % |
| Темні ельфи | ближній +15 %, магія −10 % |
| Гноми | ближній +10 %, дальній −10 % |
| Некроманти | магія +10 %, ближній −10 % |
| Маги | магія +15 %, ближній −20 % |

Перевірити, що `collectModifiers` застосовує від'ємний `percent` і фільтр `magic` до шкоди заклинань героя; якщо ні — виправити в рушії. Бонус раси й відсоток архетипу множаться (раса — модифікатор, архетип — після модифікаторів).

### Перевірка

- Юніт-тести: HP за архетипом/ВИТ; множники архетипу в `from-character`; рядок розбору; магія в `cast`; від'ємний расовий бонус.
- Прогін балансу (`scripts/balance-library.ts` / симуляція) для 6 архетипів × рівні 1/5/10 — жоден архетип не сильніший за середній більш ніж на ~15 % за `HP × DPR`; цифри в таблиці коригуються під результат.
- **Підсумкова таблиця (обов'язковий результат у кінці роботи):** для кожного архетипу та кожної раси (архетип × раса) — HP і приблизна шкода за удар (ближній / дальній / магія) на рівнях 1, 3, 6, 10, 15, порахована фінальним кодом (`getCharacterStats` / `average.ts`), з переліком припущень щодо характеристик і зброї. Записується в `docs/reports/hero-growth-2026-10.md` і виводиться користувачу.
