# Конструктор кампаній — етап 4: механіки D&D 5e (дизайн)

## Context

Мета епіку уточнена користувачем 2026-10-22: будь-хто, хто грає в D&D 5e, має перенести свою кампанію в трекер **за всіма правилами**, так само як HOMM5 працює зараз. Епік вважається завершеним, коли є два повноцінні режими — HOMM5 і 5e. **Warhammer (етап 5) переноситься на після MVP.** Злиття `feat/constructor` у `main` і prod — після етапів 1–4 і 6.

Розвідка (стан коду на 2026-10-22):
- **Стани.** `applyCondition` пише `ActiveEffect` з `type: "condition"` і маркером у `effects`. Ключі (`CONDITION_KEYS`) механічні — `skip_action`, `immobilized`, `no_reaction`, `no_bonus_action`, `disable_*` — і рушій читає їх через `hasEffectMarker`. 5e-станів немає. `charm` і `berserk` — HOMM-контроль, а не 5e «зачарований». `ActiveEffect.abilityEffects: StaticEffect[]` уже читає `collectModifiers` (`collect-modifiers.ts:186`).
- **Перевага й перешкода** є тільки на атаках (`attack/bonus.ts`: `rollModeReasons`, прапорці `advantage`/`disadvantage`/`…ForAttackers`). `rollSavingThrow` (`spell/power.ts:24`) = d20 + модифікатор, без майстерності, переваги й автопровалу.
- **Рятівні кидки.** `Character.savingThrows` (`Record<ability, boolean>`) тільки показуються. Рятівні кидки кидають заклинання (`spell/cast/outcome.ts`) і `maneuvers/fire-burst.ts`; клієнт може передати готовий кидок (`saveRolls`).
- **0 HP.** `applyDamageToTarget` → `unconscious` (HP 0) / `dead` (HP < 0). Кидків смерті немає; союзники встають після перемоги (`turn/victory.ts`).
- **Концентрації немає.**
- **Класи.** `Character.class` — вільний текст для показу. На рушій впливає лише `archetype` (5 ключів у коді). Слоти — саморобна таблиця або крива повного заклинача 5e до 10 рівня; рівні заклинань 0–5.
- Правила кампанії: `RulesetSchema` (секції з default = поточна поведінка) + `MECHANIC_REGISTRY`; рушій читає зафіксовану копію `battle.rules`; `Ruleset` уже передається в початок ходу (`turn/start-end.ts`).

## Загальні правила етапу 4

- **Нульова зміна HOMM5.** Нові секції `rules` мають default «вимкнено» або «як зараз»; нові ключі станів і прапорців не використовуються в HOMM-контенті. Усі наявні тести рушія проходять без змін.
- Механіки — каталог у коді (`MECHANIC_REGISTRY`, реєстр станів); кампанія вмикає й налаштовує їх у `rules`. Рушій бою читає тільки `battle.rules`.
- Нові бонуси й прапорці читаються лише через `collectModifiers`/`runAbilities`, як вимагає `abilities.md`.
- Міграції лише розширюють схему. 4a міграцій не потребує (усе в JSON: `rules`, snapshot, `Spell.definition`).

## 4a. Дизайн

### 1. Правила (`lib/utils/rules/schema.ts`)

Нові секції `RulesetSchema` (і `RulesetPatchSchema`, `MECHANIC_REGISTRY`, вкладки на `dm/rules`):

```ts
saves:         { proficiency: false }                       // майстерність з Character.savingThrows
deathSaves:    { enabled: false, unitsDieAtZero: true }     // кидки смерті героїв; юніти при 0 HP помирають
concentration: { enabled: false, dcCap: null }              // null — 2014 (без межі), 30 — 2024
conditions:    { enabled: false, exhaustion: "2014" }       // меню станів ДМ і група 5e в редакторі; "2014" | "2024" — таблиця виснаження
```

Default кожної секції відтворює поточну поведінку. Перевага/перешкода й автопровал рятівних кидків не мають перемикача: вони походять лише з даних (стани 5e, прапорці), яких у HOMM-контенті немає.

### 2. Стани 5e

`lib/utils/battle/conditions/` — реєстр `CONDITION_5E_REGISTRY` (`satisfies Record<Condition5eKey, Condition5eDef>`):

```ts
type Condition5eDef = {
  label: string;               // українська назва
  description: string;
  markers: ConditionKey[];     // наявні маркери: skip_action(100), no_reaction, no_bonus_action, immobilized, ...
  flags: StaticEffect[];       // прапорці для collectModifiers
  implies?: Condition5eKey[];  // напр. paralyzed → incapacitated
};
```

Ключі: `blinded`, `charmed`, `deafened`, `frightened`, `grappled`, `incapacitated`, `invisible`, `paralyzed`, `petrified`, `poisoned`, `prone`, `restrained`, `stunned`, `unconscious`, `exhaustion`.

| Стан | Як діє в рушії |
|---|---|
| Засліплений | власні атаки — перешкода; атаки по ньому — перевага |
| Зачарований | не може атакувати джерело стану (атакою чи шкідливим заклинанням) |
| Оглухлий | лише маркер (бойового ефекту немає) |
| Наляканий | перешкода на атаки, поки джерело живе; рух, що зменшує відстань до джерела, відхиляється |
| Схоплений | швидкість 0 (`immobilized`); 2024: перешкода на атаки по всіх, крім того, хто схопив |
| Недієздатний | без дії, бонусної дії й реакції (`skip_action` 100 + `no_bonus_action` + `no_reaction`); знімає концентрацію |
| Невидимий | власні атаки — перевага; атаки по ньому — перешкода |
| Паралізований | недієздатний + швидкість 0; автопровал Сил/Спр; атаки по ньому — перевага; влучання з 5 фт — крит |
| Скам'янілий | недієздатний + швидкість 0; автопровал Сил/Спр; атаки по ньому — перевага; опір усій шкоді; імунітет до отруєння |
| Отруєний | власні атаки — перешкода |
| Повалений | власні атаки — перешкода; атаки по ньому з 5 фт — перевага, здалеку — перешкода (вставання — частина 4b; до 4b стан знімає ДМ або тривалість) |
| Обплутаний | швидкість 0; власні атаки — перешкода; атаки по ньому — перевага; перешкода на рятівні Спр |
| Приголомшений (stunned) | недієздатний + швидкість 0; автопровал Сил/Спр; атаки по ньому — перевага |
| Непритомний | недієздатний + швидкість 0 + повалений; автопровал Сил/Спр; атаки по ньому — перевага; влучання з 5 фт — крит |
| Виснаження (1–6) | 2014: 1 — (перевірки, поза боєм), 2 — швидкість ×½, 3 — перешкода на атаки й рятівні, 4 — макс. HP ×½, 5 — швидкість 0, 6 — смерть. 2024: −2×рівень до кидків d20 (атаки, рятівні), швидкість −5 фт×рівень, 6 — смерть |

Нові прапорці (`FlagSchema`, `labels.ts`, редактор здібностей):
- `saveAdvantage` / `saveDisadvantage` `{ abilities: AbilityKey[] | "all", vsSpells?: true }` — «Магічний опір» = `saveAdvantage all vsSpells`;
- `autoFailSave` `{ abilities: AbilityKey[] }`;
- `saveProficiency` `{ abilities: AbilityKey[] }` — для юнітів і здібностей (герої беруть його з `Character.savingThrows`, якщо `rules.saves.proficiency`);
- `autoCritAdjacent` — влучання по власнику з 5 фт (сусідня клітинка) стає критом;
- `proneDefense` — атаки по власнику з 5 фт мають перевагу, здалеку — перешкоду (окремий прапорець, бо наявні `…ForAttackers` не залежать від відстані);
- новий стат `savingThrow` у `DYNAMIC_STATS` (`modifyStat`, flat) — для «Благословення»/«Порчі» та бонусів рятівних кидків.

Застосування: `applyCondition` приймає `condition: ConditionKey | Condition5eKey`. Для 5e-ключа він пише один `ActiveEffect` (`type: "condition"`, `name` = назва стану), де `effects` = маркер самого стану + маркери реєстру (з `implies`), а `abilityEffects` = прапорці реєстру. Варіант виснаження береться з `ctx.rules.conditions.exhaustion` у момент накладання; `value` маркера `exhaustion` = рівень, повторне накладання додає рівні (до 6; на 6 — смерть). Додаткові поля `applyCondition`:
- `saveEnds?: { ability: AbilityKey }` — наприкінці кожного ходу ціль повторює рятівний кидок проти СК накладача (зберігається в ефекті), успіх знімає стан;
- `levels?: 1–6` (лише для `exhaustion`).

Імунітети: `conditionImmunity` приймає й 5e-ключі (`[...CONDITION_KEYS, ...CONDITION_5E_KEYS, "fear", "berserk", "charm"]`). Імунітет до `incapacitated` не блокує `stunned` — перевіряється лише ключ, що накладається.

Рушій читає стани:
- атаки — `rollModeReasons` (прапорці з `abilityEffects` уже потрапляють у `collectModifiers`) + нові `proneDefense` (за відстанню атакувальника до цілі) і `autoCritAdjacent` (у `attack/critical`);
- `frightened`/`charmed` — перевірка джерела (`ActiveEffect.source.participantId`) у валідації атаки/заклинання й руху (`grid/path.ts`);
- маркери (`skip_action`, `immobilized`, …) — як зараз, через `hasEffectMarker`.

### 3. Рятівні кидки

`rollSavingThrow` переходить на `rollSave({ target, ability, dc, participants, rules, rng, presetRoll, source })` у `lib/utils/battle/saves/`; усі виклики оновлюються, `rollSavingThrow` видаляється:
1. `autoFailSave` для цієї характеристики → провал без кидка (лог «автопровал»).
2. Режим кидка: `saveAdvantage`/`saveDisadvantage` (з урахуванням `vsSpells`, коли кидок проти заклинання) + виснаження 2014 рівня 3+; обидва → звичайний.
3. Бонус = модифікатор + майстерність (`saveProficiency` або `Character.savingThrows` за `rules.saves.proficiency`) + `modifyStat savingThrow` + виснаження 2024 (−2×рівень).
4. `presetRoll` (від клієнта) — перший d20; другий для переваги/перешкоди кидає сервер.

Результат містить `mode`, `rolls`, `bonus`, `autoFail` для лога й `actionDetails.savingThrows`. Виклики: `spell/cast/outcome.ts`, `maneuvers/fire-burst.ts`, повторні кидки `saveEnds`, концентрація, кидки смерті (вони — окремий d20 без модифікатора).

### 4. Кидки смерті (`rules.deathSaves.enabled`)

Наслідки шкоди (кидки смерті, масивна шкода, концентрація) рахує один хелпер `applyDamageConsequences({ before, after, amount, crit, rules, rng })` (`lib/utils/battle/damage/consequences.ts`), який викликається одразу після кожного примітиву шкоди (`applyDamageToTarget`, `applyRawDamage` у заклинаннях, маневрах, зонах, `dealDamage`, DOT). Коли обидві механіки вимкнено, він повертає `after` без змін.

Тільки для героїв і NPC-героїв (`createBattleParticipantFromCharacter`); юніти при `unitsDieAtZero` переходять у `dead` одразу на 0 HP.
- HP 0 → статус `unconscious` + стан `unconscious` (без тривалості) + `battleData.deathSaves = { successes: 0, failures: 0, stable: false }`.
- Шкода ≥ макс. HP понад 0 (залишок після падіння на 0) → одразу `dead`.
- Черга ходу непритомного нестабільного героя (у циклі пропуску `processEndOfTurn`): d20 (сервер; лог). 10+ — успіх, 1 — два провали, 20 — 1 HP, приходить до тями (стан знімається, лічильники скидаються). 3 успіхи → `stable`; 3 провали → `dead`. Хід пропускається, як і зараз.
- Шкода по герою на 0 HP: +1 провал (+2, якщо влучання критичне); стабільність скидається.
- Лікування > 0 → HP, стан `unconscious` знімається, лічильники скидаються.
- Чинне «союзники встають після перемоги» лишається.
- Вимкнено (default) — поточна поведінка без змін.

UI: у картці учасника на 0 HP — три кружечки успіхів і провалів (`components/battle`), у лозі — кидки.

### 5. Концентрація (`rules.concentration.enabled`)

- `SpellDefinitionSchema.concentration?: boolean` + перемикач у редакторі заклинання.
- Каст такого заклинання: кастер отримує `ActiveEffect` «Концентрація: <назва>» (`type: "buff"`, тривалість = найдовша тривалість ефектів заклинання, `concentration: { castId }`); усі `ActiveEffect` і зони, накладені цим кастом, отримують `concentrationOf: { casterId, castId }`. Новий каст із концентрацією спершу знімає попередню.
- Шкода по кастеру з концентрацією → рятівний кидок Вит (через `rollSave`) проти СК `max(10, ⌊шкода/2⌋)`, з межею `dcCap`, якщо вона задана. Провал, стан `incapacitated`, смерть чи 0 HP → концентрація зникає разом з усіма ефектами `concentrationOf` цього касту (на всіх учасниках і в зонах).
- Вимкнено — поле `concentration` ігнорується.

### 6. ДМ: накласти/зняти стан вручну

Новий бойовий роут `conditions` (Zod + `runBattleMutation` + `conditions-mutation.ts`, доступ `dm`): `{ participantId, action: "apply" | "remove", condition, rounds?, levels?, saveEnds? }`. Накладання використовує той самий шлях, що й `applyCondition`, тільки без ability-власника (джерело «ДМ»). UI: у швидких діях ДМ на учаснику — меню станів 5e (`ResponsiveDialog hud`: список станів з описом, тривалість; поточні стани з кнопкою «Зняти»). Меню показується, коли `rules.conditions.enabled` або в бою вже є 5e-стан; HOMM-кампанія за замовчуванням цього меню не бачить. Рушій обробляє 5e-стани незалежно від `enabled` (вони приходять лише з даних).

Показ: стани 5e — у наявному списку ефектів учасника з назвою, іконкою і тривалістю (`view`); для гравця видно стани ворогів (вони очевидні за столом).

### 7. Перевірка 4a

- Нові тести (`__tests__` поряд): реєстр (кожен стан → маркери/прапорці; `implies`), `applyCondition` з 5e-ключем, імунітети, виснаження 2014/2024 і накопичення рівнів, `saveEnds`; `rollSave` (автопровал, перевага/перешкода/скасування, майстерність з правил, `vsSpells`, preset + другий кубик); атаки по паралізованому з 5 фт (крит), по поваленому зблизька/здалеку, наляканий біля джерела; кидки смерті (успіхи, провали, 1, 20, шкода на 0, крит, масивна шкода, лікування, стабільність); концентрація (DC, межа, знімання ефектів інших учасників і зон, новий каст, недієздатність); роут `conditions` (DM-only, 403 для гравця); `parseRules` для нових секцій.

Після перевірки тестові дані видаляються.

## 4b. Дизайн: дії 5e в бою

Розвідка (2026-10-22):
- Дія/бонус/реакція — `actionFlags`; рух рахується в клітинках (`CELL_FEET = 5`), `movementUsed`, BFS `reachable` (`grid/path.ts`), сервер отримує лише точку призначення — шлях не передається.
- Бонусна дія = лише вміння з тригером `bonusAction` через `runAbilityUse` (`pipeline/ability-use.ts`); загального маршруту «базова дія» немає.
- Реакція зараз — HOMM-відплата (`attack/retaliation.ts`): лише у відповідь на атаку; атак при відході, «зони контролю», вимушеного руху (поштовх), підготовленої дії, вставання з положення лежачи немає.
- Перевірок навичок у рушії немає (`Character.skills` лише показується).
- Мапа необов'язкова: без мапи атаки не перевіряють відстань, рух неможливий.

Рішення (ухвалені без окремого обговорення, бо користувач попросив «пиши спек і починай»):
- Дві зброї та Додаткова атака — частина 4c (залежать від класів і властивостей зброї); 4b їх не робить.
- Атаки при відході — автоматичні (реактор не обирає), як решта реакцій рушія; ручний вибір реакції гравцем — поза етапом.
- Шлях руху будує сервер (BFS з батьками, той самий порядок сусідів, що в `reachable`), а не клієнт: так сервер лишається джерелом правди без зміни API руху.

### 1. Правила

```ts
actions: { enabled: false, opportunityAttacks: true, variant: "2014" }   // "2014" | "2024": формула Схоплення/Штовхання
```

`enabled: false` (default) — жодних нових кнопок і атак при відході; HOMM без змін. Вкладка «Дії 5e» на `dm/rules`.

### 2. Каталог базових дій

`lib/utils/battle/actions/` — реєстр `CORE_ACTION_REGISTRY` (`satisfies Record<CoreActionKey, CoreActionDef>`): `{ label, description, cost: "action" | "bonusAction" | "movement", target: "none" | "ally" | "enemyAdjacent" | "self", run(ctx) }`. Один бойовий маршрут `core-action` (Zod `discriminatedUnion("action")` + `runBattleMutation` + `core-action-mutation.ts`), доступ `currentController` (власник на своєму ході, ДМ — за будь-кого).

| Дія | Вартість | Ефект |
|---|---|---|
| Ривок (`dash`) | дія | `battleData.extraMovement += movementBudget` (клітинки) до кінця ходу; `remainingMovement` враховує |
| Відхід (`disengage`) | дія | ефект «Відхід» до кінця ходу (маркер `disengaged`) — рух не провокує атак |
| Ухилення (`dodge`) | дія | ефект «Ухилення» до початку наступного ходу: `disadvantageForAttackers` + `saveAdvantage ["dexterity"]`; знімається, якщо власник стає недієздатним або швидкість 0 |
| Допомога (`help`) | дія | союзник у межах 5 фт отримує ефект «Допомога» (`advantage` на наступну атаку, `consumeOn: "ownAttack"`), що зникає на початку наступного ходу помічника |
| Сховатися (`hide`) | дія | перевірка Скритності (`rollCheck`) проти найбільшої пасивної Уважності ворогів (10 + мод. Мудр + майстерність, якщо є); успіх → ефект «Схований» (як `invisible`: `advantage` на атаки, `disadvantageForAttackers`), знімається після власної атаки чи заклинання (`consumeOn: "ownAttack"` + каст) |
| Підготувати (`ready`) | дія | `battleData.readied = { kind: "attack", round }`; до початку свого наступного ходу власник (або ДМ) може «Виконати підготовлену атаку» на будь-якому ході — атака через наявний конвеєр атаки, витрачає реакцію; на початку наступного ходу `readied` зникає |
| Встати (`standUp`) | рух | знімає всі ефекти з власним ключем `prone`; витрачає половину `movementBudget` (якщо руху не вистачає — відмова) |
| Схоплення (`grapple`) | дія (одна атака) | ціль — суміжний ворог (розміри істот не моделюються, тож обмеження «не більше ніж на розмір більша» не перевіряється). 2014: Атлетика атакувальника проти більшого з Атлетики/Акробатики цілі (`rollCheck`); 2024: ціль кидає рятівний Сил або Спр (на вибір рушія — більший модифікатор) проти СК 8 + мод. Сил + майстерність. Успіх → `grappled` з джерелом = атакувальник |
| Штовхання (`shove`) | дія (одна атака) | та сама перевірка; успіх → `prone` або відштовхнути на 5 фт (вибір гравця в запиті; клітинка позаду цілі має бути вільною та прохідною, інакше лише `prone`) |
| Вирватися (`escape`) | дія | схоплений: Атлетика/Акробатика проти Атлетики схоплювача (2014) або проти СК схоплювача (2024); успіх → знімає `grappled` від цього джерела |

Схоплення: стан зникає, коли схоплювач недієздатний або вони більше не суміжні; рух схоплювача тягне ціль у клітинку, яку схоплювач щойно звільнив, і коштує подвійно (5e: половина швидкості). Без мапи дії руху (`dash`, `standUp`, поштовх на 5 фт) лише записуються в лог.

### 3. Перевірки (`rollCheck`)

`lib/utils/battle/checks/roll-check.ts`: `rollCheck({ actor, skill | ability, participants, rules, rng, presetRoll })` → `{ roll, rolls, bonus, total, mode }`. Бонус = мод. характеристики + майстерність, якщо навичка є в `abilities.skillProficiencies` (з `Character.skills`, лише `true`) або прапорець `skillProficiency { skills }`; перевага/перешкода — нові прапорці `checkAdvantage`/`checkDisadvantage { skills | "all" }` + виснаження 2014 рівня 1+ (перешкода) / 2024 (−2×рівень). Каталог навичок — наявний `lib/constants/skills.ts`. Цю ж функцію використає 4d (перевірки поза боєм).

### 4. Атаки при відході

У `move-mutation.ts` після валідації `reachable`, коли `rules.actions.enabled && rules.actions.opportunityAttacks`:
- шлях = `pathTo(map, participants, mover, to)` (BFS з батьками; той самий граф, що `reachable`);
- для кожного ворога E, який: живий і не недієздатний, має невитрачену реакцію, має ближню атаку, мувер був у межах досяжності E (5 фт або досяжність зброї) і на кроці шляху виходить з неї, мувер не має `disengaged` — E атакує мувера в точці виходу (наявний конвеєр атаки, одна ближня атака, витрачає реакцію `hasUsedReaction`);
- якщо мувер падає на 0 HP / помирає — рух зупиняється в цій клітинці; лог: «⚔ Атака при відході: E → мувер».
- Рух ДМ у режимі розстановки (`free`, чужий хід) атак не провокує.

### 5. UI

- `ActionGrid`: плитка «Дії» (коли `rules.actions.enabled`) → `ResponsiveDialog hud` зі списком доступних дій (вартість, опис; недоступні — вимкнені з причиною), вибір цілі для `help`/`grapple`/`shove` (суміжні учасники зі списку або клік по мапі — через наявний вибір цілі майстра атаки, якщо його можна перевикористати), для `shove` — «Повалити / Відштовхнути».
- Кнопка «Підготовлена атака» в картці учасника з `readied` (для власника й ДМ) поза його ходом.
- `view/turn-exhausted.ts` враховує `extraMovement` і доступність базових дій (автозавершення ходу не спрацьовує, поки є дія і `rules.actions.enabled`).
- Лог: кожна дія — подія з назвою дії й результатом перевірки.

### 6. Перевірка 4b

- Наявні тести — без змін; HOMM (`actions.enabled: false`) — рух і атаки ідентичні.
- Нові тести: реєстр і маршрут (вартість, доступ, відмови: дію витрачено, ціль не суміжна, `standUp` без руху), `dash` + `remainingMovement`, `disengage` блокує атаку при відході, `dodge` (перешкода атакувальникам, перевага рятівних Спр, зникає на початку ходу), `help` (перевага на одну атаку), `hide` (успіх/провал проти пасивної Уважності, знімається після атаки), `ready` (атака поза ходом витрачає реакцію, зникає на початку ходу), `grapple`/`shove`/`escape` 2014 і 2024, тягнення схопленого, `pathTo`, атаки при відході (вихід з досяжності, кілька ворогів, без реакції, недієздатний ворог, мувер падає — рух зупинено, режим розстановки ДМ), `rollCheck`.
- `battle-sweep` на HOMM5; живий прогін: кампанія з увімкненими `actions` — Ривок, Відхід, атака при відході, Ухилення, Допомога, Сховатися, Схоплення з тягненням, Штовхання, Встати; десктоп + 500 px.

## 4c-1. Дизайн: класи й рівні

Розвідка (2026-10-22):
- `Character.class`/`subclass` — вільний текст, на рушій не впливає. На бій впливає лише `archetype` (5 ключів, `hero-archetypes.ts`): `hpPerLevel` і множники ближньої/дальньої/магічної шкоди.
- HP — `getHeroMaxHpBreakdown` (`hero-scaling.ts`), рахується під час збирання учасника, не зберігається.
- Майстерність — `proficiencyForLevel` (`rules/formulas.ts`) від `Character.level`; формула за замовчуванням збігається з 5e.
- Слоти: `Character.spellSlots` (JSON), прогресія раси (`spellSlotProgression`, кола 1–5) або крива повного заклинача до рівня героя 10 (`spell-slots.ts`); у бою `current = max` на старті. Межа кіл 0–5 (а в `createSpellSchema` — 1–5) жорстко записана в Zod-схемах заклинань і рас, формі й закладках книги, `view/hero.ts` (`TIERS`, `slotLevels`), `SlotGrid`, `spellLevelMetal`, CSS `.circle-0…5`, `calculateSpellSlotGain`.
- Здібності раси вливаються в персонажа через `collectCharacterAbilities` (`abilities/build/collect.ts`); ліміти — `perBattle/perRound/perTurn/cooldownRounds/chance`, відпочинків немає.
- Підвищення рівня — `POST …/level-up` (ДМ): +1 рівень, випадкове +1 до характеристики, приріст слотів. Гравець не може змінювати `level` і `archetype` (`patch-character.ts`).
- Раса прив'язана до персонажа за назвою; синхронізація з джерелом видаляє рядки напряму (`sync/apply.ts`), не через сервіс.

### 1. Правила

```ts
classes: { enabled: false }   // HP завжди «середнє» (без кидків)
```

`enabled: false` (default) — HOMM без змін: архетип, HP за формулою HOMM, слоти раси. `enabled: true` — персонаж із непорожнім `classes` рахується від класів: архетип ігнорується (множники 1), HP за кістками, рятівні стартового класу (разом із ручними), слоти за класами. Персонаж із порожнім `classes` і далі рахується по-HOMM-івськи, тож увімкнення не ламає наявних героїв. Вкладка «Класи» на `dm/rules`, рядок у `MECHANIC_REGISTRY`.

### 2. Ресурс контенту `classes`

Модель Prisma `GameClass` (таблиця `classes`, `campaignId`, `sourceId`/`sourceHash`), повний шлях раси: `CONTENT_RESOURCES`, `ContentKind`, роути `collectionRoutes`, кеш довідника (`ReferenceKind`), бандл шаблону (`BUNDLE_TABLES`, `SYNC_TABLE_SCOPES`), синхронізація з джерелом, OpenAPI, MCP — усе автоматично з ресурсу.

```ts
{
  name, icon?, color?,
  hitDie: 6 | 8 | 10 | 12,
  savingThrows: AbilityKey[],                       // 2
  proficiencies: { armor: string[]; weapons: string[]; tools: string[] },   // текст для показу
  skillChoices: { count: number; from: SkillKey[] },  // підказка у формі персонажа
  caster: "none" | "full" | "half" | "third" | "pact",
  spellcastingAbility: AbilityKey | null,
  features: { level: number; abilities: Ability[] }[],          // 1–20
  subclassLevel: number | null,
  subclasses: { id: string; name: string; features: { level: number; abilities: Ability[] }[] }[],
}
```

Підкласи вкладені в клас (менше роутів; синхронізація — цілим записом; id підкласів стабільні, бо синхронізація оновлює наявні рядки). Видалення класу через сервіс відмовляє (409, текст у `api-errors.ts`), якщо його використовує персонаж.

### 3. Персонаж

- Нова колонка `Character.classes Json @default("[]")`: `[{ classId, subclassId?, level }]`; перший запис — стартовий клас (рятівні, максимум кістки на 1-му рівні).
- `Character.level` = сума рівнів класів (сервер підтримує інваріант); від нього, як і зараз, майстерність. Текстові `class`/`subclass` у режимі класів сервер заповнює з назв («Воїн 5 / Чарівник 2») — для показу й AI-контексту.
- `classes` змінює лише ДМ (як `level`/`archetype` у `patch-character.ts`).
- Запис із неіснуючим `classId` (клас видалено синхронізацією) у розрахунках пропускається; форма показує «Клас не знайдено — оберіть інший».
- Міграція (лише розширення): таблиця `classes` + `ENABLE ROW LEVEL SECURITY`, колонка `characters.classes`.

### 4. Похідні характеристики (`lib/utils/characters/classes/`)

Чисті функції, спільні для листа, форми й збирання учасника:
- **HP (середнє):** 1-й рівень стартового класу — максимум кістки + мод. Тіл; кожен наступний рівень (будь-якого класу) — `кістка/2 + 1` + мод. Тіл; мінімум 1 HP за рівень. Нічого не зберігається.
- **Рятівні кидки:** об'єднання `savingThrows` стартового класу і ручних `Character.savingThrows` (риси, предмети).
- **Характеристика заклинань:** `Character.spellcastingAbility`, якщо порожня — першого класу-заклинача. Окремі DC для класів мультикласу — поза етапом.
- **Кістки хітів:** список «Nd{кістка}» за класами — лише показ (витрата — 4d).

### 5. Вміння класу

Нове джерело `AbilitySource.type: "class"` (з `id` класу або підкласу). `collectCharacterAbilities` додає вміння класу з `feature.level ≤ рівень у цьому класі` і підкласу (якщо обраний) поруч із расою; далі як зараз (`resolveAbilities`, `bakePassives`).

`LimitsSchema` отримує `perRest: { rest: "short" | "long"; uses: number }`. До 4d рушій трактує його як `perBattle = uses` (лічильник `abilityUsage` у бою); постійні заряди між боями — разом із відпочинками в 4d. Підказка заряду в UI — «N / відпочинок».

Вміння з вибором (бойовий стиль тощо) — поза етапом: ДМ додає обране як персональне вміння героя, як зараз.

### 6. Слоти за класами (`lib/utils/spells/class-slots.ts`)

`classSpellSlots(classes)` → `{ "1".."9": { max }, pact?: { level, max } }`:
- рівень заклинача = Σ: `full` — рівень, `half` — ⌊рівень/2⌋, `third` — ⌊рівень/3⌋; якщо клас-заклинач один — `half` = ⌈рівень/2⌉ від 2-го рівня, `third` = ⌈рівень/3⌉ від 3-го (таблиці PHB);
- слоти — таблиця мультикласу 5e (рівень заклинача 1–20 → кола 1–9);
- пакт — окремо, таблиця Чаклуна за рівнем у класі `pact`.

У режимі класів (персонаж з класами) старт бою бере слоти з `classSpellSlots` (`current = max`), а не з раси чи `Character.spellSlots`; лист персонажа показує те саме, `Character.spellSlots` оновлюється при зміні класів. Каст заклинання кола N: звичайний слот кола N, якщо немає — слот пакту з колом ≥ N. Вибір слота і підсилення вищим колом — 4c-2.

### 7. Кола 0–9

Межа 0–5 → 0–9 скрізь, де вона жорстко записана (див. розвідку); `createSpellSchema` допускає 0 (кантрипи); `.circle-6…9` у `hud.css`. Обмеження HOMM лишаються даними HOMM: прогресія раси (1–5), крива до рівня героя 10, відкриття кіл майстерністю школи. `SlotGrid` показує лише кола зі слотами. HOMM-контент не має кіл вище 5 — поведінка не змінюється.

### 8. Підвищення рівня

У режимі класів `POST …/level-up` приймає `{ classId, subclassId? }`: новий рівень у наявному класі або новий клас (мультиклас); підклас обов'язковий, коли рівень класу досягає `subclassLevel`, і заборонений раніше. Межа `campaign.maxLevel` — на суму. Випадкове «+1 до характеристики» (HOMM) не застосовується — збільшення характеристик ДМ вносить у листі. Слоти перераховуються з класів.

### 9. UI

- Сторінка ДМ «Класи» (`HudPage`, `HudCard`) і форма класу (`HudForm`): вкладки «Основне» (кістка, рятівні, майстерності, навички на вибір, тип заклинача і характеристика), «Вміння за рівнями» (секція на рівень з `AbilityListEditor`), «Підкласи» (рівень підкласу; на кожен підклас — назва і вміння за рівнями). Пункт меню — коли `rules.classes.enabled`.
- Форма персонажа в режимі класів: замість тексту класу й архетипу — список «клас + підклас + рівень» (ДМ), загальний рівень лише для читання, підказка `skillChoices`, перегляд HP за кістками.
- Підвищення рівня (ДМ): `ResponsiveDialog` з вибором класу (наявний / новий) і підкласу, коли стає доступним.
- Лист персонажа: «Воїн 5 / Чарівник 2», кістки хітів, слоти з пактом окремим рядком.

### 10. Перевірка 4c-1

- Наявні тести — без змін; HOMM (`classes.enabled: false` або персонаж без класів) — HP, слоти, здібності ідентичні; `battle-sweep` на HOMM5.
- Нові тести: `classSpellSlots` (кожен тип одного класу, мультиклас, пакт + повний заклинач), HP (1-й рівень, мультиклас, від'ємний мод. Тіл), рятівні (об'єднання), збирання учасника (вміння за рівнем і підкласом, `perRest` як `perBattle`, невідомий `classId`), level-up (новий клас, підклас на `subclassLevel`, межа рівня), каст слотом пакту, ресурс `classes` (CRUD, 409 при видаленні використаного, бандл і синхронізація), Zod кіл 0–9 і кантрип у `create`, гравець не може змінити `classes`.
- Живий прогін: кампанія з `classes.enabled` → класи Воїн (з підкласом) і Чаклун → персонаж-мультиклас → бій: HP, рятівні, вміння, слот пакту; десктоп + 500 px.

## 4c-2. Дизайн: атаки й заклинання 5e

Розвідка (2026-10-22):
- `BattleAttack.properties` (`types/battle.ts:97`) — вільний рядок, рушій його не читає. Зброя — артефакт: `WeaponStatsSchema` (`lib/utils/artifacts/weapon-stats.ts`) ↔ колонки `bonuses`/`modifiers`; форма `ArtifactWeaponFields`. Юніти — `unitAttackSchema`.
- Шкода героя (`damage/hero-damage.ts`): кубик зброї + кубики героя за рівнем + рівень + мод. (`primaryAbility` або Сил/Спр) + «+N» зброї, × множник архетипу. Атакувальна характеристика — `attackAbilityKey`; фехтувальної немає.
- Крит: шкода залежить лише від ефекту крита (`criticals.effects`: `double_damage`/`max_damage`/`additional_damage`); з вимкненими ефектами крит шкоди не додає. Клієнтське прев'ю (`damage/breakdown.ts:67`) завжди множить ×2 — розходиться із сервером.
- Ближня атака — жорстко ≤ 1 клітинка (`grid/attack-reach.ts`), так само поріг атак при відході (`actions/opportunity.ts:60`). Дальня поруч із ворогом відхиляється; дальність — останнє число `range`.
- «Кілька атак за дію» немає; `actionsPerTurn`/`pendingExtraActions` — цілі додаткові дії (HOMM). Бонусна дія — лише вміння й заклинання; атаки бонусною дією немає. Схоплення/Штовхання (4b) вимагають невитраченої дії.
- Сітка спорядження: `weapon`, `range_weapon`, `shield`; клітинка приймає лише артефакти свого типу (`CharacterArtifactsSection`, `stash-actions.ts`); `extract-attacks` ключ `shield` не читає. Окремої логіки щита в рушії немає — артефакт дає свої `bonuses`.
- Заклинання: одне число `dice`; грані — майстерність школи (герой) або рівень (юніт), кількість росте з рівнем кастера (`spells/model/dice.ts`, `spell/caster-dice.ts` — спільний для сервера й клієнта). Коло заклинання на кубики не впливає. Запит касту не має слота; `spellSlotKey` обирає автоматично (коло N, далі пакт ≥ N). Розв'язка — лише `auto`/`save`, атаки заклинанням немає. Поля визначення зберігаються окремими колонками `spells`.
- На snapshot учасника немає ознаки режиму класів (`resolvedClasses` у `from-character.ts` не зберігається).

### 1. Перемикач режиму

`from-character.ts` ставить `abilities.damageModel = "5e"`, коли персонаж у режимі класів (`resolvedClasses` не порожній). Без поля — HOMM. Рушій перевіряє лише це поле; юніти до 4e лишаються HOMM. Поле проходить `split-participant`/`participant-patch` як решта `abilities`.

### 2. Шкода атаки 5e

У `heroAttackDamageParts`/`heroDamageContext` для `damageModel: "5e"`:
- формула = кубик зброї (або `versatileDice`) + мод. характеристики + «+N» зброї; без кубиків героя, без рівня, без множника архетипу;
- характеристика: ближня — Сил, дальня — Спр, `finesse` — більша з Сил/Спр, метальна (`thrown`) — як ближня;
- бонус атаки — як зараз (мод. + майстерність; майстерність у зброї класу лише текст, тож додається завжди);
- далі той самий ланцюжок (`compute.ts`): здібності, ефект крита, «+N», ослаблення, баланс, опори, укриття.

Ті самі функції живлять прев'ю (`averageAttackDamage`, `weaponPreview`, лист персонажа) і серверні атаки (`server-attack.ts`), тож прев'ю = сервер.

### 3. Криты

`rules.criticals.doubleDice: false` (нове поле секції). `true` — на криті кількість кубиків шкоди подвоюється (кубики зброї й кубики здібностей у формулі; модифікатори — ні). Діє на всі атаки (зброєю й заклинанням), разом з ефектами критів або без них. Default — HOMM без змін. Прев'ю крита (`damage/breakdown.ts`) показує те, що рахує сервер (подвоєні кубики або ефект крита), а не завжди ×2. Перемикач у вкладці «Криты» редактора правил.

### 4. Властивості зброї

`traits: WeaponTrait[]` у `WeaponStatsSchema` (зберігається як новий тип у `modifiers`; `weaponStatsFromRow` його не відкидає) і в `unitAttackSchema`; `BattleAttack.traits` + `versatileDice?`. Текст `properties` лишається приміткою — міграції даних немає. Рушій читає `traits` лише у героя 5e (у юнітів — з 4e).

| Ключ | Дія |
|---|---|
| `light` | дозволяє бій двома зброями |
| `finesse` | атака й шкода від більшої з Сил/Спр |
| `twoHanded` | забороняє атаку другою рукою цього ходу і `versatile` (обмеження «не зі щитом» не застосовується: сітка HOMM тримає лук і щит одночасно, зміна спорядження в бою не моделюється) |
| `versatile` + `versatileDice` | кубик `versatileDice`, коли клітинка «Щит» порожня |
| `reach` | ближня досяжність 2 клітинки: атака (`attackReachError`, `enemiesInReach`) і поріг атак при відході |
| `thrown` | ближня зброя з `range` може атакувати як дальня (без перешкоди «ворог поруч» — це ближня зброя); характеристика як у ближньої; зброя лишається в руці |
| `ammunition` | лише показ (набої не рахуються) |

Дальність `"80/320"` = звичайна/максимальна: у 5e за звичайною — перешкода (нова причина в `rollModeReasons`), за максимальною — відмова. Дальня атака з ворогом поруч у 5e — перешкода, а не відмова. HOMM: як зараз (останнє число, відмова поруч з ворогом).

### 5. Додаткова атака

Новий стат `attacksPerAction` у `DYNAMIC_STATS` (`modifyStat`, flat): вміння класу «Додаткова атака» дає +1 (Воїн 11 — +2). Відмінний від `actionsPerTurn`: додаткова дія від `actionsPerTurn` дає нову дію «Атака» з повним набором атак.
- Перша атака дією витрачає дію і пише `battleData.attacksLeft = attacksPerAction` (кількість атак, що лишилися; 0 — поле не пишеться).
- Наступний запит атаки при `attacksLeft > 0` бере атаку з лічильника, а не дію (`validateAttackRequest`/`applyMainActionUsed`); кожна атака — своя ціль і зброя.
- Схоплення й Штовхання (4b) при `attacksLeft > 0` теж беруть атаку з лічильника.
- `attacksLeft` скидається в `turn/turn-state.ts`; дія лишається витраченою, навіть якщо атаки не використано.
- Атаки поза ходом (атака при відході, підготовлена, відплата) — завжди одна, лічильник не чіпають.
- Автозавершення ходу (`view/turn-exhausted.ts`) не спрацьовує, поки `attacksLeft > 0`.

### 6. Бій двома зброями

Лише герой 5e:
- Клітинка «Щит» у режимі класів приймає й артефакти типу WEAPON з `light` (сітка `CharacterArtifactsSection`, «Вдягнути» зі сховища, серверна перевірка вдягання). `extract-attacks` читає ключ `shield`: зброя там → атака з `hand: "off"`; у HOMM нічого не змінюється (такий артефакт туди не вдягнеш).
- Запит атаки отримує `offHand: true`: витрачається бонусна дія. Умови: цього ходу була атака дією «Атака» легкою ближньою зброєю основної руки (`battleData.attackedWithLight`), зброя другої руки легка, ні основна, ні друга не `twoHanded`.
- Шкода другої руки: додатний модифікатор не додається, від'ємний — додається; прапорець `twoWeaponFighting` (бойовий стиль) повертає модифікатор.
- Атака другою рукою не дає Додаткової атаки. Редакція 2024 (майстерність зброї, Nick) — поза етапом.

### 7. Заклинання 5e

Нові колонки `spells` (міграція `20261028000000_spell_5e_dice`, лише розширення), поля `SpellDefinitionSchema`, усі необов'язкові й ігноровані в HOMM:
- `dieSides?: 4 | 6 | 8 | 10 | 12` — грань у 5e (порожньо — d6);
- `upcastDice?: number` — +N кубиків за кожне коло понад базове;
- `upcastTargets?: number` — +N до `maxTargets` за коло;
- `addAbilityMod?: boolean` — додати мод. характеристики заклинань до шкоди/лікування;
- межа `SpellDiceSchema` 20 → 40.

OpenAPI/MCP/бандл отримують поля автоматично; ручне відображення (`resources/spells.ts` update, `readSpellDefinition`/`spellDefinitionColumns`, `BOOK_SPELL_SELECT`, `toBookSpell`, `SpellRules`) дописується.

Кубики (`casterSpellDice(caster, spell, castLevel)`, гілка для `damageModel: "5e"`):
- кантрип: `dice × (1 + [рів ≥ 5] + [рів ≥ 11] + [рів ≥ 17])`, рівень = `abilities.level` (сума класів);
- коло ≥ 1: `dice + upcastDice × (castLevel − level)`;
- грань `dieSides ?? 6`; майстерність школи й рівень кастера не впливають.
HOMM-гілка `spellDice` без змін.

Вибір слота: запит касту (`cast-spell-schema.ts`, `SpellCastData`) отримує `slotKey?` («1»…«9» | «pact»). Сервер перевіряє: слот існує, не порожній, його коло (`slotLevel`) ≥ коло заклинання; `castLevel = slotLevel`. Без `slotKey` — автовибір `spellSlotKey`, як зараз (HOMM, юніти, DM-каст). `actionDetails.spellSlotUsed`/`spellLevel` і тригер `spellCast` отримують фактичне коло касту. Кількість цілей = `maxTargets + upcastTargets × (castLevel − level)`.

Атака заклинанням: `SpellResolutionSchema` + `{ kind: "attack" }` (цілі `enemy`/`area`). Кидок d20 + мод. характеристики заклинань + майстерність (або `spellAttackBonus`, якщо заданий) проти КЗ кожної цілі; перевага/перешкода — через `rollModeReasons` (стани, дальність, ворог поруч); промах — без шкоди й ефектів; крит — подвоєні кубики при `doubleDice`. d20 кидає клієнт (preset, як в атаці зброєю) або сервер. HOMM-контент такої розв'язки не має.

До 4e лишаються HOMM-івськими: закляття юнітів, множник архетипу (у режимі класів = 1), бонуси здібностей у `computeSpellPower`.

### 9. Перевірка 4c-2

## 4d. Дизайн: поза боєм

Розвідка (2026-10-22):

### 1. Правила

```ts
outOfCombat: {
  persistResources: false,           // HP, тимч. HP, слоти, пакт, заряди perRest, виснаження живуть між боями
  longRestHitDice: "half",           // "half" (2014) | "all" (2024)
  xp: false,                         // false — віхи (як зараз), true — таблиця досвіду 5e
  inspiration: false,
}
```

Вкладка «Поза боєм» на `dm/rules`, рядок у `MECHANIC_REGISTRY`, хеш синхронізації шаблону. Усе вимкнено за замовчуванням — HOMM5 і наявні кампанії без змін. Перемикачі не залежать від `classes.enabled` (HOMM-кампанія може ввімкнути збереження ресурсів; кістки хітів тоді просто відсутні). Шаблон SRD (4f) вмикає все.

### 2. Дані

Міграція (лише розширення):
- `characters.resources Json @default("{}")`, `characters.inspiration Boolean @default(false)`;
- таблиця `character_logs` (`id`, `campaignId`, `characterId`, `actorUserId?`, `kind`, `data Json`, `createdAt`; індекс `(characterId, createdAt)`; `ENABLE ROW LEVEL SECURITY`; каскад від кампанії й персонажа).

`resources` зберігає **витрачене**, а не поточне, тож підвищення рівня чи зміна класу нічого не перераховує (`lib/utils/characters/resources/schema.ts`):

  tempHp?: number;
  dead?: boolean;
  slotsSpent?: Record<"1".."9" | "pact", number>;

### 3. Бій ↔ ресурси (лише коли `persistResources`)

Чиста логіка — `lib/utils/characters/resources/battle.ts`; рушій читає `battle.rules` (заморожена копія).

**Старт бою** (`createBattleParticipantFromCharacter`, коли персонаж має `resources`):
- `currentHp = clamp(resources.hp ?? max, 0, max)`, `tempHp = resources.tempHp ?? 0`; `hp = 0` → учасник стартує непритомним (з кидками смерті, якщо вони ввімкнені), `dead` → мертвим;
- слоти: `current = max(0, max − slotsSpent[k])` (і для класів, і для збережених слотів);
- `abilityUsage[key].battle = charges[key]` для вмінь з `perRest`;
- виснаження `N > 0` → ефект `exhaustion` рівня N через `applyCondition` (з урізанням HP для 2024, як у 4a);
- `battleData.inspiration = Character.inspiration` (коли `inspiration` увімкнено, незалежно від `persistResources`).

**Завершення бою** (`saveBattle`, гілка `completing`, у тій самій транзакції): для кожного учасника з `characterId`, що був на мапі (не резерв), рахується `applyBattleResult(resources, participant)` → `hp`, `tempHp`, `dead`, `slotsSpent = max − current`, `charges` для `perRest`, `exhaustion = exhaustionLevel`; `shortRestOpen` скидається. Інші стани й концентрація не переносяться. Пишеться `Character.resources` (+ `inspiration`, якщо увімкнено) і запис журналу `battle_result` (HP до/після, витрачені слоти). Юніти й призвані — ні. Видалений бій без завершення — нічого не пише.

**Перемога**: зараз `completeBattle` повертає непритомних союзників до max HP. При `persistResources` — до **1 HP** (у 5e стабілізований герой приходить до тями з 1 HP); `completeBattle` отримує `rules`. Мертві (`dead`) лишаються мертвими, доки ДМ не змінить стан у листі.

### 4. Відпочинки (`lib/utils/characters/resources/rest.ts`, роут `POST /api/campaigns/[id]/rest`, ДМ)

Тіло: `{ kind: "short" | "long" | "close", characterIds: string[] }`. Доступно лише при `persistResources`; персонажі мають бути в кампанії й не `PENDING`. Відповідь — оновлені `resources` героїв.

- **Короткий**: слоти пакту → повні; заряди `perRest.rest = "short"` → 0; `shortRestOpen = true`.
- **Довгий** (мертві пропускаються): `hp` → повне, `tempHp` → 0; усі слоти й пакт; усі заряди `perRest`; кістки хітів: повертається ⌊загальний рівень / 2⌋ (мінімум 1) або всі (`longRestHitDice: "all"`), починаючи з найбільших кісток; виснаження −1; `shortRestOpen = false`.
- **`close`**: `shortRestOpen = false` (кнопка «Завершити відпочинок»). Старт бою з цим героєм теж закриває вікно (у записі після бою).

Кожна дія — запис журналу кожному герою.

### 5. Кістки хітів (`POST /api/campaigns/[id]/characters/[characterId]/hit-dice`, власник або ДМ)

Тіло `{ classId }`. Умови: `persistResources`, персонаж у режимі класів, `shortRestOpen`, не мертвий, у класі є невитрачені кістки. Сервер кидає `d{hitDie} + мод. Тіл` (мінімум 0), додає до HP (до max), `hitDiceSpent[classId] += 1`, журнал `hit_die`. Помилки — 409 з текстами з `api-errors.ts`.

### 6. Кидки з листа (`POST …/characters/[characterId]/roll`, власник або ДМ)

Тіло `{ kind: "check", skill } | { kind: "check", ability } | { kind: "save", ability }` + `useInspiration?: boolean`. Сервер будує учасника тим самим шляхом, що й лист (`buildSheetFor`, з ресурсами — тож виснаження діє), і викликає `rollCheck` / `rollSave` (без DC: `success` не показується). `useInspiration` (коли натхнення увімкнене й є) додає перевагу і знімає натхнення. Відповідь `{ rolls, mod, total, mode }`; клієнт показує результат і анімацію 3D-кубиків (`useDiceRoller` з готовими значеннями). Журнал `check`/`save`.

### 7. Досвід (`rules.outOfCombat.xp`)

- Таблиця порогів 5e (рівні 2–20) — `lib/constants/experience.ts`; `xpForLevel`, `levelUpAvailable(character, maxLevel)`.
- `POST /api/campaigns/[id]/experience` (ДМ): `{ characterIds, amount, split: boolean, note? }` — кожному `amount` або `⌊amount / n⌋`; журнал `xp`. Від'ємна сума дозволена (виправлення), досвід не нижче 0.
- Підвищення рівня як і раніше робить ДМ наявним діалогом; лист показує «Досвід X / поріг» і «Доступне підвищення рівня», список персонажів ДМ — значок.
- Автоматичний досвід за переможених — 4e (CR → XP).

### 8. Натхнення (`rules.outOfCombat.inspiration`)

- `POST …/characters/[characterId]/inspiration` (ДМ): `{ value: boolean }`; журнал `inspiration`.
- Витрата: кидок з листа (`useInspiration`) і атака в бою: поле `useInspiration` у запиті атаки → причина переваги в `rollModeReasons` (і в прев'ю клієнта, щоб кидок d20 ішов з перевагою), сервер знімає `battleData.inspiration`; після бою значення пишеться в `Character.inspiration`. Рятівні кидки в бою кидає той, хто накладає ефект, — натхнення там не застосовується.

### 9. ДМ: правка ресурсів (`PATCH …/characters/[characterId]/resources`, ДМ)

`{ hp?, tempHp?, exhaustion?, dead?, reset?: true }` — ручне лікування, воскресіння, зняття виснаження, «повністю відновити»; журнал `resources_edit`. `GET …/characters/[characterId]/log?cursor=` (власник або ДМ) — журнал сторінками по 30.

### 10. UI

- **Лист персонажа** (`components/character-profile/`): у `ProfileHero` — HP поточні / max і тимчасові, виснаження, натхнення (значок), досвід із порогом; кістки хітів «витрачено / усього» з кнопкою «Витратити» на клас (лише у вікні короткого відпочинку); у вкладці «Бій» рятівні кидки й навички — кнопки кидка (діалог з перемикачем «Натхнення» і результатом); у «Магії» слоти й пакт — поточні / max; заряди `perRest` у вкладці «Вміння» — «N / відпочинок»; нова вкладка «Журнал».
- **ДМ, сторінка персонажів**: кнопки «Відпочинок» (діалог: короткий/довгий, вибір героїв, за замовчуванням усі схвалені герої) і «Завершити відпочинок», коли є відкрите вікно; «Досвід» (діалог: герої, сума, поділити); у картці героя — HP, значок «рівень доступний», натхнення.
- **ДМ, лист героя**: «Ресурси» (діалог правки §9), перемикач натхнення.
- **Бій**: перемикач «Натхнення» в діалозі атаки, коли воно є.
- Хуки в `lib/hooks/characters/` (`useRest`, `useSpendHitDie`, `useSheetRoll`, `useAwardXp`, `useInspiration`, `useEditResources`, `useCharacterLog`), клієнт у `lib/api/characters.ts`; мутації інвалідують `characterKeys.sheet`, список персонажів і журнал.

### 11. Поза обсягом 4d

Відновлення слотів уміннями класу (Arcane Recovery тощо — ДМ правкою ресурсів); ритуали; тривалість відпочинку й переривання; кидки поза боєм для юнітів; MCP/OpenAPI для відпочинків (етап 6); realtime оновлення листа.

### 12. Перевірка 4d

- Наявні тести — без змін (`persistResources: false` — старт бою з повними ресурсами, `completeBattle` — max HP); `battle-sweep` на HOMM5.
- Нові тести: схема й чисті функції ресурсів (короткий/довгий, кістки хітів half/all з різними кістками, мертвий пропускається, виснаження −1), старт бою з ресурсів (HP, 0 HP → непритомний, слоти, пакт, заряди, виснаження), `applyBattleResult` (резерв не пишеться, юніти ні, `shortRestOpen` скидається), перемога → 1 HP при `persistResources`, роути (права власник/ДМ/чужий гравець, 409 поза вікном, `persistResources` вимкнено → 409), кидок з листа з натхненням і виснаженням, досвід (поділ, не нижче 0, `levelUpAvailable`), натхнення в атаці (перевага й зняття), журнал (сторінки), Zod правил і міграція з RLS; компонентні — діалог відпочинку, кнопка кістки хітів.
- Живий прогін (десктоп): кампанія з класами й усіма перемикачами «Поза боєм» → бій (витратити слот, вміння `perRest`, отримати шкоду) → після бою лист показує залишок → короткий відпочинок → гравець витрачає кістку хітів → довгий → усе відновлено; кидок навички з натхненням; досвід до порогу → значок і level-up. Тестові дані видаляються.
- Документи: `battle.md` («5e: поза боєм»), `abilities.md` (`perRest` між боями), STATUS, хендоф, пам'ять.

## 4e. Дизайн: монстри й баланс 5e

Розвідка (2026-10-22):
- `Unit` має `level` (тір HOMM 1–7), `proficiencyBonus`, `attacks[]` (варіанти атаки), `abilities`; CR, XP, рятівних кидків, легендарного нічого немає. Бібліотека HOMM сіє `level = tier`, `proficiencyBonus = proficiencyForTier`.
- `createBattleParticipantFromUnit` не ставить `damageModel`, тож юніти завжди йдуть HOMM-шляхом шкоди; СК юніта = `saveDcBase + prof + level` (у `balance/stats.ts` — без тіру: розбіжність).
- Додаткові атаки — стат `attacksPerAction` (4c-2), лічильник `attacks-left.ts`. Атака поза ходом — патерн `readiedAttack` (`requireActor(…, { anyTurn })`).
- `rollSave` чистий; викликається в `spell/cast/outcome.ts`, `concentration`, `save-ends`, `grapple`, `fire-burst`, листі. Легендарного опору немає.
- Тригер вмінь `roundStart` уже є (ініціатива 20 ≈ початок раунду).
- Баланс — лише `computeFairScaling` у трьох місцях: `setupFairScaling` (UI), `balance-post` (автопідбір), `scaleEnemiesForFairBattle` (старт).
- Завершення бою: `saveBattle` (гілка `completing`) уже викликає `persistCharacterResources` (4d); досвід — `xpShare`/`addExperience`/`lockCharacters` і журнал `xp` з 4d.

Рішення користувача (2026-10-22): обидві редакції 5e (2014 і 2024) перемикачем у правилах. Решта — рішення сесії за дорученням користувача (див. нижче), HOMM5 без змін.

### 1. Правила

```ts
encounters: {
  balance: "fair",       // "fair" — computeFairScaling (HOMM, як зараз); "xp" — бюджет XP 5e без масштабування
  edition: "2014",       // "2014" | "2024": пороги складності й множник кількості
  autoXp: false,         // після перемоги XP переможених ділиться між героями (потрібне outOfCombat.xp)
}
```

Вкладка «Зустрічі» на `dm/rules`, рядок у `MECHANIC_REGISTRY`, хеш синхронізації шаблону. Default — поведінка HOMM5.

### 2. Юніт: поля 5e

Міграція (лише розширення) у `units`:
- `cr Float?` — 0, 0.125, 0.25, 0.5, 1…30; `null` — юніт HOMM (усе як зараз);
- `xp Int?` — ручне перевизначення; інакше з таблиці CR;
- `multiattack Int @default(1)`;
- `legendaryActions Int @default(0)`, `legendaryResistances Int @default(0)`;
- `saveProficiencies Json @default("[]")` — ключі характеристик.

Таблиці (`lib/constants/challenge.ts`): CR → XP і CR → майстерність (однакові у 2014 і 2024), підпис CR («1/8»). Поля проходять весь шлях ресурсу `units`: Zod create/update/import, `resources/units.ts`, `toUnit`, `types/units.ts`, `unit-form.ts`, бандл/синхронізація (автоматично з DMMF), OpenAPI (оновити `app/api/openapi.json`), MCP (зі схеми).

**Юніт з `cr` (монстр 5e)** у `createBattleParticipantFromUnit`:
- майстерність = таблиця CR (якщо `proficiencyBonus` не задано явно інакше — форма підставляє значення з CR при виборі CR, ДМ може змінити);
- `abilities.damageModel = "5e"` — шкода зброї й заклинань іде шляхом 4c-2 (кубик + модифікатор, властивості `traits`);
- СК = `saveDcBase + prof + найбільший мод. Інт/Мдр/Хар` (без тіру); `balance/stats.ts` рахує так само для юнітів з `cr`;
- `saveProficiencies` у snapshot (їх читає `rollSave`, 4a);
- мультиатака: `multiattack > 1` → синтетичне пасивне вміння `modifyStat attacksPerAction flat (multiattack − 1)` (рушій читає лише через `collectModifiers`);
- `battleData.legendary = { actions, actionsLeft, resistLeft }`, коли поля > 0;
- `xp` у `basicInfo` для авто-досвіду й балансу.

Юніт без `cr` — нульова зміна (тест на весь snapshot HOMM-юніта).

### 3. Легендарні дії

- Новий базовий вид дії `legendary` у роуті `core-action` (`anyTurn`, лише ДМ): `{ action: "legendary", actorId, option: { kind: "attack", attackIndex, targetIds } | { kind: "ability", abilityId, targetIds? } }`.
- Умови: у учасника `legendary.actionsLeft ≥ вартість`, зараз **не** його хід, він дієздатний (не `incapacitated`). Атака коштує 1 і йде через `resolveServerAttack` (як підготовлена атака, одна атака без мультиатаки); вміння — нове обмеження `limits.legendaryCost: 1–3`: таке вміння використовується лише як легендарна дія (у звичайному ході прихована).
- `actionsLeft` відновлюється на початку ходу цього учасника (`processStartOfTurn`).
- UI: у панелі ДМ на картці учасника з `legendary` — кнопка «Легендарна дія (N/M)» → `ResponsiveDialog` з вибором атаки/вміння і цілей (перевикористати вибір цілей діалогу базових дій 4b).

### 4. Легендарний опір

Автоматичний: коли учасник з `legendary.resistLeft > 0` провалює рятівний кидок, провал стає успіхом, `resistLeft − 1`, у лозі «Легендарний опір (N залишилось)». Один помічник `resolveSave(participant, saveResult)` → `{ result, participant }` — викликається там, де результат `rollSave` змінює стан учасника (`spell/cast/outcome.ts`, `concentration`, `save-ends`, `grapple`, `fire-burst`). Лист персонажа не зачіпає (юніти там не кидають). Однаково для 2014 і 2024.

### 5. Дії лігва

Без нового механізму: дія лігва — вміння юніта з тригером `roundStart` (початок раунду ≈ ініціатива 20) і `perRound: 1`. Редактор вмінь показує для тригера `roundStart` підказку «дія лігва»; опис у `abilities.md`.

### 6. Баланс за бюджетом XP (`encounters.balance: "xp"`)

Чистий модуль `lib/utils/battle/balance/xp-budget.ts`, спільний для UI й сервера:
- **2014:** пороги героя за рівнем (легкий / середній / складний / смертельний, DMG), сума по групі; XP ворогів × множник кількості (1 → ×1, 2 → ×1.5, 3–6 → ×2, 7–10 → ×2.5, 11–14 → ×3, 15+ → ×4; група < 3 — крок вгору, ≥ 6 — крок вниз); складність — найвищий досягнутий поріг.
- **2024:** бюджет героя за рівнем (низька / помірна / висока), сума по групі; XP ворогів без множника.
- Результат: `{ edition, enemyXp, adjustedXp, thresholds, difficulty, missingCr: unitIds[] }`.

У режимі `xp`:
- підготовка бою показує складність і XP (`BalanceSummary` має другий вигляд), без множників HP/шкоди; юніти без CR — попередження «немає CR, не враховано»;
- старт бою не масштабує ворогів (множники 1); `scaleEnemiesForFairBattle` не викликається;
- автопідбір (`balance-post`) отримує цільову складність (чипи в UI, default — середня/помірна) і набирає юнітів з CR до порогу.

`fair` — без змін (`computeFairScaling`). Правило `balance.md` «setup і старт рахують однаково» зберігається в обох режимах.

### 7. Авто-досвід (`encounters.autoXp` і `outOfCombat.xp`)

У `saveBattle` (гілка `completing`, та сама транзакція, після `persistCharacterResources`) при **перемозі**: сума `xp` ворогів (`originalSide` — вороги, статус мертвий/непритомний; без призваних `summonedBy`, без слотів додаткового ходу), ділиться порівну (`xpShare`, `split`) між героями-персонажами, що були в бою (на мапі, не резерв, живі чи ні); `addExperience` з блокуванням рядків (`lockCharacters`); журнал `xp` з `battleId`. У лозі бою — рядок «Досвід: N кожному». Повторне завершення (відкат) — той самий захист, що в 4d (запис лише при переході в COMPLETED).

### 8. UI

- Форма юніта: блок «5e» (коли `classes.enabled` або `encounters.balance = "xp"`): CR (select з дробами), XP (підставляється з CR, можна змінити), майстерність з CR, мультиатака, легендарні дії й опір, рятівні кидки (чекбокси).
- Список юнітів: чип «CR 1/2» біля назви, коли є CR.
- Картка учасника в бою: «Леґ. дії N/M», «Леґ. опір N».
- Редактор правил: вкладка «Зустрічі».

### 9. Поза обсягом 4e

Регіональні ефекти лігва; «легендарні дії на кінці чужого ходу» строго (дозволено будь-коли поза своїм ходом); мультиатака з різними атаками за схемою («2 кігті + укус» — ДМ обирає атаку на кожен удар із лічильника); монстри-заклинателі з окремими слотами; навички монстрів; редакція 2024 для інших механік, крім балансу.

### 10. Перевірка 4e

- Наявні тести — без змін (юніт без `cr`, `balance: "fair"`); `battle-sweep` на HOMM5.
- Нові тести: таблиці CR (XP, майстерність, дроби), snapshot юніта з CR (damageModel, СК, рятівні, мультиатака як вміння, legendary), шкода монстра 5e, легендарна дія (атака, вміння з `legendaryCost`, бюджет, свій хід — відмова, гравець — 403, відновлення на початку ходу), легендарний опір (провал → успіх у кожному з викликів, лічильник, лог), `xp-budget` 2014 (множники, розмір групи) і 2024, режим `xp` у setup/старті/автопідборі, авто-досвід (вороги, призвані виключені, поділ, лише перемога, вимкнено — нічого), Zod юніта й міграція.

## 4f-0. Дизайн: імпорт контенту

Рішення користувача (2026-10-22): більшість потенційних клієнтів уже користуються іншими сервісами — перенесення має бути максимально простим. Імпорт CSV для всіх типів контенту, приклад CSV для завантаження і інструмент, що перетворює довільний CSV у наш формат. Дизайн погоджено в чаті: один майстер з мапінгом колонок + приклад/експорт CSV + опційний AI-мапінг; частина стоїть перед 4f, і шаблон SRD заливається цим імпортером.

Розвідка (2026-10-22):

Вади: самописний парсер (`lib/utils/common/file-import.ts`) ламає клітинки з переносами, не знімає BOM, роздільник жорстко `;`; наявні назви пропускаються, а не оновлюються; одна погана стрічка — 400 на весь файл; рятівні кидки, поля 5e, імунітети, мораль, справжні вміння не імпортуються. З 6 CSV у `docs/units` через UI проходить один.
- Інші 9 ресурсів (`CONTENT_RESOURCES`: races, classes, spells, spell-groups, main-skills, skills, artifacts, artifact-sets, tracks) і дерева скілів — лише створення по одному (UI, REST, MCP `content_create`) або бандл усієї кампанії при створенні нової.
- Прикладів для завантаження й експорту CSV немає. `csv-parse` є лише в devDependencies і ніде не використовується.
- Є: `ImportDialog`/`useFileImport` (простий), `content_schema` (JSON Schema кожного типу), AI ДМ `pickDmTextModel` + `generateObject` (зразок — `generate-backstory.ts`), `ConversionIssue` для попереджень, текстова мова атак юнітів (`unit-parsing.ts`), перетворення тексту в вміння-нотатки (`special-abilities.ts`).

### 1. Реєстр полів імпорту (`lib/utils/content/import/fields/`)

Для кожного типу — список полів, спільний для клієнта й сервера (без `server-only`):

```ts
type ImportField = {
  key: string;                 // шлях у тілі create (напр. "armorClass", "basicInfo.name")
  label: string;               // українська назва колонки в прикладі
  aliases: string[];           // синоніми заголовків (укр/англ, регістр і пробіли ігноруються)
  type: "string" | "int" | "number" | "bool" | "enum" | "list" | "dice" | "cr"
      | "ref" | "refList" | "json" | "attacks" | "abilitiesText";
  enumValues?: readonly string[];      // значення й укр. підписи приймаються
  ref?: ContentKind;                   // "ref"/"refList": назва → id у кампанії
  required?: boolean;
  example: string;                     // значення для прикладу CSV
};
```

Типи: `list` — роздільники `,` `;` `|`; `dice` — «1к6+2», «2d8 + STR»; `cr` — «1/4», «0.25», «5»; `bool` — так/ні/true/false/1/0/+; `attacks` — наявна текстова мова юнітів або JSON; `abilitiesText` — текст стає вміннями-нотатками (як зараз), JSON-масив — справжніми вміннями (Zod `AbilitiesSchema`); `json` — JSON у клітинці (вкладені поля: `features`/`subclasses` класу, `targeting`/`resolution`/`spellEffects` заклинання, `weapon` артефакта).

Покриття: units (з полями 5e, рятівними, імунітетами, моралю, цілями; синоніми — усі заголовки нинішнього CSV-імпорту, тож старі файли працюють), spells, skills, main-skills, spell-groups, races, classes, artifacts, artifact-sets. Дерева скілів — лише JSON (одне дерево на расу, `save_skill_tree`). Треки — поза обсягом (файли).

### 2. Перетворення й перевірка (`lib/utils/content/import/`)

- `parseTable(text)` — `csv-parse` (перенести в dependencies; браузерна збірка): автороздільник (`,` `;` `\t`), BOM, лапки з переносами, порожні рядки; JSON-файл — масив об'єктів або один об'єкт.
- `autoMap(headers, fields)` → `{ [header]: fieldKey | null }` за синонімами; ручний мапінг поверх.
- `transformRow(row, mapping, fields)` → `{ value, issues }` — значення в тіло create; посилання лишаються назвами (розв'язує сервер).
- Сервер: `importContent(actor, kind, { rows, mode, dryRun })` у `lib/server/content/import.ts` через сервіс ресурсу (`assertCan`, `CONTENT_RESOURCES`): посилання за назвою (без урахування регістру) у межах кампанії; Zod create/update ресурсу на кожен рядок; режим `create` (дубль назви — помилка рядка) / `update` (за назвою: оновити, інакше створити) / `skip` (наявні пропустити); валідні рядки пишуться в одній транзакції, невалідні — у звіті. Відповідь: `{ results: { row, status: "created" | "updated" | "skipped" | "error", name?, issues[] }[], counts }`. `dryRun` — та сама перевірка без запису (крок попереднього перегляду). Ліміт — 500 рядків за запит (клієнт ділить файл на частини). Кеш довідника інвалідовується як при звичайному записі.

### 3. API

- `POST /api/campaigns/[id]/content-import/[kind]` — тіло `{ rows, mode, dryRun? }`; операція `<kind>.import` у `CONTENT_OPERATIONS` (OpenAPI), права `content:write`. Наявний `POST /units/import` лишається сумісним (делегує в новий шлях, мапінг — нинішні синоніми).
- `GET /api/campaigns/[id]/content-import/[kind]/example.csv` — приклад: заголовки (`label`) і 2–3 рядки (`example`).
- `GET /api/campaigns/[id]/content-export/[kind].csv` — експорт кампанії в тому самому форматі (посилання — назви, вкладене — JSON у клітинці), тож «вивантажив → змінив → завантажив» працює; `content:read`.
- MCP: інструмент `content_import(kind, rows, mode, dryRun)` (рядок в `AI_TOOLS`, scope `content:write`), щоб зовнішній агент переносив дані сам.

### 4. AI-мапінг (опційно)

`POST /api/campaigns/[id]/content-import/[kind]/ai-map` (ДМ, з ключем AI): тіло `{ headers, sample }` (≤ 5 рядків, обрізані клітинки) → `generateObject` з Zod-схемою відповіді `{ mapping: { [header]: fieldKey | null }, notes: string[] }` (fieldKey — лише з реєстру; інше відкидається). Шаблон — `generate-backstory.ts`: охорона, rate limit, `pickDmTextModel`, `aiErrorMessage`; ключ не залишає сервер. Результат лише заповнює крок мапінгу — ДМ бачить і змінює. Без ключа кнопка прихована.

### 5. UI

Спільний майстер `ContentImportWizard` (`components/content-import/`, `ResponsiveDialog hud`), хуки в `lib/hooks/content-import/`, клієнт у `lib/api/content-import.ts`:
1. **Файл** — CSV/TSV/JSON (XLSX — підказка «збережіть як CSV»); посилання «Завантажити приклад CSV».
2. **Колонки** — таблиця «колонка файлу → поле» (select з полями типу, «пропустити»), автозбіг, кнопка «Підказати AI»; обов'язкові незіставлені поля підсвічуються. Мапінг запам'ятовується в `localStorage` за набором заголовків.
3. **Перегляд** — `dryRun`: перші 50 рядків, статуси й помилки по рядках, лічильники; режим (створити / оновити за назвою / пропустити наявні).
4. **Імпорт** — запис частинами, підсумок, «Завантажити звіт помилок CSV».

Кнопки «Імпорт» і «Експорт CSV» — на сторінках бібліотеки ДМ кожного типу (юніти — замість `UnitImportDialog`), а також на шаблоні.

## Ризики

- **Перетин з HOMM-контролем.** `charm` (HOMM, перехід на бік) ≠ `charmed` (5e). Різні ключі й підписи; редактор показує 5e-стани окремою групою.
- **Розмір snapshot.** Стан додає один `ActiveEffect` з кількома прапорцями; на egress це не впливає помітно (дельти).
- **Клієнтські кидки.** Перевага на рятівному кидку з `presetRoll` — другий кубик кидає сервер; майстер заклинання показує режим кидка до підтвердження (через ту саму `rollSave`-логіку режиму, спільну для клієнта й сервера).
- **Концентрація на чужих ефектах.** Знімання за `concentrationOf` має проходити всіх учасників і зони за один прохід; тест на кілька цілей + зону обов'язковий.
