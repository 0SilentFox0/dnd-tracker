# Конструктор кампаній — етап 4: механіки D&D 5e (дизайн)

## Context

Мета епіку уточнена користувачем 2026-10-22: будь-хто, хто грає в D&D 5e, має перенести свою кампанію в трекер **за всіма правилами**, так само як HOMM5 працює зараз. Епік вважається завершеним, коли є два повноцінні режими — HOMM5 і 5e. **Warhammer (етап 5) переноситься на після MVP.** Злиття `feat/constructor` у `main` і prod — після етапів 1–4 і 6.

Розвідка (стан коду на 2026-10-22):
- **Стани.** `applyCondition` пише `ActiveEffect` з `type: "condition"` і маркером у `effects`. Ключі (`CONDITION_KEYS`) механічні — `skip_action`, `immobilized`, `no_reaction`, `no_bonus_action`, `disable_*` — і рушій читає їх через `hasEffectMarker`. 5e-станів немає. `charm` і `berserk` — HOMM-контроль, а не 5e «зачарований». `ActiveEffect.abilityEffects: StaticEffect[]` уже читає `collectModifiers` (`collect-modifiers.ts:186`).
- **Перевага й перешкода** є тільки на атаках (`attack/bonus.ts`: `rollModeReasons`, прапорці `advantage`/`disadvantage`/`…ForAttackers`). `rollSavingThrow` (`spell/power.ts:24`) = d20 + модифікатор, без майстерності, переваги й автопровалу.
- **Рятівні кидки.** `Character.savingThrows` (`Record<ability, boolean>`) тільки показуються. Рятівні кидки кидають заклинання (`spell/cast/outcome.ts`) і `maneuvers/fire-burst.ts`; клієнт може передати готовий кидок (`saveRolls`).
- **0 HP.** `applyDamageToTarget` → `unconscious` (HP 0) / `dead` (HP < 0). Кидків смерті немає; союзники встають після перемоги (`turn/victory.ts`).
- **Концентрації немає.**
- **Класи.** `Character.class` — вільний текст для показу. На рушій впливає лише `archetype` (5 ключів у коді). Слоти — саморобна таблиця або крива повного заклинача 5e до 10 рівня; рівні заклинань 0–5.
- Правила кампанії: `RulesetSchema` (секції з default = поточна поведінка) + `MECHANIC_REGISTRY`; рушій читає зафіксовану копію `battle.rules`; `Ruleset` уже передається в початок ходу (`turn/start-end.ts`).

## Загальні правила етапу 4

- **Нульова зміна HOMM5.** Нові секції `rules` мають default «вимкнено» або «як зараз»; нові ключі станів і прапорців не використовуються в HOMM-контенті. Усі наявні тести рушія проходять без змін.
- Механіки — каталог у коді (`MECHANIC_REGISTRY`, реєстр станів); кампанія вмикає й налаштовує їх у `rules`. Рушій бою читає тільки `battle.rules`.
- Нові бонуси й прапорці читаються лише через `collectModifiers`/`runAbilities`, як вимагає `abilities.md`.
- Міграції лише розширюють схему. 4a міграцій не потребує (усе в JSON: `rules`, snapshot, `Spell.definition`).

## 4a. Дизайн

### 1. Правила (`lib/utils/rules/schema.ts`)

Нові секції `RulesetSchema` (і `RulesetPatchSchema`, `MECHANIC_REGISTRY`, вкладки на `dm/rules`):

```ts
saves:         { proficiency: false }                       // майстерність з Character.savingThrows
deathSaves:    { enabled: false, unitsDieAtZero: true }     // кидки смерті героїв; юніти при 0 HP помирають
concentration: { enabled: false, dcCap: null }              // null — 2014 (без межі), 30 — 2024
conditions:    { enabled: false, exhaustion: "2014" }       // меню станів ДМ і група 5e в редакторі; "2014" | "2024" — таблиця виснаження
```

Default кожної секції відтворює поточну поведінку. Перевага/перешкода й автопровал рятівних кидків не мають перемикача: вони походять лише з даних (стани 5e, прапорці), яких у HOMM-контенті немає.

### 2. Стани 5e

`lib/utils/battle/conditions/` — реєстр `CONDITION_5E_REGISTRY` (`satisfies Record<Condition5eKey, Condition5eDef>`):

```ts
type Condition5eDef = {
  label: string;               // українська назва
  description: string;
  markers: ConditionKey[];     // наявні маркери: skip_action(100), no_reaction, no_bonus_action, immobilized, ...
  flags: StaticEffect[];       // прапорці для collectModifiers
  implies?: Condition5eKey[];  // напр. paralyzed → incapacitated
};
```

Ключі: `blinded`, `charmed`, `deafened`, `frightened`, `grappled`, `incapacitated`, `invisible`, `paralyzed`, `petrified`, `poisoned`, `prone`, `restrained`, `stunned`, `unconscious`, `exhaustion`.

| Стан | Як діє в рушії |
|---|---|
| Засліплений | власні атаки — перешкода; атаки по ньому — перевага |
| Зачарований | не може атакувати джерело стану (атакою чи шкідливим заклинанням) |
| Оглухлий | лише маркер (бойового ефекту немає) |
| Наляканий | перешкода на атаки, поки джерело живе; рух, що зменшує відстань до джерела, відхиляється |
| Схоплений | швидкість 0 (`immobilized`); 2024: перешкода на атаки по всіх, крім того, хто схопив |
| Недієздатний | без дії, бонусної дії й реакції (`skip_action` 100 + `no_bonus_action` + `no_reaction`); знімає концентрацію |
| Невидимий | власні атаки — перевага; атаки по ньому — перешкода |
| Паралізований | недієздатний + швидкість 0; автопровал Сил/Спр; атаки по ньому — перевага; влучання з 5 фт — крит |
| Скам'янілий | недієздатний + швидкість 0; автопровал Сил/Спр; атаки по ньому — перевага; опір усій шкоді; імунітет до отруєння |
| Отруєний | власні атаки — перешкода |
| Повалений | власні атаки — перешкода; атаки по ньому з 5 фт — перевага, здалеку — перешкода (вставання — частина 4b; до 4b стан знімає ДМ або тривалість) |
| Обплутаний | швидкість 0; власні атаки — перешкода; атаки по ньому — перевага; перешкода на рятівні Спр |
| Приголомшений (stunned) | недієздатний + швидкість 0; автопровал Сил/Спр; атаки по ньому — перевага |
| Непритомний | недієздатний + швидкість 0 + повалений; автопровал Сил/Спр; атаки по ньому — перевага; влучання з 5 фт — крит |
| Виснаження (1–6) | 2014: 1 — (перевірки, поза боєм), 2 — швидкість ×½, 3 — перешкода на атаки й рятівні, 4 — макс. HP ×½, 5 — швидкість 0, 6 — смерть. 2024: −2×рівень до кидків d20 (атаки, рятівні), швидкість −5 фт×рівень, 6 — смерть |

Нові прапорці (`FlagSchema`, `labels.ts`, редактор здібностей):
- `saveAdvantage` / `saveDisadvantage` `{ abilities: AbilityKey[] | "all", vsSpells?: true }` — «Магічний опір» = `saveAdvantage all vsSpells`;
- `autoFailSave` `{ abilities: AbilityKey[] }`;
- `saveProficiency` `{ abilities: AbilityKey[] }` — для юнітів і здібностей (герої беруть його з `Character.savingThrows`, якщо `rules.saves.proficiency`);
- `autoCritAdjacent` — влучання по власнику з 5 фт (сусідня клітинка) стає критом;
- `proneDefense` — атаки по власнику з 5 фт мають перевагу, здалеку — перешкоду (окремий прапорець, бо наявні `…ForAttackers` не залежать від відстані);
- новий стат `savingThrow` у `DYNAMIC_STATS` (`modifyStat`, flat) — для «Благословення»/«Порчі» та бонусів рятівних кидків.

Застосування: `applyCondition` приймає `condition: ConditionKey | Condition5eKey`. Для 5e-ключа він пише один `ActiveEffect` (`type: "condition"`, `name` = назва стану), де `effects` = маркер самого стану + маркери реєстру (з `implies`), а `abilityEffects` = прапорці реєстру. Варіант виснаження береться з `ctx.rules.conditions.exhaustion` у момент накладання; `value` маркера `exhaustion` = рівень, повторне накладання додає рівні (до 6; на 6 — смерть). Додаткові поля `applyCondition`:
- `saveEnds?: { ability: AbilityKey }` — наприкінці кожного ходу ціль повторює рятівний кидок проти СК накладача (зберігається в ефекті), успіх знімає стан;
- `levels?: 1–6` (лише для `exhaustion`).

Імунітети: `conditionImmunity` приймає й 5e-ключі (`[...CONDITION_KEYS, ...CONDITION_5E_KEYS, "fear", "berserk", "charm"]`). Імунітет до `incapacitated` не блокує `stunned` — перевіряється лише ключ, що накладається.

Рушій читає стани:
- атаки — `rollModeReasons` (прапорці з `abilityEffects` уже потрапляють у `collectModifiers`) + нові `proneDefense` (за відстанню атакувальника до цілі) і `autoCritAdjacent` (у `attack/critical`);
- `frightened`/`charmed` — перевірка джерела (`ActiveEffect.source.participantId`) у валідації атаки/заклинання й руху (`grid/path.ts`);
- маркери (`skip_action`, `immobilized`, …) — як зараз, через `hasEffectMarker`.

### 3. Рятівні кидки

`rollSavingThrow` переходить на `rollSave({ target, ability, dc, participants, rules, rng, presetRoll, source })` у `lib/utils/battle/saves/`; усі виклики оновлюються, `rollSavingThrow` видаляється:
1. `autoFailSave` для цієї характеристики → провал без кидка (лог «автопровал»).
2. Режим кидка: `saveAdvantage`/`saveDisadvantage` (з урахуванням `vsSpells`, коли кидок проти заклинання) + виснаження 2014 рівня 3+; обидва → звичайний.
3. Бонус = модифікатор + майстерність (`saveProficiency` або `Character.savingThrows` за `rules.saves.proficiency`) + `modifyStat savingThrow` + виснаження 2024 (−2×рівень).
4. `presetRoll` (від клієнта) — перший d20; другий для переваги/перешкоди кидає сервер.

Результат містить `mode`, `rolls`, `bonus`, `autoFail` для лога й `actionDetails.savingThrows`. Виклики: `spell/cast/outcome.ts`, `maneuvers/fire-burst.ts`, повторні кидки `saveEnds`, концентрація, кидки смерті (вони — окремий d20 без модифікатора).

### 4. Кидки смерті (`rules.deathSaves.enabled`)

Наслідки шкоди (кидки смерті, масивна шкода, концентрація) рахує один хелпер `applyDamageConsequences({ before, after, amount, crit, rules, rng })` (`lib/utils/battle/damage/consequences.ts`), який викликається одразу після кожного примітиву шкоди (`applyDamageToTarget`, `applyRawDamage` у заклинаннях, маневрах, зонах, `dealDamage`, DOT). Коли обидві механіки вимкнено, він повертає `after` без змін.

Тільки для героїв і NPC-героїв (`createBattleParticipantFromCharacter`); юніти при `unitsDieAtZero` переходять у `dead` одразу на 0 HP.
- HP 0 → статус `unconscious` + стан `unconscious` (без тривалості) + `battleData.deathSaves = { successes: 0, failures: 0, stable: false }`.
- Шкода ≥ макс. HP понад 0 (залишок після падіння на 0) → одразу `dead`.
- Черга ходу непритомного нестабільного героя (у циклі пропуску `processEndOfTurn`): d20 (сервер; лог). 10+ — успіх, 1 — два провали, 20 — 1 HP, приходить до тями (стан знімається, лічильники скидаються). 3 успіхи → `stable`; 3 провали → `dead`. Хід пропускається, як і зараз.
- Шкода по герою на 0 HP: +1 провал (+2, якщо влучання критичне); стабільність скидається.
- Лікування > 0 → HP, стан `unconscious` знімається, лічильники скидаються.
- Чинне «союзники встають після перемоги» лишається.
- Вимкнено (default) — поточна поведінка без змін.

UI: у картці учасника на 0 HP — три кружечки успіхів і провалів (`components/battle`), у лозі — кидки.

### 5. Концентрація (`rules.concentration.enabled`)

- `SpellDefinitionSchema.concentration?: boolean` + перемикач у редакторі заклинання.
- Каст такого заклинання: кастер отримує `ActiveEffect` «Концентрація: <назва>» (`type: "buff"`, тривалість = найдовша тривалість ефектів заклинання, `concentration: { castId }`); усі `ActiveEffect` і зони, накладені цим кастом, отримують `concentrationOf: { casterId, castId }`. Новий каст із концентрацією спершу знімає попередню.
- Шкода по кастеру з концентрацією → рятівний кидок Вит (через `rollSave`) проти СК `max(10, ⌊шкода/2⌋)`, з межею `dcCap`, якщо вона задана. Провал, стан `incapacitated`, смерть чи 0 HP → концентрація зникає разом з усіма ефектами `concentrationOf` цього касту (на всіх учасниках і в зонах).
- Вимкнено — поле `concentration` ігнорується.

### 6. ДМ: накласти/зняти стан вручну

Новий бойовий роут `conditions` (Zod + `runBattleMutation` + `conditions-mutation.ts`, доступ `dm`): `{ participantId, action: "apply" | "remove", condition, rounds?, levels?, saveEnds? }`. Накладання використовує той самий шлях, що й `applyCondition`, тільки без ability-власника (джерело «ДМ»). UI: у швидких діях ДМ на учаснику — меню станів 5e (`ResponsiveDialog hud`: список станів з описом, тривалість; поточні стани з кнопкою «Зняти»). ## 4b. Дизайн: дії 5e в бою

Розвідка (2026-10-22):
- Дія/бонус/реакція — `actionFlags`; рух рахується в клітинках (`CELL_FEET = 5`), `movementUsed`, BFS `reachable` (`grid/path.ts`), сервер отримує лише точку призначення — шлях не передається.

- Реакція зараз — HOMM-відплата (`attack/retaliation.ts`): лише у відповідь на атаку; атак при відході, «зони контролю», вимушеного руху (поштовх), підготовленої дії, вставання з положення лежачи немає.

### 1. Правила

```ts

```

`enabled: false` (default) — жодних нових кнопок і атак при відході; HOMM без змін. Вкладка «Дії 5e» на `dm/rules`.

### 2. Каталог базових дій

`lib/utils/battle/actions/` — реєстр `CORE_ACTION_REGISTRY` (`satisfies Record<CoreActionKey, CoreActionDef>`): `{ label, description, cost: "action" | "bonusAction" | "movement", target: "none" | "ally" | "enemyAdjacent" | "self", run(ctx) }`. Один бойовий маршрут `core-action` (Zod `discriminatedUnion("action")` + `runBattleMutation` + `core-action-mutation.ts`), доступ `currentController` (власник на своєму ході, ДМ — за будь-кого).

| Дія | Вартість | Ефект |
|---|---|---|
| Ривок (`dash`) | дія | `battleData.extraMovement += movementBudget` (клітинки) до кінця ходу; `remainingMovement` враховує |
| Відхід (`disengage`) | дія | ефект «Відхід» до кінця ходу (маркер `disengaged`) — рух не провокує атак |
| Ухилення (`dodge`) | дія | ефект «Ухилення» до початку наступного ходу: `disadvantageForAttackers` + `saveAdvantage ["dexterity"]`; знімається, якщо власник стає недієздатним або швидкість 0 |
| Допомога (`help`) | дія | союзник у межах 5 фт отримує ефект «Допомога» (`advantage` на наступну атаку, `consumeOn: "ownAttack"`), що зникає на початку наступного ходу помічника |
| Сховатися (`hide`) | дія | перевірка Скритності (`rollCheck`) проти найбільшої пасивної Уважності ворогів (10 + мод. Мудр + майстерність, якщо є); успіх → ефект «Схований» (як `invisible`: `advantage` на атаки, `disadvantageForAttackers`), знімається після власної атаки чи заклинання (`consumeOn: "ownAttack"` + каст) |
| Підготувати (`ready`) | дія | `battleData.readied = { kind: "attack", round }`; до початку свого наступного ходу власник (або ДМ) може «Виконати підготовлену атаку» на будь-якому ході — атака через наявний конвеєр атаки, витрачає реакцію; на початку наступного ходу `readied` зникає |
| Встати (`standUp`) | рух | знімає всі ефекти з власним ключем `prone`; витрачає половину `movementBudget` (якщо руху не вистачає — відмова) |
| Схоплення (`grapple`) | дія (одна атака) | ціль — суміжний ворог (розміри істот не моделюються, тож обмеження «не більше ніж на розмір більша» не перевіряється). 2014: Атлетика атакувальника проти більшого з Атлетики/Акробатики цілі (`rollCheck`); 2024: ціль кидає рятівний Сил або Спр (на вибір рушія — більший модифікатор) проти СК 8 + мод. Сил + майстерність. Успіх → `grappled` з джерелом = атакувальник |
| Штовхання (`shove`) | дія (одна атака) | та сама перевірка; успіх → `prone` або відштовхнути на 5 фт (вибір гравця в запиті; клітинка позаду цілі має бути вільною та прохідною, інакше лише `prone`) |
| Вирватися (`escape`) | дія | схоплений: Атлетика/Акробатика проти Атлетики схоплювача (2014) або проти СК схоплювача (2024); успіх → знімає `grappled` від цього джерела |

Схоплення: стан зникає, коли схоплювач недієздатний або вони більше не суміжні; рух схоплювача тягне ціль у клітинку, яку схоплювач щойно звільнив, і коштує подвійно (5e: половина швидкості). Без мапи дії руху (`dash`, `standUp`, поштовх на 5 фт) лише записуються в лог.

### 4. Атаки при відході

## 4c-1. Дизайн: класи й рівні

Розвідка (2026-10-22):
- `Character.class`/`subclass` — вільний текст, на рушій не впливає. На бій впливає лише `archetype` (5 ключів, `hero-archetypes.ts`): `hpPerLevel` і множники ближньої/дальньої/магічної шкоди.
- HP — `getHeroMaxHpBreakdown` (`hero-scaling.ts`), рахується під час збирання учасника, не зберігається.
- Майстерність — `proficiencyForLevel` (`rules/formulas.ts`) від `Character.level`; формула за замовчуванням збігається з 5e.
- Слоти: `Character.spellSlots` (JSON), прогресія раси (`spellSlotProgression`, кола 1–5) або крива повного заклинача до рівня героя 10 (`spell-slots.ts`); у бою `current = max` на старті. Межа кіл 0–5 (а в `createSpellSchema` — 1–5) жорстко записана в Zod-схемах заклинань і рас, формі й закладках книги, `view/hero.ts` (`TIERS`, `slotLevels`), `SlotGrid`, `spellLevelMetal`, CSS `.circle-0…5`, `calculateSpellSlotGain`.
- Здібності раси вливаються в персонажа через `collectCharacterAbilities` (`abilities/build/collect.ts`); ліміти — `perBattle/perRound/perTurn/cooldownRounds/chance`, відпочинків немає.
- Підвищення рівня — `POST …/level-up` (ДМ): +1 рівень, випадкове +1 до характеристики, приріст слотів. Гравець не може змінювати `level` і `archetype` (`patch-character.ts`).
- Раса прив'язана до персонажа за назвою; синхронізація з джерелом видаляє рядки напряму (`sync/apply.ts`), не через сервіс.

### 1. Правила

```ts
classes: { enabled: false }   // HP завжди «середнє» (без кидків)
```

`enabled: false` (default) — HOMM без змін: архетип, HP за формулою HOMM, слоти раси. `enabled: true` — персонаж із непорожнім `classes` рахується від класів: архетип ігнорується (множники 1), HP за кістками, рятівні стартового класу (разом із ручними), слоти за класами. Персонаж із порожнім `classes` і далі рахується по-HOMM-івськи, тож увімкнення не ламає наявних героїв. Вкладка «Класи» на `dm/rules`, рядок у `MECHANIC_REGISTRY`.

### 2. Ресурс контенту `classes`

Модель Prisma `GameClass` (таблиця `classes`, `campaignId`, `sourceId`/`sourceHash`), повний шлях раси: `CONTENT_RESOURCES`, `ContentKind`, роути `collectionRoutes`, кеш довідника (`ReferenceKind`), бандл шаблону (`BUNDLE_TABLES`, `SYNC_TABLE_SCOPES`), синхронізація з джерелом, OpenAPI, MCP — усе автоматично з ресурсу.

```ts
{
  name, icon?, color?,
  hitDie: 6 | 8 | 10 | 12,
  savingThrows: AbilityKey[],                       // 2
  proficiencies: { armor: string[]; weapons: string[]; tools: string[] },   // текст для показу
  skillChoices: { count: number; from: SkillKey[] },  // підказка у формі персонажа
  caster: "none" | "full" | "half" | "third" | "pact",
  spellcastingAbility: AbilityKey | null,
  features: { level: number; abilities: Ability[] }[],          // 1–20
  subclassLevel: number | null,
  subclasses: { id: string; name: string; features: { level: number; abilities: Ability[] }[] }[],
}
```

Підкласи вкладені в клас (менше роутів; синхронізація — цілим записом; id підкласів стабільні, бо синхронізація оновлює наявні рядки). Видалення класу через сервіс відмовляє (409, текст у `api-errors.ts`), якщо його використовує персонаж.

### 3. Персонаж

- Нова колонка `Character.classes Json @default("[]")`: `[{ classId, subclassId?, level }]`; перший запис — стартовий клас (рятівні, максимум кістки на 1-му рівні).
- `Character.level` = сума рівнів класів (сервер підтримує інваріант); від нього, як і зараз, майстерність. Текстові `class`/`subclass` у режимі класів сервер заповнює з назв («Воїн 5 / Чарівник 2») — для показу й AI-контексту.
- `classes` змінює лише ДМ (як `level`/`archetype` у `patch-character.ts`).
- Запис із неіснуючим `classId` (клас видалено синхронізацією) у розрахунках пропускається; форма показує «Клас не знайдено — оберіть інший».
- Міграція (лише розширення): таблиця `classes` + `ENABLE ROW LEVEL SECURITY`, колонка `characters.classes`.

### 4. Похідні характеристики (`lib/utils/characters/classes/`)

Чисті функції, спільні для листа, форми й збирання учасника:
- **HP (середнє):** 1-й рівень стартового класу — максимум кістки + мод. Тіл; кожен наступний рівень (будь-якого класу) — `кістка/2 + 1` + мод. Тіл; мінімум 1 HP за рівень. Нічого не зберігається.
- **Рятівні кидки:** об'єднання `savingThrows` стартового класу і ручних `Character.savingThrows` (риси, предмети).
- **Характеристика заклинань:** `Character.spellcastingAbility`, якщо порожня — першого класу-заклинача. Окремі DC для класів мультикласу — поза етапом.
- **Кістки хітів:** список «Nd{кістка}» за класами — лише показ (витрата — 4d).

### 5. Вміння класу

Нове джерело `AbilitySource.type: "class"` (з `id` класу або підкласу). `collectCharacterAbilities` додає вміння класу з `feature.level ≤ рівень у цьому класі` і підкласу (якщо обраний) поруч із расою; далі як зараз (`resolveAbilities`, `bakePassives`).

`LimitsSchema` отримує `perRest: { rest: "short" | "long"; uses: number }`. До 4d рушій трактує його як `perBattle = uses` (лічильник `abilityUsage` у бою); постійні заряди між боями — разом із відпочинками в 4d. Підказка заряду в UI — «N / відпочинок».

Вміння з вибором (бойовий стиль тощо) — поза етапом: ДМ додає обране як персональне вміння героя, як зараз.

### 6. Слоти за класами (`lib/utils/spells/class-slots.ts`)

`classSpellSlots(classes)` → `{ "1".."9": { max }, pact?: { level, max } }`:
- рівень заклинача = Σ: `full` — рівень, `half` — ⌊рівень/2⌋, `third` — ⌊рівень/3⌋; якщо клас-заклинач один — `half` = ⌈рівень/2⌉ від 2-го рівня, `third` = ⌈рівень/3⌉ від 3-го (таблиці PHB);
- слоти — таблиця мультикласу 5e (рівень заклинача 1–20 → кола 1–9);
- пакт — окремо, таблиця Чаклуна за рівнем у класі `pact`.

У режимі класів (персонаж з класами) старт бою бере слоти з `classSpellSlots` (`current = max`), а не з раси чи `Character.spellSlots`; лист персонажа показує те саме, `Character.spellSlots` оновлюється при зміні класів. Каст заклинання кола N: звичайний слот кола N, якщо немає — слот пакту з колом ≥ N. Вибір слота і підсилення вищим колом — 4c-2.

### 7. Кола 0–9

Межа 0–5 → 0–9 скрізь, де вона жорстко записана (див. розвідку); `createSpellSchema` допускає 0 (кантрипи); `.circle-6…9` у `hud.css`. Обмеження HOMM лишаються даними HOMM: прогресія раси (1–5), крива до рівня героя 10, відкриття кіл майстерністю школи. `SlotGrid` показує лише кола зі слотами. HOMM-контент не має кіл вище 5 — поведінка не змінюється.

### 8. Підвищення рівня

У режимі класів `POST …/level-up` приймає `{ classId, subclassId? }`: новий рівень у наявному класі або новий клас (мультиклас); підклас обов'язковий, коли рівень класу досягає `subclassLevel`, і заборонений раніше. Межа `campaign.maxLevel` — на суму. Випадкове «+1 до характеристики» (HOMM) не застосовується — збільшення характеристик ДМ вносить у листі. Слоти перераховуються з класів.

Пункт меню — коли `rules.classes.enabled`.

## 4c-2. Дизайн: атаки й заклинання 5e

Розвідка (2026-10-22):
- `BattleAttack.properties` (`types/battle.ts:97`) — вільний рядок, рушій його не читає. Зброя — артефакт: `WeaponStatsSchema` (`lib/utils/artifacts/weapon-stats.ts`) ↔ колонки `bonuses`/`modifiers`; форма `ArtifactWeaponFields`. Юніти — `unitAttackSchema`.
- Шкода героя (`damage/hero-damage.ts`): кубик зброї + кубики героя за рівнем + рівень + мод. (`primaryAbility` або Сил/Спр) + «+N» зброї, × множник архетипу. Атакувальна характеристика — `attackAbilityKey`; фехтувальної немає.
- Крит: шкода залежить лише від ефекту крита (`criticals.effects`: `double_damage`/`max_damage`/`additional_damage`); з вимкненими ефектами крит шкоди не додає. Клієнтське прев'ю (`damage/breakdown.ts:67`) завжди множить ×2 — розходиться із сервером.
- Ближня атака — жорстко ≤ 1 клітинка (`grid/attack-reach.ts`), так само поріг атак при відході (`actions/opportunity.ts:60`). Дальня поруч із ворогом відхиляється; дальність — останнє число `range`.
- «Кілька атак за дію» немає; `actionsPerTurn`/`pendingExtraActions` — цілі додаткові дії (HOMM). Бонусна дія — лише вміння й заклинання; атаки бонусною дією немає. Схоплення/Штовхання (4b) вимагають невитраченої дії.
- Сітка спорядження: `weapon`, `range_weapon`, `shield`; клітинка приймає лише артефакти свого типу (`CharacterArtifactsSection`, `stash-actions.ts`); `extract-attacks` ключ `shield` не читає. Окремої логіки щита в рушії немає — артефакт дає свої `bonuses`.
- Заклинання: одне число `dice`; грані — майстерність школи (герой) або рівень (юніт), кількість росте з рівнем кастера (`spells/model/dice.ts`, `spell/caster-dice.ts` — спільний для сервера й клієнта). Коло заклинання на кубики не впливає. Запит касту не має слота; `spellSlotKey` обирає автоматично (коло N, далі пакт ≥ N). Розв'язка — лише `auto`/`save`, атаки заклинанням немає. Поля визначення зберігаються окремими колонками `spells`.
- На snapshot учасника немає ознаки режиму класів (`resolvedClasses` у `from-character.ts` не зберігається).

### 1. Перемикач режиму

`from-character.ts` ставить `abilities.damageModel = "5e"`, коли персонаж у режимі класів (`resolvedClasses` не порожній). Без поля — HOMM. Рушій перевіряє лише це поле; юніти до 4e лишаються HOMM. Поле проходить `split-participant`/`participant-patch` як решта `abilities`.

### 2. Шкода атаки 5e

У `heroAttackDamageParts`/`heroDamageContext` для `damageModel: "5e"`:
- формула = кубик зброї (або `versatileDice`) + мод. характеристики + «+N» зброї; без кубиків героя, без рівня, без множника архетипу;
- характеристика: ближня — Сил, дальня — Спр, `finesse` — більша з Сил/Спр, метальна (`thrown`) — як ближня;
- бонус атаки — як зараз (мод. + майстерність; майстерність у зброї класу лише текст, тож додається завжди);
- далі той самий ланцюжок (`compute.ts`): здібності, ефект крита, «+N», ослаблення, баланс, опори, укриття.

Ті самі функції живлять прев'ю (`averageAttackDamage`, `weaponPreview`, лист персонажа) і серверні атаки (`server-attack.ts`), тож прев'ю = сервер.

### 3. Криты

`rules.criticals.doubleDice: false` (нове поле секції). `true` — на криті кількість кубиків шкоди подвоюється (кубики зброї й кубики здібностей у формулі; модифікатори — ні). Діє на всі атаки (зброєю й заклинанням), разом з ефектами критів або без них. Default — HOMM без змін. Прев'ю крита (`damage/breakdown.ts`) показує те, що рахує сервер (подвоєні кубики або ефект крита), а не завжди ×2. Перемикач у вкладці «Криты» редактора правил.

### 4. Властивості зброї

`traits: WeaponTrait[]` у `WeaponStatsSchema` (зберігається як новий тип у `modifiers`; `weaponStatsFromRow` його не відкидає) і в `unitAttackSchema`; `BattleAttack.traits` + `versatileDice?`. Текст `properties` лишається приміткою — міграції даних немає. Рушій читає `traits` лише у героя 5e (у юнітів — з 4e).

| Ключ | Дія |
|---|---|
| `light` | дозволяє бій двома зброями |
| `finesse` | атака й шкода від більшої з Сил/Спр |
| `twoHanded` | забороняє атаку другою рукою цього ходу і `versatile` (обмеження «не зі щитом» не застосовується: сітка HOMM тримає лук і щит одночасно, зміна спорядження в бою не моделюється) |
| `versatile` + `versatileDice` | кубик `versatileDice`, коли клітинка «Щит» порожня |
| `reach` | ближня досяжність 2 клітинки: атака (`attackReachError`, `enemiesInReach`) і поріг атак при відході |
| `thrown` | ближня зброя з `range` може атакувати як дальня (без перешкоди «ворог поруч» — це ближня зброя); характеристика як у ближньої; зброя лишається в руці |
| `ammunition` | лише показ (набої не рахуються) |

Дальність `"80/320"` = звичайна/максимальна: у 5e за звичайною — перешкода (нова причина в `rollModeReasons`), за максимальною — відмова. Дальня атака з ворогом поруч у 5e — перешкода, а не відмова. HOMM: як зараз (останнє число, відмова поруч з ворогом).

### 5. Додаткова атака

Новий стат `attacksPerAction` у `DYNAMIC_STATS` (`modifyStat`, flat): вміння класу «Додаткова атака» дає +1 (Воїн 11 — +2). Відмінний від `actionsPerTurn`: додаткова дія від `actionsPerTurn` дає нову дію «Атака» з повним набором атак.
- Перша атака дією витрачає дію і пише `battleData.attacksLeft = attacksPerAction` (кількість атак, що лишилися; 0 — поле не пишеться).
- Наступний запит атаки при `attacksLeft > 0` бере атаку з лічильника, а не дію (`validateAttackRequest`/`applyMainActionUsed`); кожна атака — своя ціль і зброя.
- Схоплення й Штовхання (4b) при `attacksLeft > 0` теж беруть атаку з лічильника.
- `attacksLeft` скидається в `turn/turn-state.ts`; дія лишається витраченою, навіть якщо атаки не використано.
- Атаки поза ходом (атака при відході, підготовлена, відплата) — завжди одна, лічильник не чіпають.
- Автозавершення ходу (`view/turn-exhausted.ts`) не спрацьовує, поки `attacksLeft > 0`.

### 6. Бій двома зброями

Лише герой 5e:
- Клітинка «Щит» у режимі класів приймає й артефакти типу WEAPON з `light` (сітка `CharacterArtifactsSection`, «Вдягнути» зі сховища, серверна перевірка вдягання). `extract-attacks` читає ключ `shield`: зброя там → атака з `hand: "off"`; у HOMM нічого не змінюється (такий артефакт туди не вдягнеш).
- Запит атаки отримує `offHand: true`: витрачається бонусна дія. Умови: цього ходу була атака дією «Атака» легкою ближньою зброєю основної руки (`battleData.attackedWithLight`), зброя другої руки легка, ні основна, ні друга не `twoHanded`.

### 7. Заклинання 5e

Нові колонки `spells` (міграція `20261028000000_spell_5e_dice`, лише розширення), поля `SpellDefinitionSchema`, усі необов'язкові й ігноровані в HOMM:
- `dieSides?: 4 | 6 | 8 | 10 | 12` — грань у 5e (порожньо — d6);
- `upcastDice?: number` — +N кубиків за кожне коло понад базове;
- `upcastTargets?: number` — +N до `maxTargets` за коло;
- `addAbilityMod?: boolean` — додати мод. характеристики заклинань до шкоди/лікування;
- межа `SpellDiceSchema` 20 → 40.

OpenAPI/MCP/бандл отримують поля автоматично; ручне відображення (`resources/spells.ts` update, `readSpellDefinition`/`spellDefinitionColumns`, `BOOK_SPELL_SELECT`, `toBookSpell`, `SpellRules`) дописується.

Кубики (`casterSpellDice(caster, spell, castLevel)`, гілка для `damageModel: "5e"`):
- кантрип: `dice × (1 + [рів ≥ 5] + [рів ≥ 11] + [рів ≥ 17])`, рівень = `abilities.level` (сума класів);
- коло ≥ 1: `dice + upcastDice × (castLevel − level)`;
- грань `dieSides ?? 6`; майстерність школи й рівень кастера не впливають.
HOMM-гілка `spellDice` без змін.

Вибір слота: запит касту (`cast-spell-schema.ts`, `SpellCastData`) отримує `slotKey?` («1»…«9» | «pact»). Сервер перевіряє: слот існує, не порожній, його коло (`slotLevel`) ≥ коло заклинання; `castLevel = slotLevel`. Без `slotKey` — автовибір `spellSlotKey`, як зараз (HOMM, юніти, DM-каст). `actionDetails.spellSlotUsed`/`spellLevel` і тригер `spellCast` отримують фактичне коло касту. Кількість цілей = `maxTargets + upcastTargets × (castLevel − level)`.

Атака заклинанням: `SpellResolutionSchema` + `{ kind: "attack" }` (цілі `enemy`/`area`). Кидок d20 + мод. характеристики заклинань + майстерність (або `spellAttackBonus`, якщо заданий) проти КЗ кожної цілі; перевага/перешкода — через `rollModeReasons` (стани, дальність, ворог поруч); промах — без шкоди й ефектів; крит — подвоєні кубики при `doubleDice`. d20 кидає клієнт (preset, як в атаці зброєю) або сервер. HOMM-контент такої розв'язки не має.

До 4e лишаються HOMM-івськими: закляття юнітів, множник архетипу (у режимі класів = 1), бонуси здібностей у `computeSpellPower`.

### 1. Правила

```ts
}
```

Вкладка «Поза боєм» на `dm/rules`, рядок у `MECHANIC_REGISTRY`, хеш синхронізації шаблону. Усе вимкнено за замовчуванням — HOMM5 і наявні кампанії без змін. Перемикачі не залежать від `classes.enabled` (HOMM-кампанія може ввімкнути збереження ресурсів; кістки хітів тоді просто відсутні). Шаблон SRD (4f) вмикає все.

### 2. Дані

Міграція (лише розширення):
- `characters.resources Json @default("{}")`, `characters.inspiration Boolean @default(false)`;
- таблиця `character_logs` (`id`, `campaignId`, `characterId`, `actorUserId?`, `kind`, `data Json`, `createdAt`; індекс `(characterId, createdAt)`; `ENABLE ROW LEVEL SECURITY`; каскад від кампанії й персонажа).

`resources` зберігає **витрачене**, а не поточне, тож підвищення рівня чи зміна класу нічого не перераховує (`lib/utils/characters/resources/schema.ts`):

```ts
{
  hp?: number;                                // відсутнє = повне здоров'я; обрізається до max при читанні
  tempHp?: number;
  dead?: boolean;
  slotsSpent?: Record<"1".."9" | "pact", number>;
  hitDiceSpent?: Record<classId, number>;
  charges?: Record<abilityKey, number>;       // використання вмінь з perRest
  exhaustion?: number;                        // 0–6 (2014) / 0–10 (2024)
  shortRestOpen?: boolean;                    // вікно кісток хітів
}
```

`resources`, `inspiration`, `experience` не входять у звичайний PATCH гравця; ДМ змінює їх окремими роутами (нижче). Бандл шаблону й синхронізація персонажів не стосуються (персонажі не в бандлі), `character_logs` теж.

Журнал: `lib/server/characters/log.ts` (`writeCharacterLog(tx, …)`) за зразком `inventory/log.ts`; види в `lib/constants/character-log.ts`: `check`, `save`, `short_rest`, `long_rest`, `rest_closed`, `hit_die`, `xp`, `inspiration`, `resources_edit`, `battle_result`.

### 3. Бій ↔ ресурси (лише коли `persistResources`)

Чиста логіка — `lib/utils/characters/resources/battle.ts`; рушій читає `battle.rules` (заморожена копія).

**Старт бою** (`createBattleParticipantFromCharacter`, коли персонаж має `resources`):
- `currentHp = clamp(resources.hp ?? max, 0, max)`, `tempHp = resources.tempHp ?? 0`; `hp = 0` → учасник стартує непритомним (з кидками смерті, якщо вони ввімкнені), `dead` → мертвим;
- слоти: `current = max(0, max − slotsSpent[k])` (і для класів, і для збережених слотів);
- `abilityUsage[key].battle = charges[key]` для вмінь з `perRest`;
- виснаження `N > 0` → ефект `exhaustion` рівня N через `applyCondition` (з урізанням HP для 2024, як у 4a);
- `battleData.inspiration = Character.inspiration` (коли `inspiration` увімкнено, незалежно від `persistResources`).

**Завершення бою** (`saveBattle`, гілка `completing`, у тій самій транзакції): для кожного учасника з `characterId`, що був на мапі (не резерв), рахується `applyBattleResult(resources, participant)` → `hp`, `tempHp`, `dead`, `slotsSpent = max − current`, `charges` для `perRest`, `exhaustion = exhaustionLevel`; `shortRestOpen` скидається. Інші стани й концентрація не переносяться. Пишеться `Character.resources` (+ `inspiration`, якщо увімкнено) і запис журналу `battle_result` (HP до/після, витрачені слоти). Юніти й призвані — ні. Видалений бій без завершення — нічого не пише.

**Перемога**: зараз `completeBattle` повертає непритомних союзників до max HP. При `persistResources` — до **1 HP** (у 5e стабілізований герой приходить до тями з 1 HP); `completeBattle` отримує `rules`. Мертві (`dead`) лишаються мертвими, доки ДМ не змінить стан у листі.

### 4. Відпочинки (`lib/utils/characters/resources/rest.ts`, роут `POST /api/campaigns/[id]/rest`, ДМ)

Тіло: `{ kind: "short" | "long" | "close", characterIds: string[] }`. Доступно лише при `persistResources`; персонажі мають бути в кампанії й не `PENDING`. Відповідь — оновлені `resources` героїв.

- **Короткий**: слоти пакту → повні; заряди `perRest.rest = "short"` → 0; `shortRestOpen = true`.
- **Довгий** (мертві пропускаються): `hp` → повне, `tempHp` → 0; усі слоти й пакт; усі заряди `perRest`; кістки хітів: повертається ⌊загальний рівень / 2⌋ (мінімум 1) або всі (`longRestHitDice: "all"`), починаючи з найбільших кісток; виснаження −1; `shortRestOpen = false`.
- **`close`**: `shortRestOpen = false` (кнопка «Завершити відпочинок»). Старт бою з цим героєм теж закриває вікно (у записі після бою).

Кожна дія — запис журналу кожному герою.

### 5. Кістки хітів (`POST /api/campaigns/[id]/characters/[characterId]/hit-dice`, власник або ДМ)

Тіло `{ classId }`. Умови: `persistResources`, персонаж у режимі класів, `shortRestOpen`, не мертвий, у класі є невитрачені кістки. Сервер кидає `d{hitDie} + мод. Тіл` (мінімум 0), додає до HP (до max), `hitDiceSpent[classId] += 1`, журнал `hit_die`. Помилки — 409 з текстами з `api-errors.ts`.

### 6. Кидки з листа (`POST …/characters/[characterId]/roll`, власник або ДМ)

Тіло `{ kind: "check", skill } | { kind: "check", ability } | { kind: "save", ability }` + `useInspiration?: boolean`. Сервер будує учасника тим самим шляхом, що й лист (`buildSheetFor`, з ресурсами — тож виснаження діє), і викликає `rollCheck` / `rollSave` (без DC: `success` не показується). `useInspiration` (коли натхнення увімкнене й є) додає перевагу і знімає натхнення. Відповідь `{ rolls, mod, total, mode }`; клієнт показує результат і анімацію 3D-кубиків (`useDiceRoller` з готовими значеннями). Журнал `check`/`save`.

### 7. Досвід (`rules.outOfCombat.xp`)

- Таблиця порогів 5e (рівні 2–20) — `lib/constants/experience.ts`; `xpForLevel`, `levelUpAvailable(character, maxLevel)`.
- `POST /api/campaigns/[id]/experience` (ДМ): `{ characterIds, amount, split: boolean, note? }` — кожному `amount` або `⌊amount / n⌋`; журнал `xp`. Від'ємна сума дозволена (виправлення), досвід не нижче 0.
- Підвищення рівня як і раніше робить ДМ наявним діалогом; лист показує «Досвід X / поріг» і «Доступне підвищення рівня», список персонажів ДМ — значок.
- Автоматичний досвід за переможених — 4e (CR → XP).

### 8. Натхнення (`rules.outOfCombat.inspiration`)

- `POST …/characters/[characterId]/inspiration` (ДМ): `{ value: boolean }`; журнал `inspiration`.
- Витрата: кидок з листа (`useInspiration`) і атака в бою: поле `useInspiration` у запиті атаки → причина переваги в `rollModeReasons` (і в прев'ю клієнта, щоб кидок d20 ішов з перевагою), сервер знімає `battleData.inspiration`; після бою значення пишеться в `Character.inspiration`. Рятівні кидки в бою кидає той, хто накладає ефект, — натхнення там не застосовується.

### 9. ДМ: правка ресурсів (`PATCH …/characters/[characterId]/resources`, ДМ)

`{ hp?, tempHp?, exhaustion?, dead?, reset?: true }` — ручне лікування, воскресіння, зняття виснаження, «повністю відновити»; журнал `resources_edit`. `GET …/characters/[characterId]/log?cursor=` (власник або ДМ) — журнал сторінками по 30.

### 10. UI

- **Лист персонажа** (`components/character-profile/`): у `ProfileHero` — HP поточні / max і тимчасові, виснаження, натхнення (значок), досвід із порогом; кістки хітів «витрачено / усього» з кнопкою «Витратити» на клас (лише у вікні короткого відпочинку); у вкладці «Бій» рятівні кидки й навички — кнопки кидка (діалог з перемикачем «Натхнення» і результатом); у «Магії» слоти й пакт — поточні / max; заряди `perRest` у вкладці «Вміння» — «N / відпочинок»; нова вкладка «Журнал».
- **ДМ, сторінка персонажів**: кнопки «Відпочинок» (діалог: короткий/довгий, вибір героїв, за замовчуванням усі схвалені герої) і «Завершити відпочинок», коли є відкрите вікно; «Досвід» (діалог: герої, сума, поділити); у картці героя — HP, значок «рівень доступний», натхнення.
- **ДМ, лист героя**: «Ресурси» (діалог правки §9), перемикач натхнення.
- **Бій**: перемикач «Натхнення» в діалозі атаки, коли воно є.
- Хуки в `lib/hooks/characters/` (`useRest`, `useSpendHitDie`, `useSheetRoll`, `useAwardXp`, `useInspiration`, `useEditResources`, `useCharacterLog`), клієнт у `lib/api/characters.ts`; мутації інвалідують `characterKeys.sheet`, список персонажів і журнал.

### 11. Поза обсягом 4d

Відновлення слотів уміннями класу (Arcane Recovery тощо — ДМ правкою ресурсів); ритуали; тривалість відпочинку й переривання; кидки поза боєм для юнітів; MCP/OpenAPI для відпочинків (етап 6); realtime оновлення листа.

### 12. Перевірка 4d

- Наявні тести — без змін (`persistResources: false` — старт бою з повними ресурсами, `completeBattle` — max HP); `battle-sweep` на HOMM5.
- Нові тести: схема й чисті функції ресурсів (короткий/довгий, кістки хітів half/all з різними кістками, мертвий пропускається, виснаження −1), старт бою з ресурсів (HP, 0 HP → непритомний, слоти, пакт, заряди, виснаження), `applyBattleResult` (резерв не пишеться, юніти ні, `shortRestOpen` скидається), перемога → 1 HP при `persistResources`, роути (права власник/ДМ/чужий гравець, 409 поза вікном, `persistResources` вимкнено → 409), кидок з листа з натхненням і виснаженням, досвід (поділ, не нижче 0, `levelUpAvailable`), натхнення в атаці (перевага й зняття), журнал (сторінки), Zod правил і міграція з RLS; компонентні — діалог відпочинку, кнопка кістки хітів.
- Живий прогін (десктоп): кампанія з класами й усіма перемикачами «Поза боєм» → бій (витратити слот, вміння `perRest`, отримати шкоду) → після бою лист показує залишок → короткий відпочинок → гравець витрачає кістку хітів → довгий → усе відновлено; кидок навички з натхненням; досвід до порогу → значок і level-up. Тестові дані видаляються.
- Документи: `battle.md` («5e: поза боєм»), `abilities.md` (`perRest` між боями), STATUS, хендоф, пам'ять.

## 4e. Дизайн: монстри й баланс 5e

Розвідка (2026-10-22):
- `Unit` має `level` (тір HOMM 1–7), `proficiencyBonus`, `attacks[]` (варіанти атаки), `abilities`; CR, XP, рятівних кидків, легендарного нічого немає. Бібліотека HOMM сіє `level = tier`, `proficiencyBonus = proficiencyForTier`.
- `createBattleParticipantFromUnit` не ставить `damageModel`, тож юніти завжди йдуть HOMM-шляхом шкоди; СК юніта = `saveDcBase + prof + level` (у `balance/stats.ts` — без тіру: розбіжність).
- Додаткові атаки — стат `attacksPerAction` (4c-2), лічильник `attacks-left.ts`. Атака поза ходом — патерн `readiedAttack` (`requireActor(…, { anyTurn })`).
- `rollSave` чистий; викликається в `spell/cast/outcome.ts`, `concentration`, `save-ends`, `grapple`, `fire-burst`, листі. Легендарного опору немає.
- Тригер вмінь `roundStart` уже є (ініціатива 20 ≈ початок раунду).
- Баланс — лише `computeFairScaling` у трьох місцях: `setupFairScaling` (UI), `balance-post` (автопідбір), `scaleEnemiesForFairBattle` (старт).
- Завершення бою: `saveBattle` (гілка `completing`) уже викликає `persistCharacterResources` (4d); досвід — `xpShare`/`addExperience`/`lockCharacters` і журнал `xp` з 4d.

Рішення користувача (2026-10-22): обидві редакції 5e (2014 і 2024) перемикачем у правилах. Решта — рішення сесії за дорученням користувача (див. нижче), HOMM5 без змін.

### 1. Правила

```ts
encounters: {
  balance: "fair",       // "fair" — computeFairScaling (HOMM, як зараз); "xp" — бюджет XP 5e без масштабування
  edition: "2014",       // "2014" | "2024": пороги складності й множник кількості
  autoXp: false,         // після перемоги XP переможених ділиться між героями (потрібне outOfCombat.xp)
}
```

Вкладка «Зустрічі» на `dm/rules`, рядок у `MECHANIC_REGISTRY`, хеш синхронізації шаблону. Default — поведінка HOMM5.

### 2. Юніт: поля 5e

Міграція (лише розширення) у `units`:
- `cr Float?` — 0, 0.125, 0.25, 0.5, 1…30; `null` — юніт HOMM (усе як зараз);
- `xp Int?` — ручне перевизначення; інакше з таблиці CR;
- `multiattack Int @default(1)`;
- `legendaryActions Int @default(0)`, `legendaryResistances Int @default(0)`;
- `saveProficiencies Json @default("[]")` — ключі характеристик.

Таблиці (`lib/constants/challenge.ts`): CR → XP і CR → майстерність (однакові у 2014 і 2024), підпис CR («1/8»). Поля проходять весь шлях ресурсу `units`: Zod create/update/import, `resources/units.ts`, `toUnit`, `types/units.ts`, `unit-form.ts`, бандл/синхронізація (автоматично з DMMF), OpenAPI (оновити `app/api/openapi.json`), MCP (зі схеми).

**Юніт з `cr` (монстр 5e)** у `createBattleParticipantFromUnit`:
- майстерність = таблиця CR (якщо `proficiencyBonus` не задано явно інакше — форма підставляє значення з CR при виборі CR, ДМ може змінити);
- `abilities.damageModel = "5e"` — шкода зброї й заклинань іде шляхом 4c-2 (кубик + модифікатор, властивості `traits`);
- СК = `saveDcBase + prof + найбільший мод. Інт/Мдр/Хар` (без тіру); `balance/stats.ts` рахує так само для юнітів з `cr`;
- `saveProficiencies` у snapshot (їх читає `rollSave`, 4a);
- мультиатака: `multiattack > 1` → синтетичне пасивне вміння `modifyStat attacksPerAction flat (multiattack − 1)` (рушій читає лише через `collectModifiers`);
- `battleData.legendary = { actions, actionsLeft, resistLeft }`, коли поля > 0;
- `xp` у `basicInfo` для авто-досвіду й балансу.

Юніт без `cr` — нульова зміна (тест на весь snapshot HOMM-юніта).

### 3. Легендарні дії

- Новий базовий вид дії `legendary` у роуті `core-action` (`anyTurn`, лише ДМ): `{ action: "legendary", actorId, option: { kind: "attack", attackIndex, targetIds } | { kind: "ability", abilityId, targetIds? } }`.
- Умови: у учасника `legendary.actionsLeft ≥ вартість`, зараз **не** його хід, він дієздатний (не `incapacitated`). Атака коштує 1 і йде через `resolveServerAttack` (як підготовлена атака, одна атака без мультиатаки); вміння — нове обмеження `limits.legendaryCost: 1–3`: таке вміння використовується лише як легендарна дія (у звичайному ході прихована).
- `actionsLeft` відновлюється на початку ходу цього учасника (`processStartOfTurn`).
- UI: у панелі ДМ на картці учасника з `legendary` — кнопка «Легендарна дія (N/M)» → `ResponsiveDialog` з вибором атаки/вміння і цілей (перевикористати вибір цілей діалогу базових дій 4b).

### 4. Легендарний опір

Автоматичний: коли учасник з `legendary.resistLeft > 0` провалює рятівний кидок, провал стає успіхом, `resistLeft − 1`, у лозі «Легендарний опір (N залишилось)». Один помічник `resolveSave(participant, saveResult)` → `{ result, participant }` — викликається там, де результат `rollSave` змінює стан учасника (`spell/cast/outcome.ts`, `concentration`, `save-ends`, `grapple`, `fire-burst`). Лист персонажа не зачіпає (юніти там не кидають). Однаково для 2014 і 2024.

### 5. Дії лігва

Без нового механізму: дія лігва — вміння юніта з тригером `roundStart` (початок раунду ≈ ініціатива 20) і `perRound: 1`. Редактор вмінь показує для тригера `roundStart` підказку «дія лігва»; опис у `abilities.md`.

### 6. Баланс за бюджетом XP (`encounters.balance: "xp"`)

Чистий модуль `lib/utils/battle/balance/xp-budget.ts`, спільний для UI й сервера:
- **2014:** пороги героя за рівнем (легкий / середній / складний / смертельний, DMG), сума по групі; XP ворогів × множник кількості (1 → ×1, 2 → ×1.5, 3–6 → ×2, 7–10 → ×2.5, 11–14 → ×3, 15+ → ×4; група < 3 — крок вгору, ≥ 6 — крок вниз); складність — найвищий досягнутий поріг.
- **2024:** бюджет героя за рівнем (низька / помірна / висока), сума по групі; XP ворогів без множника.
- Результат: `{ edition, enemyXp, adjustedXp, thresholds, difficulty, missingCr: unitIds[] }`.

У режимі `xp`:
- підготовка бою показує складність і XP (`BalanceSummary` має другий вигляд), без множників HP/шкоди; юніти без CR — попередження «немає CR, не враховано»;
- старт бою не масштабує ворогів (множники 1); `scaleEnemiesForFairBattle` не викликається;
- автопідбір (`balance-post`) отримує цільову складність (чипи в UI, default — середня/помірна) і набирає юнітів з CR до порогу.

`fair` — без змін (`computeFairScaling`). Правило `balance.md` «setup і старт рахують однаково» зберігається в обох режимах.

### 7. Авто-досвід (`encounters.autoXp` і `outOfCombat.xp`)

У `saveBattle` (гілка `completing`, та сама транзакція, після `persistCharacterResources`) при **перемозі**: сума `xp` ворогів (`originalSide` — вороги, статус мертвий/непритомний; без призваних `summonedBy`, без слотів додаткового ходу), ділиться порівну (`xpShare`, `split`) між героями-персонажами, що були в бою (на мапі, не резерв, живі чи ні); `addExperience` з блокуванням рядків (`lockCharacters`); журнал `xp` з `battleId`. У лозі бою — рядок «Досвід: N кожному». Повторне завершення (відкат) — той самий захист, що в 4d (запис лише при переході в COMPLETED).

### 8. UI

З 6 CSV у `docs/units` через UI проходить один.
- Інші 9 ресурсів (`CONTENT_RESOURCES`: races, classes, spells, spell-groups, main-skills, skills, artifacts, artifact-sets, tracks) і дерева скілів — лише створення по одному (UI, REST, MCP `content_create`) або бандл усієї кампанії при створенні нової.

### 1. Реєстр полів імпорту (`lib/utils/content/import/fields/`)

Для кожного типу — список полів, спільний для клієнта й сервера (без `server-only`):

```ts
type ImportField = {
  key: string;                 // шлях у тілі create (напр. "armorClass", "basicInfo.name")
  label: string;               // українська назва колонки в прикладі
  aliases: string[];           // синоніми заголовків (укр/англ, регістр і пробіли ігноруються)
  type: "string" | "int" | "number" | "bool" | "enum" | "list" | "dice" | "cr"
      | "ref" | "refList" | "json" | "attacks" | "abilitiesText";
  enumValues?: readonly string[];      // значення й укр. підписи приймаються
  ref?: ContentKind;                   // "ref"/"refList": назва → id у кампанії
  required?: boolean;
  example: string;                     // значення для прикладу CSV
};
```

Типи: `list` — роздільники `,` `;` `|`; `dice` — «1к6+2», «2d8 + STR»; `cr` — «1/4», «0.25», «5»; `bool` — так/ні/true/false/1/0/+; `attacks` — наявна текстова мова юнітів або JSON; `abilitiesText` — текст стає вміннями-нотатками (як зараз), JSON-масив — справжніми вміннями (Zod `AbilitiesSchema`); `json` — JSON у клітинці (вкладені поля: `features`/`subclasses` класу, `targeting`/`resolution`/`spellEffects` заклинання, `weapon` артефакта).

Покриття: units (з полями 5e, рятівними, імунітетами, моралю, цілями; синоніми — усі заголовки нинішнього CSV-імпорту, тож старі файли працюють), spells, skills, main-skills, spell-groups, races, classes, artifacts, artifact-sets. Дерева скілів — лише JSON (одне дерево на расу, `save_skill_tree`). Треки — поза обсягом (файли).

### 2. Перетворення й перевірка (`lib/utils/content/import/`)

- `parseTable(text)` — `csv-parse` (перенести в dependencies; браузерна збірка): автороздільник (`,` `;` `\t`), BOM, лапки з переносами, порожні рядки; JSON-файл — масив об'єктів або один об'єкт.
- `autoMap(headers, fields)` → `{ [header]: fieldKey | null }` за синонімами; ручний мапінг поверх.
- `transformRow(row, mapping, fields)` → `{ value, issues }` — значення в тіло create; посилання лишаються назвами (розв'язує сервер).
- Сервер: `importContent(actor, kind, { rows, mode, dryRun })` у `lib/server/content/import.ts` через сервіс ресурсу (`assertCan`, `CONTENT_RESOURCES`): посилання за назвою (без урахування регістру) у межах кампанії; Zod create/update ресурсу на кожен рядок; режим `create` (дубль назви — помилка рядка) / `update` (за назвою: оновити, інакше створити) / `skip` (наявні пропустити); валідні рядки пишуться в одній транзакції, невалідні — у звіті. Відповідь: `{ results: { row, status: "created" | "updated" | "skipped" | "error", name?, issues[] }[], counts }`. `dryRun` — та сама перевірка без запису (крок попереднього перегляду). Ліміт — 500 рядків за запит (клієнт ділить файл на частини). Кеш довідника інвалідовується як при звичайному записі.

### 3. API

- `POST /api/campaigns/[id]/content-import/[kind]` — тіло `{ rows, mode, dryRun? }`; операція `<kind>.import` у `CONTENT_OPERATIONS` (OpenAPI), права `content:write`. Наявний `POST /units/import` лишається сумісним (делегує в новий шлях, мапінг — нинішні синоніми).
- `GET /api/campaigns/[id]/content-import/[kind]/example.csv` — приклад: заголовки (`label`) і 2–3 рядки (`example`).
- `GET /api/campaigns/[id]/content-export/[kind]` — експорт кампанії в тому самому форматі (посилання — назви, вкладене — JSON у клітинці), тож «вивантажив → змінив → завантажив» працює; `content:read`.
- MCP: інструмент `content_import(kind, rows, mode, dryRun)` (рядок в `AI_TOOLS`, scope `content:write`), щоб зовнішній агент переносив дані сам.

### 4. AI-мапінг (опційно)

`POST /api/campaigns/[id]/content-import/[kind]/ai-map` (ДМ, з ключем AI): тіло `{ headers, sample }` (≤ 5 рядків, обрізані клітинки) → `generateObject` з Zod-схемою відповіді `{ mapping: { [header]: fieldKey | null }, notes: string[] }` (fieldKey — лише з реєстру; інше відкидається). Шаблон — `generate-backstory.ts`: охорона, rate limit, `pickDmTextModel`, `aiErrorMessage`; ключ не залишає сервер. Результат лише заповнює крок мапінгу — ДМ бачить і змінює. Без ключа кнопка прихована.

### 5. UI

Спільний майстер `ContentImportWizard` (`components/content-import/`, `ResponsiveDialog hud`), хуки в `lib/hooks/content-import/`, клієнт у `lib/api/content-import.ts`:
1. **Файл** — CSV/TSV/JSON (XLSX — підказка «збережіть як CSV»); посилання «Завантажити приклад CSV».
2. **Колонки** — таблиця «колонка файлу → поле» (select з полями типу, «пропустити»), автозбіг, кнопка «Підказати AI»; обов'язкові незіставлені поля підсвічуються. Мапінг запам'ятовується в `localStorage` за набором заголовків.
3. **Перегляд** — `dryRun`: перші 50 рядків, статуси й помилки по рядках, лічильники; режим (створити / оновити за назвою / пропустити наявні).
4. **Імпорт** — запис частинами, підсумок, «Завантажити звіт помилок CSV».

Кнопки «Імпорт» і «Експорт CSV» — на сторінках бібліотеки ДМ кожного типу (юніти — замість `UnitImportDialog`), а також на шаблоні.

### 1. Конвеєр

```

                               друкарських помилок
  → data/templates/srd-5.2/{spell-groups,spells,races,classes,units,artifacts}.json   (комітимо)
  → data/templates/srd-5.2/manifest.json   (SHA, дата, лічильники, credits)
```

## 4f-2. Дизайн: броня 5e і числа класів

Розвідка (2026-10-23):
- **КЗ сьогодні.** Герой: `combatStats.armorClass = Character.armorClass` — число, яке ДМ вводить руками (`from-character.ts:176`), і в режимі класів теж. Юніт: `unit.armorClass` (у монстрів SRD — уже готове КЗ). Далі КЗ рахує лише `statWithModifiers(…, "armor", base)` (`getEffectiveArmorClass`, `attack/bonus.ts:137`, лист `sheet/lines.ts`): `armor` — динамічний стат (`DYNAMIC_STATS`), бонуси — `modifyStat armor` з вмінь (щит SRD — `+2`, артефакти HOMM, Shield). Мод. Спр до КЗ ніде не додається; `computeArmorClass`/Unarmored Defense немає.
- **Слот броні є** (`ArtifactSlot.ARMOR`), але в артефакта немає моделі броні. Зброя живе в `weapon` тіла create/patch ↔ записи в колонці `modifiers` (`weaponStatsColumns`/`weaponStatsFromRow`, білий список `ArtifactModifierType`); snapshot уже несе `equippedArtifacts[].modifiers`. Шаблон за цим зразком — без міграції, бандл/синхронізація/експорт уже возять `modifiers`.
- **Перешкода скритності** виражається наявним прапорцем `checkDisadvantage { skills: ["stealth"] }` (ключ `stealth` є в `DND_SKILLS`, його читає `rollCheck` і «Сховатися» 4b). Вимога Сили — нічим: `speed` — запечений стат (`BAKED_STATS`), умова на запечених статах заборонена (`bakePassives` бере лише вміння без `condition`).
- **Формули.** `formulaContext` має лише `hero_level` (сума рівнів), `lost_hp_percent`, `morale`, `cells_moved`; модифікаторів характеристик, майстерності й рівня в класі немає. Кубики (`Amount`) — рядок `NdM`, без змінних. `perRest.uses` — лише число. Вміння класу збирає `classResolved` (`abilities/build/collect.ts`), і саме там відомий рівень у класі; на snapshot класи не зберігаються.
- **Ресурси.** Ліміт — лічильник одного вміння (`abilityUsage[key]`); спільних пулів (ці/фокус, очки чаклунства, Channel Divinity, Lay on Hands) немає. 4d зберігає `resources.charges[key] = { used, rest }` і скидає за `rest` — пул туди лягає без зміни схеми.
- **Дані SRD.** `ClassFeatureItem.column_value` **заповнений** для всіх колонок таблиць класів (звіт мапінгу помилявся — він дивився інший зріз): Rages 2…6, Rage Damage +2/+3/+4, Bardic Die D6…D12, Sneak Attack 1d6…10d6, Martial Arts 1d6…1d12, Focus/Sorcery Points 2…20, Channel Divinity 2…4, Second Wind 2…4, Wild Shape 2…4, Favored Enemy 2…6, Unarmored Movement +10…+30 ft. Броня (`Armor.json`, 12 + щит): `ac_base`, `ac_add_dexmod`, `ac_cap_dexmod` (2 у середньої), `strength_score_required` (13/15), `grants_stealth_disadvantage`; категорії немає — виводиться (без Спр → важка, межа 2 → середня, інакше легка).
- Конвертер 4f-1 відкидає колонки (`CLASS_TABLE_DATA`), `druid_wild-shape-uses`, обрізає вміння з > 6 рядками рівнів до першого (Unarmored Movement), а оверрайд дає одне вміння на фічу (Channel Divinity і Monk's Focus мають по 2–3 опції в одному тексті). У шаблоні 24 оверрайди умінь класів.

### 1. Правила

Нової секції немає: модель броні й числа класів діють лише для героя в режимі класів (`rules.classes.enabled` і непорожні `classes`), як 4c-1/4c-2 (рекомендоване; користувач спав — переглянути).
- Альтернатива: перемикач `classes.armorModel` — зайва вісь налаштувань, без класів модель усе одно не має сенсу.

### 2. Дані

**Броня артефакта.** `armor?: ArmorStats` у `createArtifactSchema`/`patchArtifactSchema` (лише для `slot: "armor"`, Zod-refine), зберігається записами в `modifiers` за зразком зброї (рекомендоване; користувач спав — переглянути):

```ts
ArmorStats = {
  category: "light" | "medium" | "heavy",
  base: number,                    // 1–30, база КЗ
  dexCap?: number | null,          // порожньо — за категорією: легка без межі, середня 2, важка 0
  strength?: number,               // 1–30, вимога Сили
  stealthDisadvantage?: boolean,
}
```

Типи записів — окремий enum `ArmorModifierType` (`armorCategory`, `armorBase`, `armorDexCap`, `armorStrength`, `armorStealth`), щоб `weaponStatsFromRow` їх не підхопив; `armorStatsFromRow(row)` — спільний для сервера, клієнта й snapshot (`equippedArtifacts[].modifiers`). Поле `armor` проходить ресурс `artifacts`, поле імпорту 4f-0 (`json`), експорт CSV, OpenAPI (оновити `app/api/openapi.json`) і MCP (зі схеми).
- Альтернатива: колонка `artifacts.armor Json?` — міграція й ручне відображення в бандлі заради того самого; модель зброї вже в `modifiers`.
- Альтернатива: броня як `modifyStat armor +N` (наближення зі звіту мапінгу) — середня втрачає межу Спр, важка хибить на мод. Спр.

**Таблиця класу.** Нова колонка `classes.columns Json @default("[]")` (міграція лише розширює; таблиця вже з RLS):

```ts
columns: {
  key: string,                     // kebab-case, унікальний у класі: "rages", "sneak-attack"
  label: string,                   // "Rages", "Sneak Attack"
  values: string[],                // рівно 20 клітинок: "2", "+2", "1d6", "D8", "+10 ft.", "" (немає)
  pool?: { rest: "short" | "long" },   // колонка — максимум спільного пулу (§3.5)
}[]                                // до 12 колонок
```

Колонки належать класу; підклас посилається на колонки свого класу (рекомендоване; користувач спав — переглянути). Розбір клітинки — `parseColumnValue`: число зі знаком і одиницею → число (`"+10 ft."` → 10), `D8` → `1d8`, `NdM` → кубики, порожньо → немає значення. Поле проходить ресурс `classes`, Zod create/update, імпорт/експорт, бандл і синхронізацію (з DMMF), OpenAPI/MCP.
- Альтернатива: таблиця значень усередині кожного вміння (`{ scale: { 1: 2, 3: 3, … } }`) — дублює одну колонку в кількох уміннях (Rage: використання і шкода), класова таблиця на листі тоді не показується.
- Альтернатива: лише змінна `class_level` у формулах — не дає ступінчастих таблиць і кубиків (Підступна атака, Martial Arts).

### 3. Рушій

**3.1. КЗ 5e** (`lib/utils/characters/classes/armor-class.ts`, чиста, спільна для учасника, листа й форми). Для героя в режимі класів після `bakePassives` (мод. Спр уже з расовими бонусами):
- є вдягнений артефакт зі `armor` у слоті «Броня» → `base + min(мод. Спр, межа)` (важка — без Спр);
- немає → `10 + мод. Спр`;
- результат пишеться в `combatStats.armorClass`; щит, Defense, Shield, магічні +N — як і досі `modifyStat armor` поверх (через `collectModifiers`).
`Character.armorClass` у режимі класів не читається — природна броня й інші бази стають уміннями (рекомендоване; користувач спав — переглянути). HOMM-герой і герой без класів — без змін.
- Альтернатива: `Character.armorClass` як база «без броні» — ДМ вводить 13 для природної броні, але подвійний облік із Unarmored Defense і незрозуміло, що перемагає.

**3.2. Наслідки броні.** Той самий крок додає учаснику синтетичне вміння з джерелом-артефактом (видно на листі й у бою, як мультиатака 4e): `checkDisadvantage stealth` при `stealthDisadvantage`; при `strength` > запеченої Сили — `modifyStat speed −10` (редакція 2024; застосовується одразу, бо запікання вже минуло). Майстерність у броні не перевіряється (§6).

**3.3. Умова `armorWorn`** у `ConditionSchema`/`CONDITION_REGISTRY`: `{ type: "armorWorn", categories: ("none" | "light" | "medium" | "heavy")[], shield?: boolean }` — правда, коли категорія вдягненої броні в списку (і щит є/немає, якщо вказано). Щит = артефакт у слоті «Щит» без статів зброї (легка зброя другої руки 4c-2 щитом не є). Умова статична (спорядження в бою не змінюється), тож `bakePassives` і перевірка вміння дозволяють її на запечених статах — і лише її (усередині `all`/`any`/`not` теж). Так виражаються Unarmored Defense (`armor` + формула, `categories: ["none"]`), Unarmored Movement (`speed`, без броні й щита), Fast Movement і Rage (не важка).

**3.4. Значення за рівнем класу.**
- Змінні формул у `formulaContext` (рушій, живі): `str_mod` … `cha_mod` (запечені модифікатори), `prof`, `class_level` (запасне значення — `hero_level`).
- Посилання на колонку `{ scale: "<key>" }` — новий варіант у `FlatSchema`, `AmountSchema` і в `perRest.uses`; `perRest.uses` також приймає `{ formula }`.
- **Розв'язання при збиранні** (`applyClassScale` у `classResolved`): для вмінь класу/підкласу `{ scale }` → значення колонки на рівні в цьому класі (число або кубики `NdM`), `class_level` у рядках формул → число рівня в класі (решта змінних лишається рушію). Після запікання `resolveLimitFormulas` перетворює `perRest.uses { formula }` на число (мін. 1). Рушій і лічильники бачать звичайні числа й кубики — `usage.ts`, `resolveAmount` і підписи лімітів не змінюються (рекомендоване; користувач спав — переглянути).
- Нерозв'язане посилання (вміння раси/скіла з `{ scale }`, неіснуючий ключ) — проблема вміння в редакторі («Посилання на таблицю класу — лише у вміннях класу»), у рушії — 0 / вміння недоступне. Zod класу перевіряє, що кожен `scale`/`pool` у `features` і `subclasses` посилається на наявну колонку.
- Альтернатива: змінна `class_level:<classId>` у рушії з рівнями класів на snapshot — більше snapshot і не розв'язує кубики.
- Альтернатива: розв'язання в рушії на кожен виклик — кожне місце, що читає `uses`/кубики, отримує учасника й таблицю.

**3.5. Спільні пули.** `LimitsSchema.pool: { key, cost }` (`cost` 1–20): вміння можна використати, коли в пулі лишилось ≥ `cost`; використання списує `cost`. Пул — колонка класу з `pool`; при збиранні ключ стає `pool:<classId>:<key>` (пули різних класів мультикласу окремі), учасник отримує `battleData.pools: Record<key, { label, max, rest }>` (max — значення колонки на рівні в класі; snapshot пишеться разом із `snapshotHash`, як завжди). Лічильник — `abilityUsage[poolKey].battle` (той самий механізм, що й `perBattle`); `withinCountLimits`/`recordUse` враховують `pool`. При `persistResources` пул переживає бій через `resources.charges[poolKey] = { used, rest }` — 4d вже скидає заряди за видом відпочинку (рекомендоване; користувач спав — переглянути). Вміння поза класом з `pool` — недоступне + проблема в редакторі.
- Альтернатива: пули як окрема сутність контенту — новий ресурс заради 5 пулів SRD.
- Альтернатива: без пулів, кожна опція з власним `perRest` — Flurry/Patient Defense/Step of the Wind і Channel Divinity рахувались би окремо, що суперечить правилам.

**3.6. Умови для Підступної атаки.** Подія `hit` (і `attack` фази `after`) отримує `rollMode?: "advantage" | "disadvantage" | "normal"` з `rollModeReasons`; нові умови `{ type: "attackRollMode", mode }` і `{ type: "allyAdjacent" }` (інший живий союзник власника в межах 1 клітинки від цілі; без позицій на мапі — хибно). Sneak Attack = `any[advantage, all[allyAdjacent, not disadvantage]]`, `perTurn: 1`. Вимога фехтувальної/дальньої зброї не перевіряється (§6).

**3.7. Прапорець `evasion`** (`abilities.md`): рятівний Спр з «половиною при успіху» → успіх 0, провал половина; у `spell/cast/outcome.ts` (і в `maneuvers/fire-burst.ts`, якщо там рятівний Спр); не діє на недієздатного (`incapacitated`).

### 4. Конвертер і шаблон

- **Броня** (`convert/artifacts.ts`): 12 обладунків → артефакти `slot: "armor"` з `armor` (категорія — виведена), опис «Light/Medium/Heavy Armor. AC … Strength … Stealth: Disadvantage. Cost … Weight …»; щит — як у 4f-1.
- **Колонки** (`convert/classes.ts`): рядки `CLASS_TABLE_DATA` → `columns` (ключ — хвіст slug без класу, `sneak-attack-column-data` → `sneak-attack`; без `PROFICIENCY_BONUS` і слотів — їх рахує `classSpellSlots`); `druid_wild-shape-uses` і `monk_unarmored-movement` (19 рядків) стають колонками, а не вміннями-дублями. Таблиця `overrides/classes.ts`:
  - `POOL_COLUMNS`: `monk_focus-points` (short), `sorcerer_sorcery-points` (long), `cleric_/paladin_channel-divinity-uses` (short), синтетична `lay-on-hands` (long);

### 7. Перевірка 4f-2

Тестові дані видаляються.
- Документи: `battle.md` («5e: броня, пули»), `abilities.md` (`armorWorn`, `scale`, `pool`, змінні формул, `evasion`, умови Підступної атаки), `content-api.md` (`armor`, `columns`), STATUS, хендоф, пам'ять.

## 4f-3. Дизайн: магічні предмети

Розвідка (2026-10-23):
- **Інвентар.** `character_inventories.equipped` — `Record<ключ клітинки, artifactId>` (сітка `ARTIFACT_GRID_9`: 9 клітинок, один перстень, клітинки для слота `item` немає), `stash` — множина id (`normalizeStash` прибирає дублікати), `items` — вільні `SpecialItem { id, name, quantity, consumable }` з дією `useItem` (−1, на 0 — видалення). Артефакт слота `item` можна лише тримати в сховищі — «Вдягнути» для нього немає, і в бій потрапляють тільки вдягнені (`loadEquippedArtifactRows`).
- **Унікальність.** Один артефакт = один власник на кампанію: `findHolder` (`lib/utils/artifacts/ownership.ts`) перевіряють `grant` (`stash/apply-stash.ts`), вдягання (`inventory/update-inventory.ts`) і «вільні артефакти» для видачі (`read-free-artifacts.ts`); довідник показує власника (`lib/cache/artifact-reference.ts`), передача — `planTransfer`. Тому SRD-«Longsword» з шаблону 4f-1 зараз може бути лише в одного героя кампанії, а дві однакові зброї в «Зброя» + «Щит» відхиляються (`ARTIFACT_ALREADY_EQUIPPED`).
- **Читачі `equipped`/`stash`** (усі беруть значення як id рядка `artifacts`): `extract-artifacts.ts`, `load-character-context.ts` (`equippedArtifactIds`), `extract-attacks.ts` (id атаки = id артефакта, `:off` для другої руки), `update-inventory.ts` (`canEquipOffHand`), `apply-stash.ts`, `read-stash.ts`, `read-free-artifacts.ts`, `transfer-artifact.ts`, `read-roster.ts`, `start-build-context.ts`, `artifact-reference.ts`, клієнтські `CharacterArtifactsSection`/`useStash`.
- **Модель артефакта** — колонки `slot`, `rarity` (common…legendary, `epic` замість very rare), `bonuses` (`attackBonus` зброї), `modifiers` (статі зброї 4c-2 і броні 4f-2 — без міграцій, бандл/синхронізація/експорт уже їх возять), `abilities`, `setId`. «+N» зброї — лише до атаки: окремого бонусу шкоди конкретної зброї немає; `damageBonus` уміння діє на всі атаки власника (фільтр `melee|ranged|magic|physical|all`). Подія `hit` не несе id зброї. Ефекту «створити заклинання з предмета» немає.
- **Ресурси.** Пули 4f-2 (`limits.pool`, `battleData.pools`, лічильник `abilityUsage[poolKey]`, переживання бою через `resources.charges[poolKey] = { used, rest }` і скидання відпочинком 4d) — готовий механізм зарядів; ключ пулу зараз лише `pool:<classId>:<key>`.
- **Дані SRD** (`MagicItem.json`, 760): weapon 445, wondrous 138, armor 104, ring 22, potion 18, wand 15, staff 12, rod 6; рідкість uncommon 178 / rare 281 / very-rare 179 / legendary 120 / common 1 / artifact 1; налаштування — 381. **513 рядків — варіанти** з FK `weapon` (416) або `armor` (97) на базовий предмет; вони згортаються в **31 сімейство**: зброя — `+1/+2/+3` (по 38), Weapon of Warning, Defender, Giant Slayer, Holy Avenger, Nine Lives Stealer, Vicious (по 38), Flame Tongue (29), Luck Blade (7), Frost Brand, Life Stealing, Wounding (по 6), Dancing (5), Sharpness, Vorpal (по 4), Berserker (3), Hammer of Thunderbolts, Oathbow (по 2); броня — `+1/+2/+3` (по 13, разом зі щитом), Armor of Resistance, Armor of Vulnerability, Demon (по 12), Adamantine, Mithral (по 8), Elven, Dwarven, Etherealness (по 2). Рідкість і налаштування в сімействі однакові (одна вада: Armor of Resistance (Splint) без налаштування). Назва — три шаблони: `База (+1)`, `Flame Tongue База`, `База of Wounding` / `Defender (База)`. Решта **247 без FK**: 2 загальні дублікати сімейств (Defender, Holy Avenger), Dragon Slayer («будь-яка зброя» без розгортки), 17 набоїв (Ammunition +N і 14 Slaying), ~16 предметів із фіксованою базою в тексті (Sun Blade → Longsword, Dagger of Venom, Mace of Smiting, Animated Shield, Dragon Scale Mail, бойові посохи → Quarterstaff…). Зілля лікування (4 ступені в одному рядку) і Spell Scroll лежать у `Item.json`, не в `MagicItem`. `cost`/`weight` порожні; «+N» — лише в назві або «determined by rarity»; заряди — прозою («has 7 charges… regains 1d6 + 1 expended charges daily at dawn», 41 предмет + 2 сімейства), опори — прозою (10), «Strength is 19 while…» (8 з поясами).

### 1. Правила

Нова секція `rules.items` (рекомендоване; користувач спав — переглянути):

```ts
items: {
  enabled: false,          // налаштування, носіння предметів зі сховища, витратні предмети в бою
  attunementLimit: 3,      // 1–10
}
```

Вкладка «Предмети» на `dm/rules`, рядок у `MECHANIC_REGISTRY`, хеш синхронізації. Default — HOMM5 і наявні кампанії без змін; пресет SRD: `enabled: true, attunementLimit: 3`. Властивості, неунікальні предмети й заряди — властивості контенту, від правил не залежать (без такого контенту нічого не змінюється).
- Альтернатива: без секції, прив'язати до `classes.enabled` (як 4f-2) — ліміт налаштування не налаштовується, а HOMM-кампанія без класів не може ввімкнути витратні предмети.

### 2. Дані

**2.1. Предмет артефакта.** `item?: ItemStats` у `createArtifactSchema`/`patchArtifactSchema`, записами в `modifiers` з окремим enum `ItemModifierType` — за зразком зброї й броні, без міграції `artifacts` (рекомендоване; користувач спав — переглянути):

```ts
ItemStats = {
  unique?: boolean,                  // default true — як HOMM; false — звичайне спорядження, тримають багато героїв
  property?: {                       // артефакт — властивість, видається лише разом із базою
    appliesTo: {
      kinds: ("weapon" | "armor" | "shield")[],
      attackType?: "melee" | "ranged",
      armorCategories?: ("light" | "medium" | "heavy")[],
      bases?: string[],              // назви базових предметів, коли набір вужчий за фільтр (≤ 60)
    },
    nameTemplate?: string,           // "{base} +1", "Flame Tongue {base}", "{base} of Wounding"; порожньо — "{name} ({base})"
    overrides?: { stealthDisadvantage?: false, strength?: null, damageType?: string, addTraits?: WeaponTrait[] },
  },
  attunement?: boolean,
  charges?: { max: number, rest: "short" | "long" | null },   // 1–50; null — не відновлюються
  consumable?: boolean,              // видається кількістю в `items`, витрачається
}
```

Плюс поле зброї `damageBonus?: number` (−20…20) у `WeaponStatsSchema` (запис `modifiers`) — «+N до шкоди цією зброєю». `itemStatsFromRow(row)` — спільний для сервера, клієнта й snapshot. Zod-refine: `property` лише в слотах weapon/range_weapon/armor/shield і без власних `weapon`/`armor`; `consumable` несумісний з `property` і `charges.rest`. Поле проходить ресурс `artifacts`, імпорт 4f-0 (`json`), експорт CSV, OpenAPI (оновити `app/api/openapi.json`) і MCP.
- Альтернатива: колонки `artifacts.kind`/`unique`/`charges` — міграція й ручне відображення в бандлі/синхронізації заради того самого.

**2.2. Посилання на предмет (ref).** Значення в `equipped`/`stash`/`attuned` — рядок `"<artifactId>"` (як зараз) або `"<baseId>+<propertyId>"` — складений предмет; `parseItemRef`/`itemRef` у `lib/utils/items/ref.ts` (рекомендоване; користувач спав — переглянути). Окремого рядка примірника немає: ідентичність примірника = (персонаж, ref); заряди живуть у `Character.resources.charges` персонажа, налаштування — у його інвентарі. Наслідок: два однакові складені предмети в одного героя ділять заряди (прийнятно).
- Альтернатива: матеріалізований артефакт на кожну видачу («Longsword Flame Tongue» як новий рядок `artifacts` з `instanceOf`) — бібліотека й бандл/синхронізація засмічуються копіями, а звичайна зброя все одно потребує копії на кожного героя.
- Альтернатива: таблиця `character_items` (примірник з власними зарядами) — найчистіше, але переписує всіх читачів `equipped`/`stash`, транзакції сховища й передачу; відкласти до потреби в різних станах однакових предметів.

**2.3. Налаштування.** Колонка `character_inventories.attuned Json @default("[]")` — масив ref (міграція лише розширює; таблиця вже з RLS) (рекомендоване; користувач спав — переглянути). Інваріант: кожен ref у `attuned` тримається героєм (`equipped` або `stash`) і має `attunement`; `stash`/`revoke`/передача/видалення предмета знімають налаштування.
- Альтернатива: у `Character.resources` — там лише витрачене, і PATCH ресурсів тільки ДМ.

**2.4. Витратні.** `SpecialItem` отримує `artifactId?` (JSON, без міграції): витратний предмет з контенту живе в `items` з кількістю, а не в `stash` (рекомендоване; користувач спав — переглянути). Видача витратного додає кількість до наявного запису з тим самим `artifactId`. Вільні `SpecialItem` без `artifactId` — як зараз.

### 3. Складання предмета (`lib/utils/items/compose.ts`, чисте)

- `matchesAppliesTo(base, property)`: база — не властивість, має статі зброї (kind weapon: слот weapon/range_weapon) або броні (kind armor: слот armor + `armor`; kind shield: слот shield без статів зброї); `attackType`, категорії броні, `bases` (назва без регістру).
- `composeItemRow(base, property)` → синтетичний рядок артефакта: `id` = ref, `name` = `nameTemplate` з `{base}`, `slot`/`icon` бази (іконка властивості, якщо є), `rarity`/`description`/`setId` властивості, `bonuses` — сума (`attackBonus`), `modifiers` — статі бази + `damageBonus` властивості (сума) + `overrides` (Mithral прибирає вимогу Сили й перешкоду скритності; Sun Blade-подібні — тип шкоди, властивості зброї), `abilities` = база ++ властивість (джерело кожного — ref, назва — складена), `item` властивості (налаштування, заряди).
- `resolveItemRows(refs, rowsById, { attuned, rules })` — **єдиний вхід** для всіх читачів §Розвідка: розбирає ref, складає, відкидає невідомі (видалений артефакт — тихо, як зараз). При `items.enabled` предмет з `attunement` без налаштування дає лише рядок бази (у складеного) або рядок без `bonuses`/`abilities` (в унікального) — неналаштований предмет нічого не дає, але лишається зброєю/бронею.
- **Носіння** (`activeItemRefs(inventory, rules)`): вдягнені + при `items.enabled` предмети слотів `item` і `ring` зі сховища (5e не має клітинок для чудесних предметів; межу дає налаштування) (рекомендоване; користувач спав — переглянути). HOMM — лише вдягнені. Альтернатива: додаткові клітинки сітки — ламає сітку 3×3 і все одно потребує ліміту.

### 4. Унікальність і видача

- `findHolder` стає ref-орієнтованим: артефакт тримається, якщо його id — ref або база/властивість у складеному ref. Перевірка застосовується лише до `unique !== false`; властивість сама по собі не унікальна, але унікальна база (HOMM-меч) у складеному ref лишається одна на кампанію (рекомендоване; користувач спав — переглянути).
- Дублікати в `equipped` дозволені лише для неунікальних (два кинджали SRD у «Зброя» + «Щит»).
- `grant` (ДМ): `{ artifactId, baseId?, quantity? }` — властивість вимагає `baseId`, що проходить `matchesAppliesTo` (422 `ITEM_BASE_MISMATCH`); витратний — `quantity` 1–99 у `items`; інакше — ref у `stash` як зараз. Журнал інвентаря пише складену назву.
- Нові дії сховища `attune`/`unattune` `{ ref }` (власник або ДМ; 409 `ATTUNEMENT_LIMIT` понад `attunementLimit`, 409, поки герой в активному бою — `battle-lock.ts`; лише при `items.enabled`). Передача (`transfer-artifact.ts`) переносить ref і знімає налаштування.
- «Вільні артефакти» для видачі: неунікальні й властивості — завжди; довідник для неунікальних показує «спорядження» замість власника.
- Схеми тіл (`stash-schema.ts`, inventory) приймають ref за регуляркою `^[a-z0-9]+(\+[a-z0-9]+)?$`.

### 5. Рушій

**5.1. Бонуси предмета.** `damageBonus` зброї потрапляє в `BattleAttack.damageBonus` (`extract-attacks.ts`) і додається пласким числом у формулі шкоди цієї атаки (`compute.ts`; та сама функція для прев'ю й сервера), для HOMM і 5e (у HOMM-контенті поля немає). «+N до КЗ/рятівних» — пасивні вміння властивості (`modifyStat armor|savingThrow`) — через `collectModifiers`, як усе.

**5.2. Умова `withThisItem`** у `ConditionSchema`/`CONDITION_REGISTRY`: правда, коли атака події зроблена предметом-джерелом уміння. Події `attack`/`hit` отримують `attackSourceId` (id атаки без `:off` = ref). Так виражаються райдери «extra 2d6 Fire damage on a hit» (Flame Tongue, Frost Brand, Vicious, Wounding) і без умови не чіпляються до іншої зброї.

**5.3. Прапорець `critImmunity`** (`abilities.md`): крит по власнику стає звичайним влучанням (Adamantine Armor, Armor of Invulnerability-подібні) — у розв'язці атаки після кидка.

**5.4. `modifyStat` для характеристик з `atLeast: N`** (лише запечені характеристики, у `bakePassives`): значення = max(власне, N) — Amulet of Health, Gauntlets of Ogre Power, Headband of Intellect, Belt of Giant Strength ×5. Інші стати `atLeast` не приймають (Zod).

**5.5. Заряди = пул предмета.** Уміння артефакта з `limits.pool { key: "charges", cost }` при збиранні отримує ключ `pool:item:<ref>`; учасник — `battleData.pools[key] = { label: назва предмета, max: charges.max, rest }` (snapshot з `snapshotHash`, як завжди). Лічильник, недоступність при нестачі, переживання бою (`resources.charges`) і скидання відпочинком — механізм 4f-2/4d без змін; `rest: null` — пул не скидається. Відновлення «1d6 + 1 на світанку» спрощено до повного на довгому відпочинку (рекомендоване; користувач спав — переглянути). Ключ `charges` поза артефактом із `charges`/`consumable` — проблема вміння в редакторі й недоступність у рушії (як `CLASS_REF_OUTSIDE`).
- Альтернатива: кидок відновлення на відпочинку — відпочинок мав би читати інвентар і артефакти кожного героя; разом з ДМ-правкою зарядів (§6) не варте 4f-3.

**5.6. Витратні в бою** (лише `items.enabled`): кожен `SpecialItem` з `artifactId` і `quantity > 0` додає вміння свого артефакта з пулом `pool:consumable:<itemId>` (max = кількість, `rest: null`; уміння пише `limits.pool { key: "charges", cost: 1 }`). При завершенні бою (`saveBattle`, гілка `completing`, та сама транзакція, незалежно від `persistResources`) витрачене віднімається від кількості, запис на 0 видаляється, журнал інвентаря `item_use`. Видалений бій без завершення — нічого не пише.

### 6. Поза боєм

- Лист: заряди з `resources.charges[pool:item:<ref>]` — «Wand of Magic Missiles 5/7 · довгий»; `PATCH …/resources` (ДМ) приймає `charges: { [poolKey]: used }` — ручне витрачання й відновлення (журнал `resources_edit`).

### 7. Конвертер і шаблон (`scripts/srd/convert/magic-items.ts`, `overrides/magic-items.ts`)

- **Звичайне спорядження**: 38 зброї й 13 броні/щит 4f-1/4f-2 отримують `item.unique: false`.
- **Властивості** (32): групування рядків із FK за назвою без назви бази (`Flame Tongue Longsword` → `Flame Tongue {base}`, `Longsword (+1)` → `{base} +1`, `Defender (Longsword)` → `Defender ({base})`) + ручна таблиця для Adamantine/Mithral/Resistance з нестандартними назвами баз (Plate, Splint, Padded, Studded Leather) і Dwarven/Elven; Dragon Slayer — властивість «будь-яка зброя» вручну. Рядок: назва сімейства («Weapon +1», «Armor +1», «Flame Tongue»), слот weapon/armor, рідкість, налаштування (більшість у сімействі), опис першого варіанта, `appliesTo` — фільтр за базами варіантів (усі зброї / ближня / категорії броні + щит); `bases` — лише коли набір вужчий (Life Stealing, Sharpness, Vorpal, Luck Blade, Hammer, Oathbow…). Загальні рядки Defender/Holy Avenger без FK відкидаються (slug записується як псевдонім).
- **Унікальні** (244 з `MagicItem` + 4 зілля лікування з `Item.json` = 248): слот — зброя/броня за базою (`UNIQUE_BASES`: ~16 предметів, статі копіюються з бази + «+N»), назви з Shield → shield, ring → ring, чудесні — регулярка назви (Amulet/Periapt/Necklace/Medallion/Scarab → amulet, Boots/Slippers → boots, Cloak/Cape/Mantle/Robe → cloak, Helm/Hat/Circlet/Headband → helmet), решта (і potion/wand/staff/rod) → item. Ammunition (17) — витратні з описом.
- **Рідкість**: common/uncommon/rare як є, very-rare → epic, legendary і artifact → legendary. **Унікальність**: усі предмети SRD `unique: false`, крім рідкості artifact (Dragon Orb) (рекомендоване; користувач спав — переглянути) — у 5e магічні предмети не одиничні на світ; HOMM-контент не зачеплено.
- **Налаштування** — `requires_attunement`. **Заряди** — регулярка `has (N|NdM + K) charges` (кубики → максимум) і `regains … (dawn|long rest)` → `rest: "long"`, `short rest` → `short`, без відновлення → `null`; кожен предмет із зарядами отримує вміння-облік «Expend a charge» (дія, нотатка, `pool charges 1`), вартість конкретних ефектів — в описі. **Витратні** — category potion, зілля з `Item.json`, набої й ручний список (Dust of …, Elemental Gem, Bead of Force, Feather Token, Oil of …, Philter of Love, Universal Solvent, Sovereign Glue).
- **Механізовано автоматично** (регулярки за описом; повний текст SRD — в описі кожного):

| Шаблон | Ефект | Приблизно |
|---|---|---|
| «+N bonus to attack rolls and damage» / «determined by rarity» (+1/+2/+3 за uncommon/rare/very rare) | `attackBonus` + `damageBonus` зброї | 3 сімейства + 8 сімейств і Dragon Slayer із «+N» у тексті + ~9 унікальних (посохи-бойові — з базою Quarterstaff) |
| «+N bonus to Armor Class» (зокрема броня й щити за рідкістю) | `modifyStat armor +N`; «no armor and no Shield» → `armorWorn none, shield without` | 3 сімейства + Dwarven/Elven/Demon + 10 унікальних |
| «+N bonus to … saving throws» | `modifyStat savingThrow` | 4 + Luck Blade |
| «Resistance to <Type> damage» (фіксований тип) | `flag resistance` | 10 + Frost Brand |
| «<Ability> is/changes to N» | `modifyStat <ability> atLeast N` | 8 |
| «Advantage on <Ability> (<Skill>) checks», «… saving throws against spells» | `checkAdvantage`, `saveAdvantage vsSpells` | ~10 |
| «extra NdM <Type> damage» при влучанні | `hit` + `withThisItem` + `dealDamage` | 4 сімейства (Flame Tongue, Frost Brand, Vicious, Wounding) + ~6 унікальних |
| Adamantine | `critImmunity` | 1 сімейство |
| Berserker | `modifyStat maxHp` формула `hero_level` | 1 сімейство |
| Зілля лікування (2d4+2 / 4d4+4 / 8d4+8 / 10d4+20) | бонусна дія `heal` собі, витратний | 4 |

Разом: **~24 з 32 властивостей і ~55 з 248 унікальних** з механікою; ще ~45 — облік зарядів; решта — опис. Вибір типу опору (Armor/Ring/Potion of Resistance), умови «проти Fiend/Giant/Dragon», заклинання з предметів, підсилення за зарядом — опис (§9).
- Цілісність (`scripts/srd/__tests__`): кожна властивість має ≥ 1 базу в шаблоні, що проходить `matchesAppliesTo`, і складені назви збігаються з назвами варіантів SRD (513 перевірок); пул `charges` лише в предметах із зарядами/витратних; `importContent` з `dryRun` без помилок. Після злиття частини — `pnpm srd:build` і `pnpm constructor:srd-template` (локально).

### 10. Перевірка 4f-3

- Наявні тести — без змін (HOMM: унікальність, сітка, передача, бій без нових полів); `battle-sweep` на HOMM5.

- Конвертер: Flame Tongue Longsword (складається з Longsword + Flame Tongue, райдер 2d6 fire), Longsword (+2) (атака/шкода +2), Breastplate (+1) (КЗ +1 поверх броні), Mithral Plate (без Сили й скритності), Wand of Magic Missiles (7 зарядів, довгий), Ring of Protection (КЗ і рятівні +1, налаштування), Amulet of Health (Тіл ≥ 19), Potion of Greater Healing (4d4+4, витратний), Belt of Giant Strength (Fire), лічильники 32/248, цілісність 513 складених назв.

Тестові дані видаляються.
- Документи: `battle.md` («5e: магічні предмети»), `abilities.md` (`withThisItem`, `critImmunity`, `atLeast`, пул `charges`), `content-api.md` (`item`, `damageBonus`, ref, шаблон), STATUS, хендоф, пам'ять.

### 11. Обсяг плану (орієнтовно 16 задач)

## 4f-4. Дизайн: вибір при створенні й рівні

Розвідка (2026-10-23):
- **Персонаж.** `Character.race` — назва раси (не id), `subrace`/`background` — вільний текст (`background` насправді біографія). `Character.classes [{ classId, subclassId?, level }]` змінює лише ДМ; `level-up` у режимі класів приймає `{ classId, subclassId? }` (`class-level-up.ts`) і випадкове «+1 до характеристики» не застосовує; характеристики героя ДМ правит у формі, HOMM-шлях (`applyLevelGain`) пише їх прямо в колонки. Сховища рис і виборів немає.
- **Вміння.** `collectCharacterAbilities` збирає скіли, расу, класи (`classResolved` з `applyClassScale`), артефакти, сети й витратні; джерела `race`/`class`/…, типу `feat` немає. Фічі класу — `{ level, abilities }`; усі вміння з вибором у шаблоні — нотатки (ASI ×51, Epic Boon ×12, Fighting Style ×3, Expertise ×4, Metamagic, Invocations, Divine/Primal Order, Weapon Mastery). Колонки класів уже мають `eldritch-invocation-count`, `weapon-mastery-count`, `cantrips`, `prepared-spells`.
- **Навички.** `rollCheck` дає майстерність з `abilities.skillProficiencies` або прапорця `skillProficiency` (через `collectModifiers`); експертизи (подвійна майстерність) немає.
- **Заклинання героя.** Бій бере `Character.knownSpells` + персональні + з дерева скілів (`resolveLearnedSpellsAndMastery`); редактора відомих заклинань персонажа в UI немає (лише API), `SpellMultiSelect` живе в полях умінь. Зв'язку «заклинання ↔ клас» у моделі немає; `HP` (`classHp`) читає сирий `character.constitution`, а не запечений.
- **Бандл і синхронізація** ремаплять будь-який id усередині JSON (`remapIds` — глибока заміна рядків), тож id у нових JSON-полях переносяться без окремого коду; імпортер має `ref`/`refList`/`json`.
- **Дані SRD.** Риси 17 (`Feat.type`: Origin 4, General 2, Fighting Style 4, Epic Boon 7; `prerequisite` — текст «Level 4+», «Level 4+, Strength or Dexterity 13+», «Fighting Style Feature», «Level 19+, Spellcasting Feature») + 35 `FeatBenefit` (назва + текст; «Repeatable» — окремий рядок у ASI, Skilled, Magic Initiate). Лінії лише в прозі `SpeciesTrait`: Elven Lineage (таблиця 3 × рівні 1/3/5), Gnomish Lineage (2 жирні абзаци), Fiendish Legacy (таблиця 3 × 1/3/5), Draconic Ancestry (таблиця 10 драконів → тип шкоди), Giant Ancestry (список 6) — разом **24 опції**, 22 посилання на заклинання SRD. Інші вибори рас: Keen Senses (1 з 3 навичок), Skillful (будь-яка навичка), Versatile (риса походження). Вибори класів: Metamagic (9 опцій у `sorcerer_metamagic-options`, 2/4/6 на 2/10/17), Eldritch Invocations (28 опцій з `*Prerequisite: Level N+ Warlock[, X Invocation]*`, кількість — колонка), бінарні опції в жирних абзацах (Divine Order, Primal Order, Blessed Strikes, Elemental Fury, Hunter's Prey, Defensive Tactics), Elemental Affinity (5 типів), Fiendish Resilience (тип, крім Force). `Spell.classes` заповнений для всіх 339 (wizard 218, sorcerer 140, bard 130, druid 124, cleric 109, warlock 72, ranger 48, paladin 38). Передісторії 4 (`BackgroundBenefit`: 3 характеристики, 2 навички, інструмент, спорядження, риса походження).

### 1. Правила

Нової секції немає (рекомендоване; користувач спав — переглянути): риси й вибори класів діють лише в режимі класів (`rules.classes.enabled` і непорожні `classes`), як 4c-1/4f-2; вибори раси (лінії) — властивість контенту раси й діють для будь-якого героя (у HOMM-расах їх немає — нульова зміна). Сторінка «Риси» в меню ДМ — коли `classes.enabled`.
- Альтернатива: `rules.classes.feats: boolean` — зайва вісь; кампанія без рис просто не має контенту `feats`, і вибори типу `feat` тоді порожні.

### 2. Вибір — спільна модель (`lib/utils/characters/choices/`)

Один механізм для ліній рас, виборів раси, виборів класу й вкладених виборів рис (рекомендоване; користувач спав — переглянути):

```ts
Choice = {
  id: string,                        // kebab-case, стабільний у межах власника (раси / класу / риси)
  label: string,                     // "Elven Lineage", "Fighting Style", "Metamagic"
  level: number,                     // 1–20: рівень у класі (клас/підклас) або загальний рівень (раса); у рисі ігнорується
  count: number | { scale: string }, // 1–30 або колонка класу ({ scale } — лише у класі, як 4f-2)
  lineage?: true,                    // лише раса, ≤ 1 на расу: назва обраної опції → Character.subrace
  kind: "option" | "feat" | "skill" | "expertise" | "abilityScore" | "spell",
  options?: ChoiceOption[],          // option; у feat — додаткові вбудовані опції (Blessed Warrior)
  featTypes?: FeatType[],            // feat: які типи рис пропонуються
  skills?: DndSkill[],               // skill/expertise: порожньо — будь-яка (expertise — будь-яка з майстерністю)
  abilities?: AbilityKey[], points?: number, max?: number,   // abilityScore: з яких, скільки +1, межа (20 / 30)
  spells?: { lists: string[], minLevel: number, maxLevel: number | "slots" },  // spell: списки, кола; "slots" — найвище коло слотів цього класу
}
ChoiceOption = {
  id, name, description?,
  minLevel?: number,                 // рівень власника (у класі — рівень у класі)
  requires?: string[],               // id інших опцій цього ж вибору (Thirsting Blade → Pact of the Blade)
  abilities: Ability[],              // як у раси/класу; нотатки дозволені
  spells?: { level: number, spellId: string }[],   // завжди відомі з загального рівня N (лінії рас)
}
Pick = { id: string, picks?: Record<choiceId, string[]> }   // id опції / риси / навички / характеристики / заклинання; picks — вкладені вибори риси
Picks = Record<choiceId, Pick[]>
```

- **Кількість** `{ scale }` розв'язується `applyClassScale`-логікою 4f-2 на рівні в класі; вибір відкривається на `level` і росте разом з колонкою (Invocations 1→10, Metamagic через синтетичну колонку `metamagic` 2/4/6). Так опції не дублюються по рівнях.
- **`abilityScore`**: `picks` — масив ключів довжиною `points` (повтор = +2): ASI `{ points: 2, max: 20 }`, Grappler `{ abilities: [str, dex], points: 1, max: 20 }`, Epic Boon `{ points: 1, max: 30 }`.
- **Вкладені вибори** — лише в рисі й без `kind: "feat"` (Zod), тож рекурсія на один рівень.
- **Чисті функції:** `resolveChoiceCount`, `pendingChoices(owner, level, picks)` (невибрані й дообрані слоти), `validatePicks(ctx)` (опція існує, `minLevel`, `requires`, без повторів, кількість ≤ розв'язаної, навичка зі списку / з майстерністю для експертизи, риса: тип у `featTypes`, `prerequisite`, `repeatable`; заклинання: є тег зі `lists`, коло в межах; характеристика: результат ≤ `max`), `abilityScoreDelta(before, after)`. Модуль без zod у рантаймі (типи — `import type`), бо збирання учасника потрапляє в клієнтський чанк бою.
- Альтернатива: окремі механізми для ліній (`races.lineages`), рис і виборів класу — три редактори й три валідатори для однієї ідеї «обрати N з набору».
- Альтернатива: вибір = прив'язка до умінь класу (`ability.choiceGroup`) — не покриває рис, навичок, характеристик і заклинань.

### 3. Дані

Одна міграція (лише розширює):
- таблиця `feats` (`id`, `campaignId`, `name`, `icon?`, `type`, `prerequisite Json`, `repeatable`, `description?`, `abilities Json`, `choices Json`, `sourceId`/`sourceHash`, часові мітки; індекс `(campaignId, name)`; каскад від кампанії; **`ENABLE ROW LEVEL SECURITY`**);
- `races.choices Json @default("[]")`; `spells.lists Json @default("[]")`; `classes.spell_list text NULL`;
- `characters.feats Json @default("[]")`, `characters.race_choices Json @default("{}")`.

**3.1. Риси — тип контенту `feats`** (рекомендоване; користувач спав — переглянути). Повний шлях 4c-1: `CONTENT_RESOURCES`, `ContentKind`, роути колекції, `ReferenceKind.FEATS`, `BUNDLE_TABLES`/`SYNC_TABLE_SCOPES`, поля імпорту 4f-0 й експорт CSV, OpenAPI (оновити `app/api/openapi.json`), MCP — автоматично з ресурсу.

```ts
{
  name, icon?, description?,
  type: "origin" | "general" | "fightingStyle" | "epicBoon",
  prerequisite: { level?: number, scores?: { abilities: AbilityKey[], min: number }, text?: string },  // scores — «будь-яка з»
  repeatable: boolean,
  abilities: Ability[],
  choices: Choice[],                 // ASI, Skilled, Magic Initiate, Grappler, бусти
}
```

Видалення риси, яку тримає персонаж (будь-яке джерело), — 409 (`FEAT_IN_USE`, як клас); синхронізація видаляє рядок напряму → невідома риса пропускається, форма показує «Рису не знайдено». Порядок імпорту шаблону: spell-groups → spells → races → classes → **feats** → units → artifacts.
- Альтернатива: риси як скіли або артефакти (звіт мапінгу) — чужі поля (дерева, слоти), немає типу й передумов.
- Альтернатива: Fighting Style лише як вбудовані опції класу — дублюються в 4 класах, а ASI-«або риса» все одно потребує каталогу.

**3.2. Раса:** `choices: Choice[]` (Zod: `count` число, `level` — загальний рівень, ≤ 1 `lineage`, унікальні id опцій). Посилання `spells[].spellId` у файлі шаблону — назвами; імпортер розв'язує їх як `refList` у вкладеному JSON (новий резолвер у полях імпорту `races`, якщо загального ще немає — перевірити в плані); бандл/синхронізація ремаплять id самі.

**3.3. Клас:** фіча `{ level, abilities, choices?: Choice[] }` у `features` і підкласах (JSON, без міграції); Zod класу перевіряє `{ scale }` у `count` як посилання на колонку (`columnRefIssues`). Нова колонка `spellList: string | null` — тег списку заклинань класу (за замовчуванням у формі — назва класу).

**3.4. Списки заклинань — теги на заклинанні** `Spell.lists: string[]` (≤ 20, рядки ≤ 40) (рекомендоване; користувач спав — переглянути). Клас посилається тегом (`spellList`), вибір `spell` — списком тегів (Magic Initiate: Cleric/Druid/Wizard; High Elf — Wizard). Без id: порядок імпорту, синхронізація й перейменування класу не ламають зв'язок; кілька класів можуть ділити список.
- Альтернатива: `classes.spellList: spellId[]` — ~1000 id у рядках класів (egress списку класів, уже відкладений у 4f-2) і клас мусить імпортуватись після заклинань.
- Альтернатива: `Spell.classes: classId[]` — заклинання імпортуються до класів (потрібен другий прохід), список прив'язаний до конкретного рядка класу.

**3.5. Вибори персонажа** (рекомендоване; користувач спав — переглянути):
- клас: `Character.classes[i].choices?: Picks` (JSON, без міграції) — вибори класу й підкласу, включно з рисами з ASI/Fighting Style/Epic Boon (`Pick.id` = id риси, `picks` — її вкладені вибори);
- раса: `Character.raceChoices: Picks` (лінія — звичайний вибір з `lineage`); сервер пише назву обраної лінії в `subrace` (для показу, AI й наявної картки ДМ — як текст `class` у 4c-1);
- `Character.feats: { id, picks?, source: "origin" | "dm" }[]` — риса походження при створенні й риси, видані ДМ поза виборами.
- `characterFeats(character, refs)` збирає риси з усіх трьох місць (для листа, `repeatable` і 409 видалення).
- Альтернатива: усі риси лише в `Character.feats` з посиланням на вибір — два джерела правди (вибір класу і запис у списку).
- Альтернатива: колонка `characters.lineage` — окремий шлях для одного з виборів раси, а Keen Senses/Skillful/Versatile однаково потребують `raceChoices`.

**3.6. Покращення характеристик (ASI)** пишеться в базові колонки `strength…charisma` при збереженні вибору: `abilityScoreDelta(старі picks, нові)` у тій самій транзакції; зміна чи зняття вибору відкочує свою дельту (рекомендоване; користувач спав — переглянути). Межа 20 (30 для бустів) — на результат. Так HP (`classHp` з сирої Тіл), КЗ, форма, друк і AI бачать нові значення без змін, а HOMM уже пише рівневий приріст так само.
- Альтернатива: синтетичне `modifyStat <ability>` з вибору (запікання) — повністю похідне, але `classHp` і форма читають сирі характеристики; довелося б переносити HP після запікання.

### 4. Сервер

- **Створення** (`create-character-schema.ts`): `raceChoices`, `feats` (лише `source: "origin"`, тип `origin`, ≤ 1, коли в кампанії є риси походження) і `classes[].choices` — валідація `validatePicks` з контекстом (раса, класи, риси, заклинання кампанії). Так само для чернеток гравця.
- **Підвищення рівня**: тіло `{ classId, subclassId?, choices?: Picks }` — вибори піднятого класу; невибране дозволене (рекомендоване; користувач спав — переглянути): лист показує «Невибрані вибори: N», доступні з кнопки «Обрати». Альтернатива: обов'язкові вибори (422) — ДМ не може підняти рівень, поки гравець думає над рисою.
- **Правка виборів** `PUT /api/campaigns/[id]/characters/[characterId]/choices` (ДМ або власник при `allowPlayerEdit`; `source: "dm"` — лише ДМ): `{ raceChoices?, feats?, classChoices?: Record<classId, Picks> }` → `validatePicks`, дельта ASI, `subrace`, запис журналу 4d `choices_edit`; 409, поки герой в активному бою (`battle-lock.ts`). Тексти помилок — `api-errors.ts` (`CHOICE_UNKNOWN`, `CHOICE_COUNT`, `FEAT_PREREQUISITE`, `FEAT_NOT_REPEATABLE`, `SPELL_NOT_IN_LIST`, `ABILITY_SCORE_CAP`). Класовий PATCH (`classes` лише ДМ) зберігає наявні `choices` записів; рівень класу нижче за рівень вибору — вибір лишається, але не діє (як вміння вищих рівнів).
- `lib/api/characters.ts` + хук `useCharacterChoices` (інвалідує лист і список персонажів).

### 5. Рушій і похідні

- **Вміння з виборів** (`collectCharacterAbilities`, нова гілка `choiceResolved`): обрані опції раси — джерело `race` («Elf: Wood Elf»), опції класу/підкласу — джерело `class` («Sorcerer: Metamagic — Quickened Spell», `applyClassScale` діє), риси — нове `AbilitySource.type: "feat"` (вміння риси + її вкладених опцій); вибір `skill` → синтетичне пасивне `flag skillProficiency`, `expertise` → `flag skillExpertise`. Далі як зараз (`resolveAbilities`, `bakePassives`, snapshot з `snapshotHash`). Вибір вищий за поточний рівень у класі/загальний рівень — не діє.
- **Прапорець `skillExpertise { skills }`** (`abilities.md`, реєстр прапорців): `checkBonus` подвоює майстерність навички (лише коли майстерність є); лист показує «×2».
- **Додані заклинання** (`grantedSpellIds`): заклинання опцій раси з `level ≤` загального рівня + вибори `spell` (класи, риси) зливаються з `knownSpells` у `resolveLearnedSpellsAndMastery` і в листі. Каст — як зараз (слоти; кантрип без слота). Безкоштовний каст «1 / довгий» — поза обсягом (§9).
- **Нічого нового в snapshot** — вибори перетворюються на вміння й заклинання при збиранні; `refresh-from-source` бере те саме.

### 6. Фільтр заклинань за класом

- Вибори `spell` класу (кантрипи `count {scale: cantrips}`, `maxLevel 0`; підготовлені `count {scale: prepared-spells}`, `minLevel 1`, `maxLevel "slots"`) — єдине місце, де застосовується список: пікер показує лише заклинання з тегом зі `lists` і колом у межах, лічильник «4 / 6»; сервер відмовляє 422 `SPELL_NOT_IN_LIST`. `"slots"` = найвище коло, яке дає цей клас сам (`classSpellSlots` одного запису; пакт — коло пакту) (рекомендоване; користувач спав — переглянути).
- `Character.knownSpells` лишається вільним списком ДМ (персональні, з предметів, домашні правила) без перевірки — HOMM і ручні випадки не ламаються. Альтернатива: перевіряти й `knownSpells` за об'єднанням списків — ламає наявних героїв і домашні правила.
- Бібліотека заклинань ДМ: чип-фільтр за тегом списку; форма заклинання — поле «Списки» (чипи з підказками наявних тегів).

### 7. Конвертер і шаблон

### 9. Поза обсягом 4f-4

**Передісторії** (4 SRD: характеристики +2/+1, 2 навички, інструмент, спорядження, риса походження) — окремий тип контенту поверх тих самих виборів, малою частиною після 4f-5 (рекомендоване; користувач спав — переглянути); до того — риса походження обирається вільно, характеристики й навички ДМ вносить руками. **Вибір параметра предмета при видачі** (тип опору Armor/Ring/Potion of Resistance; велетень/дракон для Giant/Dragon Slayer) — **4f-5**: потребує третього сегмента ref у всіх читачах `resolveItemRows`, а умови за типом істоти — механізм монстрів 4f-5. Безкоштовний каст «1 / довгий» без слота (заклинання ліній, Magic Initiate, Mystic Arcanum, Signature Spells) — 4f-5 разом із заклинаннями з предметів; Breath Weapon драконороджених — механізм подиху 4f-5. Weapon Mastery (властивостей майстерності в рушії немає); активні ефекти метамагії й більшості заклинань-закликів (оголошені опції, як Reckless Attack у 4f-2); Great Weapon Fighting, Savage Attacker; вибір характеристики заклинань для лінії/риси (береться характеристика героя); заміна виборів «лише на рівні / після відпочинку» (міняти можна будь-коли поза боєм за правами); `skillChoices` класу як вибір (лишається підказкою); інструменти й мови; AI-контекст рис (`ai/tools/party.ts`).

## Ризики

- **Перетин з HOMM-контролем.** `charm` (HOMM, перехід на бік) ≠ `charmed` (5e). Різні ключі й підписи; редактор показує 5e-стани окремою групою.
- **Розмір snapshot.** Стан додає один `ActiveEffect` з кількома прапорцями; на egress це не впливає помітно (дельти).
- **Клієнтські кидки.** Перевага на рятівному кидку з `presetRoll` — другий кубик кидає сервер; майстер заклинання показує режим кидка до підтвердження (через ту саму `rollSave`-логіку режиму, спільну для клієнта й сервера).
- **Концентрація на чужих ефектах.** Знімання за `concentrationOf` має проходити всіх учасників і зони за один прохід; тест на кілька цілей + зону обов'язковий.
- **Ліцензії ассетів.** В офіційних шаблонах — лише власні AI-іконки; арт з особистою ліцензією (Forgotten Adventures тощо) — тільки в кампанії користувача, `assets:attach` без `--allow-official` відмовляє для офіційного шаблону. SRD 5.2 вимагає атрибуції — `credits` копіюється в усі похідні кампанії.
- **Якість евристик SRD.** Сторона й кількість цілей заклинань виводяться з тексту; ~40 популярних перевіряються вручну, решту ДМ виправляє в редакторі.
- **КЗ у режимі класів стає похідним (4f-2).** `Character.armorClass` героя з класами більше не читається: локальні тестові герої з ручним КЗ отримають 10 + Спр + броня; природна броня й нетипові бази — уміннями. На HOMM не впливає; prod-даних із класами ще немає.
- **Розширення спільних схем умінь (4f-2).** `{ scale }` у `Flat`/`Amount`/`uses` і `limits.pool` ростуть у кожному місці JSON Schema — тест розміру OpenAPI (< 130 000) уже близько до межі; перевірити `$ref`-дедуплікацію, не піднімати ліміт без потреби. Рушій бачить лише розв'язані числа, тож поза класами `scale` — лише проблема в редакторі.
- **Нові змінні формул (4f-2).** `prof`, `str_mod` … `cha_mod`, `class_level` могли б змінити результат наявної HOMM-формули, якщо вона містить ці слова (зараз така формула дає 0 як невідома). Перед злиттям — пошук по `abilities` усіх таблиць локальної копії й prod (після свіжого бекапу).
- **Наближення умінь класів (4f-2).** Lay on Hands — по 5 HP, Uncanny Dodge і Deflect Attacks — лікування після влучання, Sacred Weapon — бонусною дією, Sneak Attack — без перевірки зброї, Relentless Rage — без зростаючого СК, пули Channel Divinity мультикласу — окремі. Повний текст SRD лишається в описі; ДМ виправляє в редакторі.
- **Ref замість id в інвентарі (4f-3).** Значення `equipped`/`stash` стають рядками `<baseId>+<propertyId>`; кожен читач, що не перейде на `resolveItemRows`, мовчки втратить складений предмет. План має одну задачу на всіх читачів і тест-сторож (пошук `\.equipped`/`\.stash` поза `lib/utils/items`). Синхронізація з джерелом видаляє артефакти напряму — ref на видалену базу/властивість просто пропускається.
- **Неунікальність SRD (4f-3).** Звичайне спорядження й магічні предмети шаблону SRD стають `unique: false`; кампанія, створена з шаблону до 4f-3, отримає прапорець лише через «оновлення з джерела». HOMM-артефакти без поля лишаються унікальними.
- **Наближення предметів (4f-3).** Райдери діють без запалювання бонусною дією, тип шкоди Vicious — тип за замовчуванням `dealDamage`, заряди відновлюються повністю на довгому відпочинку, Defender — постійні +3 без перенесення в КЗ, ~190 унікальних предметів — лише опис. Повний текст SRD лишається в описі; ДМ виправляє в редакторі.
- **Носіння зі сховища (4f-3).** При `items.enabled` усі предмети слотів `item`/`ring` у сховищі діють; ДМ має прибирати непотрібні в «Підсумок», а межу задає лише налаштування. Предмет без налаштування (Boots of Elvenkind) діє, навіть якщо їх кілька.
- **Вибори в JSON (4f-4).** Пікі посилаються на id опцій і рис усередині JSON класу/раси/риси; синхронізація з джерелом, що перейменує id опції чи видалить рису, лишає «осиротілий» вибір — він пропускається в рушії, форма показує «Вибір не знайдено», лист — бейдж невибраних. Конвертер генерує id з slug фіч, тож перезаливка шаблону їх не змінює.
- **ASI у базових характеристиках (4f-4).** Дельта пишеться в колонки; ручна правка ДМ між виборами може зробити відкат нижчим за початкове значення чи вищим за межу — валідація на результат, видалення риси (409) не відкочує характеристики, синхронізація, що видалила рису, теж. На HOMM не впливає (вибори лише в режимі класів).
- **Списки тегами (4f-4).** Тег — рядок: друкарська помилка в `spellList` чи `lists` дає порожній список; форма класу показує кількість заклинань у списку (0 → попередження), цілісність SRD звіряє з `Spell.classes`.
- **Розмір OpenAPI (4f-4).** `Choice` з'являється в класах, расах і рисах — тримати одним `$ref`; тест розміру (< 130 000) уже близько до межі після 4f-2/4f-3.
- **Невибрані вибори (4f-4).** Level-up без виборів дозволений — герой може воювати без рис/кантрипів; бейдж на листі й у списку ДМ — єдиний сигнал.
