# Конструктор кампаній — етап 4: механіки D&D 5e (дизайн)

## Context

Мета епіку уточнена користувачем 2026-10-22: будь-хто, хто грає в D&D 5e, має перенести свою кампанію в трекер **за всіма правилами**, так само як HOMM5 працює зараз. Епік вважається завершеним, коли є два повноцінні режими — HOMM5 і 5e. **Warhammer (етап 5) переноситься на після MVP.** Злиття `feat/constructor` у `main` і prod — після етапів 1–4 і 6.

Розвідка (стан коду на 2026-10-22):
- **Стани.** `applyCondition` пише `ActiveEffect` з `type: "condition"` і маркером у `effects`. Ключі (`CONDITION_KEYS`) механічні — `skip_action`, `immobilized`, `no_reaction`, `no_bonus_action`, `disable_*` — і рушій читає їх через `hasEffectMarker`. 5e-станів немає. `charm` і `berserk` — HOMM-контроль, а не 5e «зачарований». `ActiveEffect.abilityEffects: StaticEffect[]` уже читає `collectModifiers` (`collect-modifiers.ts:186`).
- **Перевага й перешкода** є тільки на атаках (`attack/bonus.ts`: `rollModeReasons`, прапорці `advantage`/`disadvantage`/`…ForAttackers`). `rollSavingThrow` (`spell/power.ts:24`) = d20 + модифікатор, без майстерності, переваги й автопровалу.
- **Рятівні кидки.** `Character.savingThrows` (`Record<ability, boolean>`) тільки показуються. Рятівні кидки кидають заклинання (`spell/cast/outcome.ts`) і `maneuvers/fire-burst.ts`; клієнт може передати готовий кидок (`saveRolls`).
- **0 HP.** `applyDamageToTarget` → `unconscious` (HP 0) / `dead` (HP < 0). Кидків смерті немає; союзники встають після перемоги (`turn/victory.ts`).
- **Концентрації немає.**
- **Класи.** `Character.class` — вільний текст для показу. На рушій впливає лише `archetype` (5 ключів у коді). Слоти — саморобна таблиця або крива повного заклинача 5e до 10 рівня; рівні заклинань 0–5.
- Правила кампанії: `RulesetSchema` (секції з default = поточна поведінка) + `MECHANIC_REGISTRY`; рушій читає зафіксовану копію `battle.rules`; `Ruleset` уже передається в початок ходу (`turn/start-end.ts`).

## Розбиття етапу 4

Кожна частина — свій план і реалізація; частини після 4a отримують свій розділ у цьому спеку (або окремий спек) перед планом.

Порядок 4a → 4f; після 4f — етап 6 (AI), потім злиття.

## Загальні правила етапу 4

- **Нульова зміна HOMM5.** Нові секції `rules` мають default «вимкнено» або «як зараз»; нові ключі станів і прапорців не використовуються в HOMM-контенті. Усі наявні тести рушія проходять без змін.
- Механіки — каталог у коді (`MECHANIC_REGISTRY`, реєстр станів); кампанія вмикає й налаштовує їх у `rules`. Рушій бою читає тільки `battle.rules`.
- Нові бонуси й прапорці читаються лише через `collectModifiers`/`runAbilities`, як вимагає `abilities.md`.
- Міграції лише розширюють схему. 4a міграцій не потребує (усе в JSON: `rules`, snapshot, `Spell.definition`).

## 4a. Дизайн

### 1. Правила (`lib/utils/rules/schema.ts`)

Нові секції `RulesetSchema` (і `RulesetPatchSchema`, `MECHANIC_REGISTRY`, вкладки на `dm/rules`):

```ts
saves:         { proficiency: false }                       // майстерність з Character.savingThrows
deathSaves:    { enabled: false, unitsDieAtZero: true }     // кидки смерті героїв; юніти при 0 HP помирають
concentration: { enabled: false, dcCap: null }              // null — 2014 (без межі), 30 — 2024
conditions:    { enabled: false, exhaustion: "2014" }       // меню станів ДМ і група 5e в редакторі; "2014" | "2024" — таблиця виснаження
```

Default кожної секції відтворює поточну поведінку. Перевага/перешкода й автопровал рятівних кидків не мають перемикача: вони походять лише з даних (стани 5e, прапорці), яких у HOMM-контенті немає.

### 2. Стани 5e

`lib/utils/battle/conditions/` — реєстр `CONDITION_5E_REGISTRY` (`satisfies Record<Condition5eKey, Condition5eDef>`):

```ts
type Condition5eDef = {
  label: string;               // українська назва
  description: string;
  markers: ConditionKey[];     // наявні маркери: skip_action(100), no_reaction, no_bonus_action, immobilized, ...
  flags: StaticEffect[];       // прапорці для collectModifiers
  implies?: Condition5eKey[];  // напр. paralyzed → incapacitated
};
```

Ключі: `blinded`, `charmed`, `deafened`, `frightened`, `grappled`, `incapacitated`, `invisible`, `paralyzed`, `petrified`, `poisoned`, `prone`, `restrained`, `stunned`, `unconscious`, `exhaustion`.

| Стан | Як діє в рушії |
|---|---|
| Засліплений | власні атаки — перешкода; атаки по ньому — перевага |
| Зачарований | не може атакувати джерело стану (атакою чи шкідливим заклинанням) |
| Оглухлий | лише маркер (бойового ефекту немає) |
| Наляканий | перешкода на атаки, поки джерело живе; рух, що зменшує відстань до джерела, відхиляється |
| Схоплений | швидкість 0 (`immobilized`); 2024: перешкода на атаки по всіх, крім того, хто схопив |
| Недієздатний | без дії, бонусної дії й реакції (`skip_action` 100 + `no_bonus_action` + `no_reaction`); знімає концентрацію |
| Невидимий | власні атаки — перевага; атаки по ньому — перешкода |
| Паралізований | недієздатний + швидкість 0; автопровал Сил/Спр; атаки по ньому — перевага; влучання з 5 фт — крит |
| Скам'янілий | недієздатний + швидкість 0; автопровал Сил/Спр; атаки по ньому — перевага; опір усій шкоді; імунітет до отруєння |
| Отруєний | власні атаки — перешкода |
| Повалений | власні атаки — перешкода; атаки по ньому з 5 фт — перевага, здалеку — перешкода (вставання — частина 4b; до 4b стан знімає ДМ або тривалість) |
| Обплутаний | швидкість 0; власні атаки — перешкода; атаки по ньому — перевага; перешкода на рятівні Спр |
| Приголомшений (stunned) | недієздатний + швидкість 0; автопровал Сил/Спр; атаки по ньому — перевага |
| Непритомний | недієздатний + швидкість 0 + повалений; автопровал Сил/Спр; атаки по ньому — перевага; влучання з 5 фт — крит |
| Виснаження (1–6) | 2014: 1 — (перевірки, поза боєм), 2 — швидкість ×½, 3 — перешкода на атаки й рятівні, 4 — макс. HP ×½, 5 — швидкість 0, 6 — смерть. 2024: −2×рівень до кидків d20 (атаки, рятівні), швидкість −5 фт×рівень, 6 — смерть |

Нові прапорці (`FlagSchema`, `labels.ts`, редактор здібностей):
- `saveAdvantage` / `saveDisadvantage` `{ abilities: AbilityKey[] | "all", vsSpells?: true }` — «Магічний опір» = `saveAdvantage all vsSpells`;
- `autoFailSave` `{ abilities: AbilityKey[] }`;
- `saveProficiency` `{ abilities: AbilityKey[] }` — для юнітів і здібностей (герої беруть його з `Character.savingThrows`, якщо `rules.saves.proficiency`);
- `autoCritAdjacent` — влучання по власнику з 5 фт (сусідня клітинка) стає критом;
- `proneDefense` — атаки по власнику з 5 фт мають перевагу, здалеку — перешкоду (окремий прапорець, бо наявні `…ForAttackers` не залежать від відстані);
- новий стат `savingThrow` у `DYNAMIC_STATS` (`modifyStat`, flat) — для «Благословення»/«Порчі» та бонусів рятівних кидків.

Застосування: `applyCondition` приймає `condition: ConditionKey | Condition5eKey`. Для 5e-ключа він пише один `ActiveEffect` (`type: "condition"`, `name` = назва стану), де `effects` = маркер самого стану + маркери реєстру (з `implies`), а `abilityEffects` = прапорці реєстру. Варіант виснаження береться з `ctx.rules.conditions.exhaustion` у момент накладання; `value` маркера `exhaustion` = рівень, повторне накладання додає рівні (до 6; на 6 — смерть). Додаткові поля `applyCondition`:
- `saveEnds?: { ability: AbilityKey }` — наприкінці кожного ходу ціль повторює рятівний кидок проти СК накладача (зберігається в ефекті), успіх знімає стан;
- `levels?: 1–6` (лише для `exhaustion`).

Імунітети: `conditionImmunity` приймає й 5e-ключі (`[...CONDITION_KEYS, ...CONDITION_5E_KEYS, "fear", "berserk", "charm"]`). Імунітет до `incapacitated` не блокує `stunned` — перевіряється лише ключ, що накладається.

Рушій читає стани:
- атаки — `rollModeReasons` (прапорці з `abilityEffects` уже потрапляють у `collectModifiers`) + нові `proneDefense` (за відстанню атакувальника до цілі) і `autoCritAdjacent` (у `attack/critical`);
- `frightened`/`charmed` — перевірка джерела (`ActiveEffect.source.participantId`) у валідації атаки/заклинання й руху (`grid/path.ts`);
- маркери (`skip_action`, `immobilized`, …) — як зараз, через `hasEffectMarker`.

### 3. Рятівні кидки

`rollSavingThrow` переходить на `rollSave({ target, ability, dc, participants, rules, rng, presetRoll, source })` у `lib/utils/battle/saves/`; усі виклики оновлюються, `rollSavingThrow` видаляється:
1. `autoFailSave` для цієї характеристики → провал без кидка (лог «автопровал»).
2. Режим кидка: `saveAdvantage`/`saveDisadvantage` (з урахуванням `vsSpells`, коли кидок проти заклинання) + виснаження 2014 рівня 3+; обидва → звичайний.
3. Бонус = модифікатор + майстерність (`saveProficiency` або `Character.savingThrows` за `rules.saves.proficiency`) + `modifyStat savingThrow` + виснаження 2024 (−2×рівень).
4. `presetRoll` (від клієнта) — перший d20; другий для переваги/перешкоди кидає сервер.

Результат містить `mode`, `rolls`, `bonus`, `autoFail` для лога й `actionDetails.savingThrows`. Виклики: `spell/cast/outcome.ts`, `maneuvers/fire-burst.ts`, повторні кидки `saveEnds`, концентрація, кидки смерті (вони — окремий d20 без модифікатора).

### 4. Кидки смерті (`rules.deathSaves.enabled`)

Наслідки шкоди (кидки смерті, масивна шкода, концентрація) рахує один хелпер `applyDamageConsequences({ before, after, amount, crit, rules, rng })` (`lib/utils/battle/damage/consequences.ts`), який викликається одразу після кожного примітиву шкоди (`applyDamageToTarget`, `applyRawDamage` у заклинаннях, маневрах, зонах, `dealDamage`, DOT). Коли обидві механіки вимкнено, він повертає `after` без змін.

Тільки для героїв і NPC-героїв (`createBattleParticipantFromCharacter`); юніти при `unitsDieAtZero` переходять у `dead` одразу на 0 HP.
- HP 0 → статус `unconscious` + стан `unconscious` (без тривалості) + `battleData.deathSaves = { successes: 0, failures: 0, stable: false }`.
- Шкода ≥ макс. HP понад 0 (залишок після падіння на 0) → одразу `dead`.
- Черга ходу непритомного нестабільного героя (у циклі пропуску `processEndOfTurn`): d20 (сервер; лог). 10+ — успіх, 1 — два провали, 20 — 1 HP, приходить до тями (стан знімається, лічильники скидаються). 3 успіхи → `stable`; 3 провали → `dead`. Хід пропускається, як і зараз.
- Шкода по герою на 0 HP: +1 провал (+2, якщо влучання критичне); стабільність скидається.
- Лікування > 0 → HP, стан `unconscious` знімається, лічильники скидаються.
- Чинне «союзники встають після перемоги» лишається.
- Вимкнено (default) — поточна поведінка без змін.

UI: у картці учасника на 0 HP — три кружечки успіхів і провалів (`components/battle`), у лозі — кидки.

### 5. Концентрація (`rules.concentration.enabled`)

- `SpellDefinitionSchema.concentration?: boolean` + перемикач у редакторі заклинання.
- Каст такого заклинання: кастер отримує `ActiveEffect` «Концентрація: <назва>» (`type: "buff"`, тривалість = найдовша тривалість ефектів заклинання, `concentration: { castId }`); усі `ActiveEffect` і зони, накладені цим кастом, отримують `concentrationOf: { casterId, castId }`. Новий каст із концентрацією спершу знімає попередню.
- Шкода по кастеру з концентрацією → рятівний кидок Вит (через `rollSave`) проти СК `max(10, ⌊шкода/2⌋)`, з межею `dcCap`, якщо вона задана. Провал, стан `incapacitated`, смерть чи 0 HP → концентрація зникає разом з усіма ефектами `concentrationOf` цього касту (на всіх учасниках і в зонах).
- Вимкнено — поле `concentration` ігнорується.

### 6. ДМ: накласти/зняти стан вручну

Новий бойовий роут `conditions` (Zod + `runBattleMutation` + `conditions-mutation.ts`, доступ `dm`): `{ participantId, action: "apply" | "remove", condition, rounds?, levels?, saveEnds? }`. Накладання використовує той самий шлях, що й `applyCondition`, тільки без ability-власника (джерело «ДМ»). UI: у швидких діях ДМ на учаснику — меню станів 5e (`ResponsiveDialog hud`: список станів з описом, тривалість; поточні стани з кнопкою «Зняти»). Меню показується, коли `rules.conditions.enabled` або в бою вже є 5e-стан; HOMM-кампанія за замовчуванням цього меню не бачить. Рушій обробляє 5e-стани незалежно від `enabled` (вони приходять лише з даних).

Показ: стани 5e — у наявному списку ефектів учасника з назвою, іконкою і тривалістю (`view`); для гравця видно стани ворогів (вони очевидні за столом).

### 7. Перевірка 4a

- Наявні тести рушія — без змін.
- Нові тести (`__tests__` поряд): реєстр (кожен стан → маркери/прапорці; `implies`), `applyCondition` з 5e-ключем, імунітети, виснаження 2014/2024 і накопичення рівнів, `saveEnds`; `rollSave` (автопровал, перевага/перешкода/скасування, майстерність з правил, `vsSpells`, preset + другий кубик); атаки по паралізованому з 5 фт (крит), по поваленому зблизька/здалеку, наляканий біля джерела; кидки смерті (успіхи, провали, 1, 20, шкода на 0, крит, масивна шкода, лікування, стабільність); концентрація (DC, межа, знімання ефектів інших учасників і зон, новий каст, недієздатність); роут `conditions` (DM-only, 403 для гравця); `parseRules` для нових секцій.

## Ризики

- **Перетин з HOMM-контролем.** `charm` (HOMM, перехід на бік) ≠ `charmed` (5e). Різні ключі й підписи; редактор показує 5e-стани окремою групою.
- **Розмір snapshot.** Стан додає один `ActiveEffect` з кількома прапорцями; на egress це не впливає помітно (дельти).
- **Клієнтські кидки.** Перевага на рятівному кидку з `presetRoll` — другий кубик кидає сервер; майстер заклинання показує режим кидка до підтвердження (через ту саму `rollSave`-логіку режиму, спільну для клієнта й сервера).
- **Концентрація на чужих ефектах.** Знімання за `concentrationOf` має проходити всіх учасників і зони за один прохід; тест на кілька цілей + зону обов'язковий.
