# Структура БД: оптимізованість, розширюваність, стабільність

Дослідження 2026-11-03. Джерела: `prisma/schema.prisma` (60 моделей, 58 міграцій від 2026-10-05), `lib/server/templates/**`, `lib/server/campaigns/**`, `lib/db.ts`, `lib/cache/reference-data.ts`, заміри на локальній prodcopy (PostgreSQL 17, 32 МБ).

Мета наступних кроків: багато одночасних сесій різних DM, без зайвої дублікації контенту шаблонів; локальні доповнення DM лишаються в його кампанії; усі клони отримують патчі шаблону.

## 1. Як влаштовано зараз

- **Усе контент-наповнення прив'язане до кампанії.** 13 контентних таблиць (`races`, `classes`, `feats`, `backgrounds`, `units`, `spells`, `spell_groups`, `main_skills`, `skills`, `skill_trees`, `artifact_sets`, `artifacts`, `campaign_tracks`) мають `campaignId` + `ON DELETE CASCADE`. Шаблон = рядок `campaigns` з `kind = "template"`.
- **Клон = повна копія.** `createCampaignFromBundle` експортує бандл шаблону, перегенеровує всі id (`newContentId`), переписує посилання всередині JSON (`remapIds` обходить усі рядки-значення), і робить `createMany` по таблицях в одній транзакції (timeout 60 с). На кожен рядок пишеться `sourceId` + `sourceHash`; у `campaign_source_syncs.baseline` лягає JSON з хешами всіх рядків (36–88 КБ на кампанію).
- **Патчі = pull.** DM запускає синхронізацію: `loadSyncContext` експортує **весь** бандл джерела, читає **всі** локальні рядки, 3-way-класифікує (source/baseline/local hash) → new/updated/conflict/deleted. Застосування переписує рядки й оновлює baseline. Push-повідомлень про нові патчі немає; версії шаблону немає.
- **Картинки не дублюються.** Іконки — URL у Supabase Storage; клон копіює лише рядок URL. На prodcopy: 4157 посилань, 1496 унікальних файлів, 0 data-URI. Шлях у бакеті містить `campaignId` **оригінального** шаблону (`spell-icons/cmvs44ooc…/spells/…`), тобто фактично картинки вже спільні між кампаніями. Mirror в свій бакет робиться лише для зовнішніх URL.
- **Бої:** `battle_scenes.version` + `updateMany where version` (optimistic lock, 409 при конфлікті), `battle_participants` як окремі рядки з `snapshotHash`, `battle_events`/`battle_snapshots` за `seq`. Записи в кампанію — `SELECT … FOR UPDATE` на `campaigns` (`lockCampaignRow`) і advisory lock на артефакти.
- **З'єднання:** Supavisor transaction mode (6543), `connection_limit=1`, `pool_timeout=10` на Vercel. Довідники кешуються `unstable_cache` на 300 с окремо на кожну кампанію.
- **RLS** увімкнено на всіх таблицях (тест `migrations-rls.test.ts`), політик немає: Prisma ходить під `postgres`, anon-ключ нічого не бачить.

### Ціна одного клону SRD-шаблону (prodcopy)

| Таблиця | Рядків | Байт у рядках | Середній рядок |
|---|---|---|---|
| spells | 996 | 1 363 КБ | 1.4 КБ |
| units | 662 | 1 165 КБ | 1.8 КБ |
| artifacts | 666 | 819 КБ | 1.3 КБ |
| classes | 24 | 252 КБ | 11 КБ |
| feats / races / backgrounds / spell_groups | 84 | ~107 КБ | — |
| **Разом** | **~2 430** | **~3.7 МБ** | + індекси ≈ 0.7 МБ |

Отже один клон ≈ 4.5 МБ на диску і ~2.4 тис. рядків. 100 кампаній ≈ 450 МБ (ліміт Supabase Free — 500 МБ), 1 000 кампаній ≈ 4.5 ГБ (Pro включає 8 ГБ). Дублікація — це не «вибух», а лінійна стаття витрат, яка стає відчутною від кількох сотень кампаній. Головна шкода не в гігабайтах, а в тому, що **кожна операція з шаблоном (клон, diff, sync) лінійна від розміру шаблону, а не від розміру зміни**.

## 2. Що зроблено добре (не чіпати)

- Чітка межа кампанії: `campaignId` + cascade на всіх дочірніх таблицях, `loadOwned` на API, `assertNoLeak`/`findForeignContentIds` при імпорті. Для «багато DM одночасно» це правильна модель: гарячі записи (бій, персонаж, інвентар) ізольовані по кампаніях, спільної точки contention немає.
- Optimistic versioning бою + окремі рядки учасників + журнал подій за `seq` — стабільна основа для real-time і відновлення.
- Міграції expand-only, RLS за замовчуванням, FK-індекси доставлені окремою міграцією (`20261112_fk_indexes`).
- Sync уже тривимірний (source/baseline/local) з хешами рядків — це саме той алгоритм, який потрібен для патчів шаблону; змінювати треба лише *над чим* він працює.
- Транзакційний контекст для записів (`createScopedDatabase` + `afterCommit`), rate-limit, idempotency для AI-дій.

## 3. Слабкі місця

### 3.1 Модель «шаблон = копія» (головне)

1. **Лінійна вартість.** Клон — 2.4 тис. INSERT в одній 60-секундній транзакції; diff/sync — експорт усього шаблону + читання всіх локальних рядків + хешування всього при кожному відкритті екрана синхронізації.
2. **Ідентифікатори не стабільні між кампаніями.** Кожен клон отримує нові id, тому посилання з JSON (`knownSpells`, `abilities`, `choices`, `itemStats`, `perform.attack`) переписуються рядковим обходом (`remapIds`, `collectKeysAndStrings`) і частина зв'язків узагалі за іменами (`name-references.ts`). Це крихко: нове JSON-поле з id або перейменування в шаблоні ламає посилання тихо.
3. **Патчі — тільки pull і тільки повний.** Немає `version`/changelog шаблону, немає індексу на `campaigns.createdFromId`, тож «кому розіслати патч» — seq scan, а «що змінилось з версії N» — перерахунок хешів усього.
4. **Локальні правки й шаблон живуть в одній таблиці** без ознаки «перекриває джерело» окрім `sourceHash != hash`. Відкотити локальну правку до шаблону або показати «ваші зміни» — це знову повний diff.

### 3.2 Схема

- **JSON без схеми в БД.** У контентних таблицях більшість полів — `Json` (у `spells` 17 JSON-колонок, у `classes` `features`/`subclasses`/`columns` по 11 КБ на рядок). Валідація лише в Zod; CHECK/enum у Postgres немає, `kind`/`status`/`visibility` — вільні рядки. Для розширюваності це плюс (нові механіки без міграцій), для стабільності — усе тримається на дисципліні коду.
- **Пропущені індекси** (FK або id-колонки без індексу): `campaigns.createdFromId`, `character_skills.skillTreeId`, `main_skills.spellGroupId`, `ai_threads.scenarioPageId`, `player_notifications.campaignId`, `world_positions.mapId`, `world_reveals.characterId`, `world_travel_log.{mapId,toMarkerId,byUserId}`, `world_notes.{authorUserId,characterId}`, `acquaintance_notes.authorUserId`. Зараз непомітно (таблиці маленькі), але це рівно ті таблиці, що ростуть із кількістю сесій.
- **`sourceId` ніде не індексований** — sync шукає по `campaignId` і фільтрує в пам'яті; для layered-моделі (нижче) буде потрібен `(campaignId, sourceId)`.
- **Історія росте без ретеншну:** `battle_snapshots`, `battle_events`, `scenario_page_versions`, `inventory_log`, `character_logs`, `world_travel_log`. Є cleanup лише для assistant-даних і нотифікацій.
- `characters.controlledBy` — `String` (not null) з `onDelete: SetNull`; при видаленні користувача це впаде на NOT NULL. Дрібниця, але стабільність.

### 3.3 Конкурентність і пул

- `connection_limit=1` на інстанс Vercel. З Fluid Compute один інстанс обслуговує кілька запитів одночасно, і всі вони стоять у черзі за одним з'єднанням (`pool_timeout=10` → помилки при сплеску). Supavisor у transaction mode спокійно тримає десятки клієнтських з'єднань; розумний старт — 5–10 на інстанс і заміри.
- Клон у 60-секундній інтерактивній транзакції тримає з'єднання і блокує bucket Supavisor; при 5–10 DM, які одночасно створюють кампанії, це вже черга.
- `unstable_cache` на кампанію: 100 кампаній з одного шаблону = 100 копій одного списку з 1 000 заклинань у Data Cache (1.4 МБ кожна) і 100 окремих прогрівів з БД. Кеш не знає, що контент спільний.

### 3.4 Картинки

Фактично вже спільні (URL), але це випадковість шляху `{campaignId оригіналу}/…`, а не контракт: шлях прив'язаний до id давно видаленого шаблону, `upsert` по тому ж шляху тихо міняє картинку всім клонам (добре для патчів, погано для «DM замінив іконку в себе» — mirror у свій бакет робиться лише для зовнішніх URL, тобто локальна заміна працює, а от видалення файлу шаблону зламає всіх). Потрібен явний контракт «спільні ассети шаблону» + політика незмінності (`cacheControl` рік уже стоїть).

## 4. Цільова структура: шари контенту замість копій

Ідея: контент шаблону зберігається **один раз** як незмінні версії; кампанія посилається на версію й тримає лише **свій шар**: додані рядки, перекриття (override) і приховані рядки. Читання = базовий шар ∖ приховані ∪ перекриття ∪ локальні.

```
content_sets          (id, key "srd-5.2", ownerUserId?, visibility)
content_set_versions  (setId, version, createdAt, changelog json)  -- незмінні
content_rows          (setId, version, table, id, data jsonb, hash)  -- id стабільний між версіями
campaigns.baseSetId / campaigns.baseVersion
campaign_content      (campaignId, table, id, op: 'add'|'override'|'hide', data jsonb, baseHash)
```

Ключові рішення:

1. **Глобально стабільні id контенту.** Рядок `spells/fireball` має той самий id у шаблоні й у всіх кампаніях. Зникає `remapIds`, зникають посилання за іменами, персонажі посилаються на id, які переживають патчі.
2. **Патч = нова версія** (`content_set_versions`), diff між версіями — одна вибірка по `hash`. Апгрейд кампанії: для рядків без override — автоматично (просто `baseVersion++`), для override — той самий 3-way-класифікатор, що є зараз, але лише над `campaign_content` (десятки рядків, а не тисячі). Push: один запит `where baseSetId = ? and baseVersion < ?` з індексом.
3. **Читання через один шар.** Усі читачі довідників уже централізовані (`lib/cache/reference-data.ts`, `lib/server/<domain>/read-*.ts`, content service) — саме там збирається «ефективний» список. Варіант у Postgres: view/функція `effective_rows(campaignId, table)`; варіант у коді: два `findMany` + merge у пам'яті, кеш базового шару **на версію**, а не на кампанію (100 кампаній — один кеш).
4. **Запис DM:** редагування базового рядка створює `override` (копія `data` + `baseHash`); «скинути до шаблону» = видалити override; видалення базового = `hide`. Усе це вже концептуально є у статусах sync.
5. **Ассети:** `content_assets (setId, hash, url)`, шлях у бакеті `sets/{setKey}/{hash}.webp`, незмінні; патч із новою іконкою = новий файл, старий лишається поки на нього посилається хоч одна версія.

Що лишається **без змін**: кампанійні таблиці (персонажі, бої, інвентар, сценарій, світ), RLS, cascade, механіка бою, Zod-схеми рядків. Міняється шар зберігання контенту й sync.

### Міграція (expand-only, по кроках)

1. **Зараз, дешево:** індекси з 3.2, `connection_limit` 5–10 + заміри, ретеншн для `battle_snapshots`/`scenario_page_versions`, явний контракт для шляхів іконок.
2. **Версії й push без зміни моделі:** `campaigns.contentVersion` у шаблоні (+1 при кожному записі в template-кампанію), `(createdFromId)` індекс, повідомлення «є оновлення» клонам, sync-diff лише коли версія змінилась (кеш бандла шаблону на версію). Це знімає найбільший біль (повний перерахунок) за день роботи.
3. **Стабільні id:** нові клони перестають перегенеровувати id базових рядків (`newContentId` лише для локальних), `(campaignId, id)` унікальність уже є. Старі кампанії живуть зі своїми id, `sourceId` — міст.
4. **Шари:** `content_rows` + `campaign_content`, читачі збирають ефективний список, нові кампанії створюються без копіювання. Старі кампанії переносяться скриптом: рядок з `hash == sourceHash` → видалити (він у базовому шарі), інакше → `override`, без `sourceId` → `add`.
5. Видалити copy-on-clone і `remapIds`.

## 5. Відповідь на три питання

- **Оптимізованість:** для поточного масштабу (десяток кампаній) — достатня: індекси на гарячих шляхах є, дельти в боях є, кеш довідників є. Не масштабується лінійно по кількості кампаній на одному шаблоні: диск, кеш і час sync ростуть пропорційно розміру шаблону × кількість клонів.
- **Розширюваність:** висока по «ширині» (нові поля/механіки — JSON без міграцій, новий мод/домен — нова таблиця з `campaignId`), низька по «глибині» (шаблон не має версій, контент не має стабільних id, посилання в JSON — рядки). Саме це блокує патчі й шари.
- **Стабільність:** транзакційна модель, блокування, версії боїв, RLS і expand-only — у порядку. Ризики: пул з'єднань на Vercel під паралельним навантаженням, відсутність ретеншну історії, крихкість `remapIds`/name-references при зміні шаблону, недоіндексовані world/notification таблиці.

Рекомендація: крок 1 і 2 зробити зараз (вони корисні за будь-якої подальшої моделі), крок 3–5 оформити як окремий епік «content layers» після альфи, разом з інфра-планом (`docs/product/infra-prod-plan-2026-10-28.md`), бо саме там з'являються реальні цифри по кількості кампаній.
