# Spike 2 — рендер сітки на 60×60, 100×100, 200×200 (без браузера)

**Дата:** 2026-11-14 · **Гілка:** `feat/map-editor-d` (від `d634fc3f3`) · **До етапу:** D ([spec](../specs/2026-11-14-map-editor-stage-d-design.md), [план](../plans/2026-11-14-map-editor-stage-d.md))

## Що і як міряли

Браузерних замірів немає (рішення користувача: лише в кінцевому живому прогоні епіку). Замість цього:

- **DOM/рендер** — `<BattleMap>` у happy-dom (vitest), той самий компонент, що в бою: кількість елементів, монтування, перерендер при появі зони руху ДМ і при «наведенні» (нова `Map` позначок з тим самим вмістом, як робить `composeMapView`), `renderToString` (SSR) і розмір HTML.
- **CPU алгоритмів** — node, медіана 7 запусків після прогріву.
- **Синтетичні дані** (`scripts/spikes/map-grid-render/scenario.ts`, детерміновано): карта n×n без фону, рамка `blocked` 2 клітинки, ~5% terrain (стіна/складна/hazard зі шкодою/зона-туман; ліміт `maxTerrainCells = 3600`), ~2n ребер-стін, 8 героїв + 8 ворогів ДМ у центрі; «мувер ДМ» — ворог (`moveBudget` = `cols*rows`).

Скрипти (окремий vitest-конфіг, у звичайний набір тестів не потрапляють):

```bash
SPIKE_OUT=/tmp/spike pnpm exec vitest run -c scripts/spikes/map-grid-render/vitest.config.mts scripts/spikes/map-grid-render/algorithms.spike.ts
# рендер — по одному розміру на процес (happy-dom на 200×200 падає з OOM за стандартного heap ~4 ГБ)
NODE_OPTIONS=--max-old-space-size=12288 SPIKE_SIDES=60  SPIKE_OUT=/tmp/spike pnpm exec vitest run -c scripts/spikes/map-grid-render/vitest.config.mts scripts/spikes/map-grid-render/render.spike.tsx
NODE_OPTIONS=--max-old-space-size=12288 SPIKE_SIDES=100 SPIKE_OUT=/tmp/spike pnpm exec vitest run -c …  render.spike.tsx
NODE_OPTIONS=--max-old-space-size=12288 SPIKE_SIDES=200 SPIKE_RENDER_RUNS=1 SPIKE_OUT=/tmp/spike pnpm exec vitest run -c … render.spike.tsx
```

Машина: Apple Silicon (dev-ноутбук), Node 22. Абсолютні мілісекунди happy-dom ≠ браузер (вставка DOM у happy-dom значно повільніша), але **масштабування** за N і кількість елементів — ті самі, що в браузері. Для телефона закладати множник 3–5× до node-цифр алгоритмів.

## Висновки

1. **Головна вартість — DOM, лінійна за площею, і множиться позначками.** Клітинка = `<polygon>` + 3 обробники; зона руху ДМ додає ще 2 полігони на кожну досяжну клітинку (`glow` + `stroke`) → ~110 тис. полігонів на 200×200, 27 МБ SSR-HTML. Перерендер при появі зони в happy-dom — 51 с (нелінійно; у браузері дешевше, але порядок «сотні мс–секунди на телефоні» реальний вже на 100×100).
2. **Наведення під час прицілювання** перерендерює всю сітку (нова `Map` з усіма `out-of-range`): 1,2 с на 200×200 у happy-dom на кожну клітинку під курсором.
3. **`moveBudget` ДМ** = площа карти → `searchPaths` ~100 мс у node на 200×200 (телефон — 300–500 мс) і та сама вартість на сервері в `move-mutation`.
4. **Нова знахідка: `placeParticipants`** — ~100 мс на 16 нерозставлених на 200×200: `sideAnchors` будує й фільтрує весь список клітинок на кожного учасника. В аудиті цього не було.
5. **`outOfRangeMarks`** — 25 мс на кожну зміну прицілу, хоча метрика Чебишова (`footprintDistance`) дає прямокутник → O(1).
6. **Дешеві за фактом:** `hazardCells` (≤ 0,1 мс), `cellsByDistance`/`nearestStandable` (≤ 2 мс на виклик, але множаться на кількість учасників/викликів), `playableBounds` (2 мс), `applyTerrainDiff` (0,27 мс) — бо terrain обмежений 3 600 клітинками. Чанковий terrain у D не потрібен; кільця/кеші — дешеві виправлення «за звичкою», а не за вимірами.
7. Рішення етапу D: злиті SVG-контури замість клітинка = елемент (кількість елементів не залежить від N), делегований pointer, дальність прямокутником, `dmMoveCap`, кеш `sideAnchors` — див. spec §3–4.
